# 08 · 非功能与运维方案

> **定位**：回答「这套系统上线后怎么保证不崩、崩了怎么发现、发现后怎么恢复、数据怎么不丢」。
> **上游**：PRD §15（非功能，量化）、§16（容量目标）、§13（日志规则）、§17（系统集成）、`01-总体设计方案`（部署单元）、`06-调度引擎详细设计`（恢复窗口）。
> **关键原则**：**每项非功能要求必须落到「可测量的指标 + 有负责人的动作」**，否则等于没写。

## 1. 非功能目标的量化基线（对齐 PRD §15/§16）

### 1.1 指标 → 设计 → 验证 的映射

> PRD 给了要求，本文给「靠什么实现」和「怎么证明达到了」。

| # | 指标（PRD 出处） | 目标值 | 靠什么实现 | 怎么验证 |
|---|---|---|---|---|
| N-1 | 调度链路可用性（§15.1） | **≥ 99.9%**（月停机 ≤ 43 分钟） | 调度器选主切换 ≤ 45s；PG 流复制；Redis Sentinel；**scheduler 常备 2 副本** | 月度可用性报表（§6.2） |
| N-2 | 调度器故障恢复（§15.1） | **≤ 45 秒**自动切换 | Redisson 分布式锁选主（`06 §10.1`）；看门狗 TTL 30s + 恢复 < 5s | 混沌测试：kill -9 调度器，测恢复时长 |
| N-3 | 平台重启后状态恢复（§15.1） | 任务状态 **0 丢失** | PG 为唯一真源（D-09）；启动时从 PG 重建就绪队列 | 重启演练：对比重启前后任务状态分布 |
| N-4 | 单节点异常不影响平台（§15.1） | 平台整体可用 | 节点隔离；心跳 3 次缺失判离线（`06 §8.1`） | 断网单节点，观察平台与其他任务不受影响 |
| N-5 | 任务列表查询（§15.4） | **< 3 秒**（10 万条历史） | 分页索引（`05 §4`）；`total_capped` 防深翻页 | 造 10 万条数据后压测 |
| N-6 | 任务详情 DAG 渲染（§15.4） | **< 3 秒**（100 步骤） | 单次聚合返回（`GET /tasks/{id}` 含 steps）；SVG 画布虚拟化 | 100 步骤任务实测 |
| N-7 | 实时日志延迟（§15.4） | **< 5 秒** | WebSocket + Redis Pub/Sub（D-10） | 打时间戳比对（算子输出时间 vs 前端渲染时间） |
| N-8 | 单工作流步骤数（§15.4） | **≥ 100**（一期 100 / 3 年 300） | DAG 内存表示（`06 §7.1`）；邻接表推进 | 300 步骤工作流跑通 |
| N-9 | 全平台并发运行任务（§15.4/§16） | **≥ 300**（一期）/ 1200（3 年） | 线程模型（`06 §13`）；连接池；Redis ZSet | 压测至 300 并发运行 |
| N-10 | 调度决策延迟（§15.4） | **< 5 秒**（可调度 → 派发） | 单线程 tick 1s（`06 §3.1`） | 队列堆积时测端到端延迟 |
| N-11 | 日志延迟与保留（§13.2/§16） | 热存 30 天 + 冷存 90 天 | `task_log` 分区表 + DROP PARTITION（M-02） | 检查分区滚动与归档任务执行记录 |
| N-12 | 审计日志保留（§16） | **3 年** | 独立表，不随任务清理；年度归档到冷表 | 检查保留策略配置 |
| N-13 | 任务记录保留（§16） | 1 年（一期）/ 3 年 | **一期 `task` 单表**（`05 §7.1`）；> 5000 万行后再按 `created_at` 分区 + 年度 DROP | 检查清理任务执行记录 |
| N-14 | 敏感数据不泄漏（§15.3） | **0 起明文泄漏** | 凭据 AES-256-GCM；日志脱敏过滤器；运维视图字段级脱敏 | 安全测试：全链路抓包搜明文 |
| N-15 | 平台自身健康可见（§15.5-5） | 独立于业务监控 | `/actuator/health` + 自研健康页（§5.3） | 面板存在性检查 |

### 1.2 容量规划（PRD §16 的具体落法）

**首年目标 → 资源估算**：

| 维度 | 首年 | 3 年 | 对资源的直接影响 |
|---|---|---|---|
| 项目数 | 30 | 100 | 权限查询走缓存，无压力 |
| 集群数 | 5 | 15 | 调度器单活可覆盖（`06 §10.1`） |
| 执行节点 | 200 | 800 | 心跳写入：200 台 × (1/15s) ≈ **13 次/秒**（3 年 53 次/秒） |
| 日均任务量 | 5,000 | 20,000 | 峰值 500/h ≈ **0.14 次/秒**（3 年 0.56 次/秒） |
| 并发运行任务 | 300 | 1,200 | 调度器内存：每任务约 50KB → **15MB / 60MB** |
| 单任务步骤 | 100 | 300 | 单任务状态内存：100 步 × 2KB = 200KB（可忽略） |
| 日志量 | 50 GB/天 | 200 GB/天 | **最大资源消耗项**，见下 |
| 任务记录 | 1 年 | 3 年 | 5000/天 × 365 = **182 万行/年** |

**存储估算（一期首年）**：

| 表 | 行数/年 | 单行估算 | 年增量 | 备注 |
|---|---|---|---|---|
| `task` | 182 万 | ~2 KB | **3.6 GB** | 含 JSONB 快照 |
| `task_step` | 182 万 × 平均 8 步 = **1456 万** | ~1.5 KB | **21 GB** | 一期单表（M-04），> 3000 万行分区 |
| `task_log` | 按 50 GB/天 × 365 | 压缩后 ~15 GB/天 | **5.4 TB** | ⚠️ **必须分区 + 定期 DROP** |
| `audit_log` | ~500/天 = 18 万 | ~1.5 KB | 270 MB | 保留 3 年 |
| 其他（项目/集群/算子/工作流等） | 少 | — | < 1 GB | 可忽略 |

> **⚠️ 结论：日志是唯一需要认真规划的存储项**。一期 5.4 TB/年（3 年 21 TB）。方案：PG 分区表存**热 30 天**（约 450 GB），冷存 90 天落对象存储（压缩后约 1.3 TB）——见 §4.2。

**PG 实例规格建议**：

| 项 | 一期（首年） | 3 年 | 说明 |
|---|---|---|---|
| 规格 | 8C / 32G / SSD 2TB | 16C / 64G / SSD 8TB | 日志分区占大头 |
| 连接池（HikariCP） | maximum-pool-size = **30** | 50 | server 多副本共享；PG `max_connections = 300` |
| 复制 | 流复制 + 1 备库 | 同 | 备库用于只读报表 + 故障切换 |
| 分区 | **`task_log` 按 `log_time` 按日分区；`audit_log` 按 `operated_at` 按月分区；`task` / `task_step` 一期单表**（`05 §7.1`） | 达阈值后启用 | 见 `05 §7.1` |

> **v3 评审修订**：此行原写「`task_log` / `task` 按 `created_at` 月分区」，与 `05 §7.1` 不符，且会导致 §4.2 的「年度 DROP PARTITION 清理任务记录」在一期无分区可操作（表根本没分区）。**分区真源是 `05 §7.1`**。

**Redis 规格**：

| 项 | 值 | 说明 |
|---|---|---|
| 内存 | **4 GB**（一期）/ 8 GB | 派遣生态（队列/锁/心跳）+ 日志 Stream 缓存（2h TTL） |
| 持久化 | AOF everysec | 派生态可重建（D-09），AOF 只为缩短恢复时间 |
| 部署 | Sentinel 3 节点 | 避免单点；不与业务 Redis 混用 |
| 淘汰策略 | `noeviction` | ⚠️ **禁止 LRU 淘汰**——队列/锁被淘汰会导致调度错乱 |

### 1.2.1 资源申请清单（PR-4 · M0 硬阻塞项）

> **用途**：直接作为向运维/云资源申请的依据。规格取自本文 §1.2 容量估算与 §2.2 副本数，**不含冗余余量以外的富余**。
>
> **环境分级**（`09 §4.2`）：`dev`（本地开发）→ `test`（CI/联调）→ `uat`（试点前）→ `prod`。**M0 只需 dev；M1 必须要有 test**，因为 SSH 与日志链路不能只用 mock 验证。

**① 应用服务器（跑 server + scheduler + nginx）**

| 项 | M0 / dev | M1 / test | prod | 说明 |
|---|---|---|---|---|
| 台数 | 1 | 2 | **2** | prod 2 台是为了 99.9%；每台各跑 1 个 server + 1 个 scheduler |

## 2. 部署架构

### 2.1 部署单元（承 `01 §4.1`）

```
                          ┌──────────────┐
                          │   Nginx      │  TLS 终止 / 静态资源 / WS 升级
                          └──────┬───────┘
                    ┌────────────┴───────────┐
                    ▼                        ▼
            ┌───────────────┐        ┌──────────────────┐
            │  flowops-web  │        │  flowops-server  │  × N（无状态，可随意扩缩）
            │  (静态资源)   │        │  Spring Boot 3   │
            └───────────────┘        └────────┬─────────┘
                                              │
                    ┌─────────────────────────┼──────────────────────┐
                    ▼                         ▼                      ▼
            ┌───────────────┐        ┌───────────────┐      ┌────────────────┐
            │  PostgreSQL   │        │    Redis      │      │ flowops-         │
            │  (主 + 备)    │        │  (Sentinel)   │      │ scheduler ×2     │
            └───────────────┘        └───────┬───────┘      │ (1 活 + 1 备)     │
                                             │              └────────┬───────┘
                                             │                       │
                                             └───────────────────────┘
                                                                     │ SSH/WinRM
                                                                     ▼
                                                          ┌────────────────────┐
                                                          │ 执行节点（200+ 台）  │
                                                          └────────────────────┘
```

### 2.2 进程职责与副本数

| 进程 | 副本 | 状态 | 说明 |
|---|---|---|---|
| `flowops-web` | 1（Nginx 服务静态资源） | 无状态 | 构建产物，可 CDN |
| `flowops-server` | **≥ 2** | 无状态 | 承载全部 REST + WebSocket |
| `flowops-scheduler` | **2 副本**（严格 1 活） | **有状态** | 单活选主（`06 §10.1`）；**不做多副本负载**，冗余靠「常备 standby 抢锁」 |
| PostgreSQL | 1 主 1 备 | 有状态 | 流复制 |
| Redis | 3（Sentinel） | 有状态 | 主从 + 哨兵 |

> **⚠️ 关键约束**：`flowops-scheduler` **不能横向扩容**。两个调度器同时运行会造成重复派发（尽管有 CAS 兜底，但会产生大量冲突日志与资源震荡）。冗余通过「备进程 + 选主」实现，不做负载分担。集群数 > 50 时再评估按集群分片（B-03/E-06）。
>
> **⚠️ v3 评审修订（A-2）**：副本数由 1 改为 **2**。原写「固定 1，冗余靠 standby 手动/编排拉起」——但进程崩溃后要先等编排层重新拉起容器（数十秒~数分钟），而 N-1（99.9%）与 N-2（≤45s）要求"有进程在等着抢锁"，单副本在**物理上无法达成**。改为 2 副本：二者竞争同一把 Redisson 锁，**实际只有 1 个活跃**，多副本不会导致重复调度。该约定未来上 K8s 同样适用（`02 §4.2`）。

### 2.3 Docker Compose（一期推荐）

```yaml
# deploy/docker-compose.yml（节选）
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: flowops
      POSTGRES_INITDB_ARGS: "--encoding=UTF8 --locale=C"
    volumes:
      - pgdata:/var/lib/postgresql/data
    command: >
      postgres -c max_connections=300 -c shared_buffers=8GB
               -c work_mem=32MB -c maintenance_work_mem=1GB
               -c wal_level=replica -c max_wal_senders=5
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U flowops"]
      interval: 10s
      retries: 5

  redis:
    image: redis:7-alpine
    command: redis-server --appendonly yes --maxmemory 4gb --maxmemory-policy noeviction
    volumes:
      - redisdata:/data

  server:
    image: flowops/server:${TAG}
    environment:
      SPRING_PROFILES_ACTIVE: prod
      DB_URL: jdbc:postgresql://postgres:5432/flowops
      REDIS_HOST: redis
      FLOWOPS_CRED_MASTER_KEY: ${FLOWOPS_CRED_MASTER_KEY}   # ← 缺失则拒绝启动（M-06）
      JAVA_OPTS: "-Xms2g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200"
    depends_on:
      postgres: { condition: service_healthy }
      redis:    { condition: service_started }
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/actuator/health"]
      interval: 15s
      start_period: 60s
    deploy:
      replicas: 2

  scheduler:
    image: flowops/scheduler:${TAG}
    environment:
      SPRING_PROFILES_ACTIVE: prod
      DB_URL: jdbc:postgresql://postgres:5432/flowops
      REDIS_HOST: redis
      FLOWOPS_CRED_MASTER_KEY: ${FLOWOPS_CRED_MASTER_KEY}
      FLOWOPS_SCHEDULER_ID: scheduler-1        # 实例标识（每个副本必须不同），用于 standby 心跳与日志区分
      JAVA_OPTS: "-Xms1g -Xmx2g -XX:+UseG1GC"
    depends_on:
      postgres: { condition: service_healthy }
    deploy:
      # ⭐ 2 副本：一主一备，竞争同一把 Redisson 锁，实际只有 1 个活跃
      #    单副本 = 崩溃后要等编排层拉起容器 → N-2（≤45s）无法达成
      replicas: 2
```

| 变量 | 必填 | 说明 |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | ✓ | `dev` / `test` / `prod` |
| `DB_URL` / `DB_USER` / `DB_PASSWORD` | ✓ | |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` | ✓ | |
| `FLOWOPS_CRED_MASTER_KEY` | ✓ | AES-256 主密钥（32 字节 base64）；**缺失则拒绝启动** |
| `FLOWOPS_SCHEDULER_ID` | ✓（scheduler） | 实例标识（**每个副本必须唯一**），用于 standby 心跳 key 与日志区分 |

### 2.4 版本与发布

| 项 | 约定 |
|---|---|
| 版本号 | 语义化 `vMAJOR.MINOR.PATCH`；镜像 tag = git commit short sha |
| 发布方式 | **滚动发布**（server）；scheduler 为**停-启**（单活，需短暂停机 **≤ 45s**，与 N-2 对齐） |
| DB 迁移 | **Flyway**（版本化 SQL，`V{timestamp}__{desc}.sql`），随 server 启动自动执行 |
| 迁移纪律 | ① **只增不删**（删列先改代码不再引用，下个版本再删）；② 大表加列必须 `NULL` 可空或带默认值；③ 索引用 `CREATE INDEX CONCURRENTLY`（在独立迁移脚本中） |
| 回滚 | server 可回滚到上一镜像；**DB 不回滚**（前向兼容设计）；scheduler 回滚需先确认无新版本任务在跑 |
| 灰度 | 一期不做灰度发布（内部平台、用户少）；试点团队即灰度（PRD §21.5） |

## 3. 可观测性

> PRD §15.5 五条要求的逐条落地。**原则：能自动发现的问题，绝不依赖用户上报。**

### 3.1 三大支柱

| 支柱 | 方案 | 数据去向 |

| **Metrics** | Spring Boot Actuator + Micrometer → Prometheus 格式 | Prometheus → Grafana（PRD §17 要求对接公司监控体系） |

### 3.3 日志规范

**格式（JSON，structlog 风格）**：

```json
{
  "ts": "2026-09-21T15:33:11.234+08:00",
  "level": "INFO",
  "logger": "c.f.s.scheduler.DispatchService",
  "trace_id": "0af7651916cd43dd8448eb211c80319c",
  "task_id": "TASK-20260921-0001",
  "step_instance_id": 88213,
  "msg": "step dispatched",
  "node_id": 42,
  "queue_id": 3,
  "duration_ms": 128
}
```

**分级使用纪律**：

| 级别 | 用途 | 示例 |
|---|---|---|
| `ERROR` | **需要人介入**的失败 | DB 连接失败、选主丢失、审计写失败 |
| `WARN` | 可自愈但需关注 | 重试、节点心跳超时、队列积压、连接池等待 |
| `INFO` | 关键状态变更（**审计级**） | 任务状态流转、派发决策、发布版本 |
| `DEBUG` | 排障细节（**prod 默认关闭**，可动态开启） | 变量解析过程、节点匹配打分明细 |

**动态日志级别**：`POST /actuator/loggers/{logger}` 支持运行期调整（排障用，`platform:config` 权限控制，操作记审计）。

**日志脱敏（PRD §15.3-2/§13.3）**：

```java
// 全局兜底：Logback 自定义 Converter
// 命中以下模式的内容在写入前替换
//   password/passwd/pwd/secret/token/api[_-]?key/private[_-]?key 后跟 : 或 = 的值
// 输出: password=***

// 精确控制：字段级
@MaskLog  // 标注在 DTO 字段，请求/响应日志记录器识别
private String secret;
```

**三层脱敏**（缺一不可）：

| 层 | 手段 | 覆盖 |
|---|---|---|
| ① 应用日志 | Logback Converter + `@MaskLog` | 平台自身日志 |
| ② 任务日志 | 日志采集器在落库前做正则替换（敏感值来自 `variable_snapshot` 的 `sensitive` 标记 + 通用模式） | 算子输出 |
| ③ 界面/接口 | 运维视图字段级脱敏（`07 §5.3`） | 前端展示 |

### 3.4 调度决策可追踪（PRD §15.5-2）

**要求**：每次调度决策记录输入与结果。

**实现**：`06 §3.3` 的 tick 幂等性要求 + 决策快照表。

> **v3 评审修订（A-4）**：原 DDL 只存在于本文，`05` 无表、`06` 无写入时机 → 任务详情「调度诊断」面板声称"直接查此表"，但该表不会被建也不会被写。**DDL 已迁至 `05 §3.5`，写入时机已固化于 `06 §14.2.1`**（四类决策 DISPATCHED/DEFERRED/BLOCKED/SKIPPED 的写入点）。下表保留作说明，实现以 `05` 的 DDL 为准。

```sql
-- 见 05 §3.5 正式 DDL（此处仅示意结构）
CREATE TABLE schedule_decision_log (
    id              bigserial PRIMARY KEY,
    trace_id        varchar(32)  NOT NULL,
    task_id         bigint       NOT NULL,
    step_instance_id bigint,
    decided_at      timestamptz  NOT NULL DEFAULT now(),
    decision        varchar(32)  NOT NULL,  -- DISPATCHED / DEFERRED / BLOCKED / SKIPPED
    reason_code     varchar(64),            -- NO_MATCHING_NODE / CONCURRENCY_LIMIT / ...
    input_snapshot  jsonb,                  -- 候选节点、资源、并发计数（脱敏后）
    chosen_node_id  bigint,
    score_detail    jsonb                   -- 三级排序打分明细
);

-- 只保留 7 天（排障用，不做长期存储）
CREATE INDEX idx_schedlog_task ON schedule_decision_log(task_id, decided_at DESC);
```

**保留策略**：7 天 TTL，按日清理（`DELETE ... WHERE decided_at < now() - interval '7 days'`）。
**价值**：任务详情「调度诊断」面板（PRD §10.10）直接查此表，回答「为什么不给我调度」。

### 4.1 安全清单（对齐 PRD §15.3 八条）

| PRD 要求 | 实现 |
|---|---|
| §15.3-1 凭据不明文展示（**含管理员**） | AES-256-GCM 加密存储；接口只返回后 4 位；**无任何「查看明文」端点** |

| §15.3-8 跨项目访问留痕 | audit_log 的 `cross_project=true` 标记 + 专项报表 |

### 4.2 数据生命周期

| 数据 | 热存 | 冷存 | 归档 | 销毁 |
|---|---|---|---|---|
| `task_log` | **30 天**（PG **按日**分区，可查可搜） | **90 天**（对象存储，按需恢复） | 按月打包 gzip | 120 天后自动删除 |
| `task` / `task_step` | **1 年**（一期）/ 3 年 | — | 一期单表 + 按 `created_at` **DELETE 分批清理**；启用分区后再用 DETACH | 按保留期清理 |

> **v3 评审修订**：`task` / `task_step` **一期是单表**（`05 §7.1`），原「年度分区 DETACH」在一期无分区可操作；且 `task_log` 是**按日**分区（不是按月），§4.2 的归档任务步骤 1「找出 30 天前的月分区」亦需改为按日。
| `audit_log` | **3 年** | 年度冷表 | — | 3 年后归档销毁（合规要求） |
| `schedule_decision_log` | **7 天** | — | — | 按日 DELETE |
| 执行节点心跳 | **7 天明细** | — | 按日聚合为指标 | 明细删除，聚合保留 1 年 |
| 算子文件 | 永久 | — | — | 版本删除时清理（`ref_count=0`） |

**日志归档任务（每日 02:00）**：

```
1. 找出 30 天前的 task_log **按日分区**（task_log_YYYYMMDD，见 05 §7.1）
2. COPY 到 gzip 文件 → 上传对象存储（{tenant}/logs/{yyyy-MM}/{task_id}.log.gz）
3. 校验上传成功（比对行数 + sha256）
4. ALTER TABLE task_log DETACH PARTITION + DROP
5. 写 audit_log（action=ARCHIVE_LOGS）
6. 失败则告警且**不删除源分区**（宁可占空间，不可丢数据）
```

**冷日志按需恢复**：任务详情查 30 天以上日志 → 前端提示「日志已归档」→ 点「申请恢复」→ 异步拉回 → 状态从 `ARCHIVED` 变 `RESTORED`（SLA：30 分钟内）。

### 4.3 备份与恢复（RPO/RTO）

| 对象 | 备份方式 | 频率 | RPO | RTO |
|---|---|---|---|---|
| PostgreSQL | `pg_basebackup` 全备 + WAL 归档 | 全备每日 01:00；WAL 连续 | **≤ 5 分钟** | **≤ 30 分钟** |
| Redis | AOF | everysec | ≤ 1s | ≤ 5 分钟（**可重建**，非关键） |
| 算子文件 | 所在 PG 机器挂载卷，随 PG 备份 | 同 PG | ≤ 1 天 | ≤ 1 小时 |
| 主密钥 `FLOWOPS_CRED_MASTER_KEY` | **离线密钥管理系统**（不在服务器上） | 变更时 | — | — |
| 配置（compose/env） | Git 仓库 | 变更时 | — | — |

**⚠️ 主密钥是单点**：密钥丢失 = 所有凭据不可解密。必须离线保存并提供**密钥轮换流程**（双密钥期：新数据用新密钥，旧数据惰性重加密）。

**无 KMS 条件下的兜底约定**（v3 评审补充）：`§4.3` 原只写"离线密钥管理系统"，小团队/内网环境通常没有 KMS。兜底做法——① 密钥写入**加密的物理介质**（U 盘/打印件）放入保险柜；② **双人保管、双人同时到场**才能取出；③ 取用与归还均写纸质/电子登记；④ 与数据库备份**分开存放**（否则一次事故同时丢失数据与密钥）。这四条满足"离线 + 不可单点取得 + 可审计"三个实质要求，KMS 只是这三条的自动化实现。

**恢复演练**：季度一次，按 runbook 走一遍全量恢复，记录实际 RTO（不演练的备份等于没有备份）。

### 4.4 传输安全

| 链路 | 措施 |
|---|---|
| 浏览器 → Nginx | TLS 1.2+，HSTS |
| Nginx → server | 内网，可选 mTLS |
| server ↔ PostgreSQL | TLS（`sslmode=require`） |
| server ↔ Redis | 密码 + 内网隔离 |
| server → 执行节点 | **SSH 密钥优先**（密码仅兼容）；WinRM 用 HTTPS；主机指纹校验（首次确认后写白名单） |

## 5. 运维手册（Runbook）

> **原则**：每份 runbook 必须能被「凌晨三点被叫醒的人」直接照着做。

### 5.1 常见故障处置

**R-01 调度器失去主控（P0）**

```
症状：flowops_scheduler_is_leader 全为 0；任务不再派发
排查：① 查 flowops-scheduler 容器/进程是否存活（应有 2 个副本）
      ② 查 Redis 选主锁：TTL flowops:scheduler:leader     ← 看谁持有、剩余多久
         redis-cli -h $REDIS_HOST TTL flowops:scheduler:leader
         redis-cli -h $REDIS_HOST GET flowops:scheduler:leader
      ③ 查 standby 心跳：EXISTS flowops:scheduler:standby:{instanceId}（TTL 10s）
处置：① 进程存活但未持有锁 → 等看门狗 TTL 过期（≤45s）自动接管
      ② 进程已死 → 拉起进程（compose up -d scheduler / k8s 拉起）
      ③ 两个进程互相抢占（脑裂疑云）→ 停掉其一，检查 Redis 时钟/NTP 一致性
验证：is_leader 恢复为 1，且 dispatched_total 开始增长
```

> **v3 评审修订（A-1）**：原 runbook 第 ② 步写「查 PG：`SELECT * FROM scheduler_lease WHERE name='default'`」——**`scheduler_lease` 表不存在**（选主实际用 Redisson 锁，见 `06 §10.1`），值班的人会卡在这一步。已改为查 Redis。

**R-02 就绪队列积压（P1）**

```
症状：flowops_ready_queue_size > 1000，任务长时间 WAITING_RESOURCE
排查：① 查节点在线率（executor_online_ratio）—— 无在线节点？
      ② 查并发额度是否被占满（项目/队列/工作流三级）
      ③ 查是否有互斥组长期占用（SELECT * FROM task WHERE status='RUNNING' ... mutex_group）
处置：① 节点离线 → 按 R-03 处理
      ② 额度满 → 确认是否真实业务高峰，是则扩容节点/调额度
      ③ 互斥组卡死 → 找到持有任务，确认是否真在运行（可能是孤儿，`06 §17 E-02`）
```

**R-03 大面积节点离线（P1）**

```
症状：executor_online_ratio < 80%
排查：① 单节点 vs 整集群（网络分区？）
      ② 凭据是否过期（查 credential.expire_at）
      ③ 节点侧 agent/SSH 服务是否存活
处置：① 网络问题 → 排查交换机/防火墙
      ② 凭据过期 → 轮换凭据（POST /credentials/{id}/rotate）
      ③ 节点服务问题 → 联系节点负责人
注意：**运行中步骤不因心跳缺失立即判失败**（PRD §20.8-4），给恢复留窗口
```

**R-04 日志写入失败/表膨胀（P2）**

```
症状：task_log 分区未滚动；磁盘使用率 > 85%
排查：① 分区创建任务是否执行（每月 1 号预建下月分区）
      ② 归档任务是否失败（audit_log 搜 ARCHIVE_LOGS）
处置：① 手动创建下月分区
      ② 手动执行归档脚本
      ③ 紧急：DROP 掉最老分区（**先确认已归档**）
```

**R-05 审计写入失败（P0）**

```
症状：flowops_audit_write_failures_total > 0
说明：审计缺失是**合规风险**，等同生产事故
处置：① 检查 audit_log 表是否可写（磁盘满？锁？）
      ② 审计异步队列是否有积压（内存队列，重启会丢）
      ③ 修复后，从应用日志（含完整审计字段的 fallback 输出）回补
```

**R-06 凭据主密钥缺失导致启动失败（P0）**

```
症状：server 启动失败，日志含 "FLOWOPS_CRED_MASTER_KEY is missing"
说明：**这是设计行为，不是 bug**——防止明文降级运行
处置：从离线密钥管理系统取回密钥，注入环境变量后重启
⚠️ 严禁：为快速恢复而注释掉校验逻辑
```

### 5.2 日常巡检清单（每日/每周）

**每日（自动化，异常才通知）**：

| 检查项 | 阈值 | 动作 |
|---|---|---|
| 磁盘使用率（PG 所在盘） | > 80% | 告警 + 人工确认归档 |
| 昨日归档任务 | 未执行 / 失败 | 告警 |
| 过期凭据 | 7 天内到期 | 提醒凭据负责人（自动通知） |
| 离线节点 | > 10% | 告警 |
| 备份成功 | 未成功 | 告警 |

**每周（人工 15 分钟）**：

| 检查项 | 关注点 |
|---|---|
| 失败任务 TOP 原因 | 是否集中某类原因 → 可能是系统性问题 |
| 慢查询日志 | 是否有新增慢查询 → 补索引 |
| 调度决策日志异常 | 大量 `BLOCKED` 集中在某资源 → 容量问题 |
| 审计日志完整性 | 数量趋势是否正常（突降 = 埋点失效） |
| 孤儿任务（`06 §17 E-02`） | RUNNING 但节点已离线 > 1 小时。**正常情况下不应出现**——`06 §8.1` 的恢复窗口是 5 分钟，超时即判失败；该项实际兜的是"恢复窗口判定链路本身异常"（LifecycleScanner 停止、调度器长期无主控） |

### 5.3 容量扩容触发点

| 指标 | 触发值 | 动作 |
|---|---|---|
| ready_queue_size 持续 5min | > 500 | 加节点 / 提额度 |
| 并发运行任务 | > 250（一期目标的 83%） | 评估加节点 |
| PG CPU | 持续 > 70% | 垂直扩容 / 加只读副本 |
| `task_step` 行数 | > 3000 万 | 启用月分区（`05 §7.1` 的 V1.1） |
| 日志日增 | > 80 GB | 缩短热存 / 提前冷存 |
| 单集群节点数 | > 200 | 评估调度器分片（B-03） |

### 5.4 平台健康页（PRD §15.5-5）

**页面**：`平台健康度`（新增页，不在原 18 页中 → **需回写 SPEC-02 页面清单为 19 页**）。

**内容**：调度器状态卡（主/备、**锁剩余 TTL**、上次 tick、standby 数）| 数据库连接池 | Redis 状态 | 节点在线率 | 队列水位（含队头阻塞） | 互斥锁持有 Top | 今日派发量 | 日志摄取量 | 最近平台告警。

**权限**：`schedule:platform:health`（平台管理员、运维人员）。

## 6. SLA 与运营指标

### 6.1 对外 SLA（对齐 PRD §15.1）

| 项 | 承诺 |
|---|---|
| 调度链路可用性 | ≥ 99.9% / 月 |
| 平台页面可用性 | ≥ 99.5% / 月（非关键路径） |
| 故障响应 | P0 ≤ 15 分钟响应，≤ 30 分钟恢复 |
| 数据可靠性 | 任务状态 0 丢失（RPO ≤ 5 分钟） |
| 日志可查性 | 热存 30 天可秒查；冷存 90 天可 30 分钟内恢复 |

### 6.2 可用性计算与月度报表

```
月度可用性 = 1 - (不可用分钟数 / 月度总分钟数)

"不可用" 定义（避免扯皮）：
  ✅ 计入：调度器无主控且 > 60s（P0）、API 错误率 > 5% 持续 5min、DB 不可写
  ❌ 不计入：计划内维护（提前 3 天通知）、单节点故障（不影响整体）、
             执行节点侧故障（非平台责任）
```

**报表项**：可用性 %、P0/P1 事件数、MTTR、MTBF、告警准确率（有效告警 / 总告警）。

### 6.3 平台自身告警规则（一期内置，不可删）

| 规则 | 条件 | 级别 | 通道 |
|---|---|---|---|
| 调度器无主控 | `is_leader` 全 0 持续 60s | P0 | 企业微信 + 邮件 + 电话（如有） |
| 派发停滞 | `dispatched_total` 5min 无增长且队列非空 | P0 | 同上 |
| 审计写入失败 | `audit_write_failures > 0` | P0 | 企业微信 + 邮件 |
| 主密钥缺失 | 启动失败（进程不存在） | P0 | 邮件 |
| 队列积压 | `ready_queue_size > 1000` 持续 5min | P1 | 企业微信 |
| 节点离线率 | `online_ratio < 80%` 持续 10min | P1 | 企业微信 |
| 备份失败 | 备份任务返回非 0 | P1 | 邮件 |
| 磁盘水位 | 使用率 > 80% | P1 | 企业微信 |
| 日志日增异常 | > 100 GB/天 | P2 | 企业微信（日报） |
| 过期凭据 | 7 天内到期 | P2 | 邮件（给负责人） |

> **与业务告警的区别**：这些是**平台自身**的告警（PRD §15.5-5 要求独立于业务监控），走独立通道，**不受业务告警的抑制窗口影响**。
