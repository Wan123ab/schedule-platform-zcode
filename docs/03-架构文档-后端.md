## 1. 工程结构

### 1.1 仓库形态

**单仓多模块（Maven Multi-Module）**，便于共享 `common` 与调度内核的独立打包：

```
flowops/
├── pom.xml                       # 父 POM（依赖版本统一管理）
├── flowops-common/               # 通用：响应包、异常、枚举基类、工具、常量
├── flowops-server/               # 应用层：REST + WebSocket + 六域业务（可多副本）
├── flowops-scheduler/            # 调度内核（单活，可独立启动）
├── flowops-executor-client/      # 执行节点通信客户端（SSH/WinRM/Agent 协议）
└── docs/  deploy/                # 设计与部署（deploy 含 Dockerfile / compose）
```

> **为什么调度内核单独成模块**：① 可独立启动进程（见 01 §4.1）；② server 与 scheduler 共享实体与 Mapper，避免代码复制；③ 未来若拆分服务，模块边界即服务边界。

### 1.2 模块依赖关系

```
        flowops-common  ◄──────┬──────────────┬──────────────┐
              ▲                │              │              │
              │                │              │              │
      flowops-executor-client ─┘              │              │
              ▲                               │              │
              │                               │              │
      flowops-scheduler ──────────────► flowops-server ◄─────┘
                                              │
                                              ▼
                                    PostgreSQL / Redis
```

**铁律**：
- `common` 不依赖任何业务模块；
- `scheduler` **不依赖** `server`（反之亦然），两者的协作通过 **DB 状态 + Redis 队列**（见 01 §4.1）；
- 共享实体与 Mapper 放 `common` 或独立的 `flowops-domain`（若实体增多建议拆出）。

## 2. 分层与包结构

### 2.1 分层职责（严格单向依赖）

```
controller  ──►  service  ──►  manager/repository  ──►  mapper  ──►  DB
   │               │                    │
   │               │                    └─ 跨表组合、缓存编排、事务边界内的复杂逻辑
   │               └─ 业务规则、事务边界、权限校验、领域事件发布
   └─ 参数校验、DTO 转换、统一响应包装
```

| 层 | 职责 | 禁止 |
|---|---|---|
| controller | 入参校验（`@Valid`）、调 service、返回统一响应 | ❌ 直连 mapper；❌ 写业务规则 |
| service | 业务规则、事务、权限、事件发布 | ❌ 拼 SQL；❌ 感知 HTTP |
| manager | 跨表/跨域组合、缓存、外部调用编排 | ❌ 定义事务边界（由 service 定） |
| mapper | 纯数据访问（MyBatis-Plus + XML） | ❌ 业务判断 |

## 3. 跨域机制

### 3.1 认证与权限（对齐 PRD §11.2 的 **6 角色 + 数据范围**）

> ⚠️ **重要**：`CONTRACT-API §0.3` 只列了 4 角色（ADMIN/OPS/DEV/VIEWER），而 `PRD §11.2` 定义了 **6 个角色**（外加租户/项目维度的数据范围）。**以 PRD 为准**，需回写契约文档（见 `00-索引` F-02）。

| 角色 | code | 说明 |
|---|---|---|
| 平台管理员 | `PLATFORM_ADMIN` | 全平台 |
| 运维人员 | `OPS` | 资产 + 任务运维，被授权集群范围 |
| 项目管理员 | `PROJECT_ADMIN` | 本项目内全部 |
| 算子维护者 | `OPERATOR_MAINTAINER` | 本人维护的算子 |
| 业务人员 | `BUSINESS` | 本项目内提交/查看本人任务 |
| 只读/审计 | `AUDITOR` | 全平台只读（审计视角） |

> PRD §11.2 矩阵中「租户」「项目空间」两类行还带有租户/项目维度的限定（如「△ 仅本项目」）。**实现采用「角色 + 数据范围（DataScope）」双要素**，不用单一角色枚举叠加角色——即一个人可有多个角色，但同一请求的数据范围由 scope 收敛。

**权限模型（RBAC + 数据范围）**：

```
权限点（Permission）：  资源:动作          如 schedule:task:stop
角色（Role）：          权限点集合          如 OPS 拥有 schedule:task:*
数据范围（DataScope）：  ALL / AUTHORIZED_CLUSTER(ids) / PROJECT(ids) / SELF_CREATED / SELF / NONE
```

> **v3 评审修订**：DataScope 枚举曾有三套命名（本文 `CLUSTER`/`SELF`、`07 §5.3` `AUTHORIZED_CLUSTER`/`SELF_CREATED`、`04 §3.2` `CLUSTER`/`SELF`）。**统一以 `07 §5.3`（D-19 本体）为准**：`AUTHORIZED_CLUSTER`（被授权集群——强调"运维只对被授权的集群可见"，比 `CLUSTER` 语义准确）、`SELF_CREATED`（本人创建的——与 `SELF`（仅本人）区分开，前者含本人创建但已被他人操作的资源）。

**校验实现**（注解 + AOP）：

```java
@RequiresPermission(value = "schedule:task:stop", scope = DataScope.PROJECT)
public TaskResp stopTask(String taskId, StopTaskReq req) { ... }
```

`PermissionService` 三重判定：① 用户是否有该权限点；② 数据范围是否覆盖目标资源；③ 特殊规则（如「凭据查看明文」对**所有角色**一律禁止 → 无对应权限点，服务端仅返回指纹）。

**关键特权规则**（PRD §11.2 明确）：

| 规则 | 实现 |
|---|---|
| 凭据明文查看：**所有角色均禁止** | 无权限点；`secret` 永不出库，仅返回 `secretFingerprint` |
| 运维跨项目查看日志原文 | 需显式授权 + **强制留痕**（写审计 `action=VIEW_LOG_RAW`） |
| 任务插队 | 仅 平台管理员 / 运维人员 |
| 工作流删除 | 仅平台管理员（**项目管理员都不可删**） |

### 3.2 多租户隔离（PRD §11.1）

**隔离层次**：`租户 → 项目 → 资源`。所有查询强制带项目过滤。

**实现**：MyBatis-Plus 的**租户插件 / 自定义数据权限拦截器**，自动为 SQL 注入 `project_id IN (...)`：

```java
// DataScopeInterceptor：根据 UserContext 的可见项目列表重写 SQL
// ⚠️ 仅对标注 @DataScoped 的 mapper 方法生效，避免误伤平台级查询（如审计全局视图）
```

**运维视图 vs 业务视图**（PRD §11.3）：
- 业务视图：强制限定在当前项目；
- 运维视图：按 `DataScope.AUTHORIZED_CLUSTER` 展开，可跨项目但**只读 + 留痕**；
- 由前端顶部「视图切换」驱动，后端凭 token 中的 scope 判定，**不接受前端传入的项目 ID 作为授权依据**（防越权）。

### 3.3 审计（注解式 + traceId 贯穿）

**设计目标**：CONTRACT §10 要求字段级 diff、`beforeSummary/afterSummary`、traceId 串联。

**实现**：

```java
@Audited(
    targetType = TargetType.WORKFLOW,
    action = "PUBLISH_WORKFLOW",
    targetIdSpel = "#workflowId",
    captureDiff = true              // 开启字段级 diff
)
public WorkflowResp publish(String workflowId) { ... }
```

`AuditAspect` 环绕执行：
1. 从 `TraceContext` 取/生成 `traceId`（**与日志、链路追踪同一标识**）；
2. 执行前查询目标对象快照 → `beforeSummary`；
3. 执行后查询 → `afterSummary` + 逐字段 `diff[]`；
4. 异步落库（避免拖慢主链路）；
5. 失败也记录（`result=FAIL`）。

**审计范围**（PRD §10.13）：登录/登出、资产增删改、凭据轮换、算子发布、工作流发布/停用/删除、触发器配置、任务提交/停止/重跑/插队、回填操作、告警规则变更、权限变更、跨项目日志查看。

**不变式**：审计表**只增不改不删**（无 UPDATE/DELETE 权限，DB 层 REVOKE）。

### 3.4 事务策略

| 场景 | 策略 |
|---|---|
| 单域写操作 | `@Transactional(rollbackFor = Exception.class)` |
| **任务状态流转** | 必须显式隔离级别 + **乐观锁**（`version` 字段）防止调度器与人工操作并发覆盖 |
| 跨域写（如「发布工作流」） | 单库本地事务；**不引入分布式事务**（同库） |
| 调度器写状态 | 短事务 + `UPDATE ... WHERE status = :expected`（CAS 风格），避免长事务锁表 |
| 审计/日志异步落库 | 独立事务（`REQUIRES_NEW`），不随主事务回滚 |

**关键约束**：调度器的状态更新**一律用条件更新（CAS）**，例如：

```sql
UPDATE task_step SET status = 'RUNNING', version = version + 1
 WHERE step_instance_id = ? AND status = 'WAITING_RESOURCE' AND version = ?
```

受影响行数为 0 → 说明状态已被他方改变，**放弃本次操作并重新读取**（这是避免重复调度的核心手段）。

### 3.5 统一响应与错误码

复用 `com.das.fly.common.api` 约定（CONTRACT §0.2）：

```json
{ "code": 0, "message": "ok", "data": {}, "trace_id": "8f2c-41ab" }
```

> 注意：因采用全局 snake_case（D-05），`traceId` 在线协议中为 `trace_id`，**CONTRACT-API 文档需同步修正**。

`ErrorCode` 枚举承载 CONTRACT §12 全部错误码，`BizException` 抛出后由 `GlobalExceptionHandler` 统一转换为响应。

## 4. 核心域内部设计

### 4.1 asset 域：凭据加密与引用计数（最敏感）

**加密存储**：

```
明文 secret ──(AES-256-GCM + 主密钥)──► 密文入库（credential.secret_encrypted）
主密钥来源：环境变量 / KMS（不进代码库、不进 DB）
指纹：SHA-256(secret) 取后 4 位可见 → secret_fingerprint
```

**规则**：
- `secret` 字段**写-only**：接口永不返回明文，只返回指纹后 4 位（CONTRACT §4）；
- 解密仅在**执行下发时**发生，且只在内存中，用完即弃；
- 日志/变量快照中自动脱敏（PRD §13.3 的 `password=` `token=` 等规则）。

**引用计数反查**（PRD §7.2 硬约束：`refCount > 0` 禁止删除）：

```sql
-- executor_node.credential_ref_id 引用
SELECT COUNT(*) FROM executor_node WHERE credential_ref_id = ?
-- 未来若有其他引用方，纳入 UNION
```

删除前置校验 + DB 外键（`ON DELETE RESTRICT`）**双保险**。

### 4.2 workflow 域：版本快照与不可变

**版本生命周期**：

```
新建工作流 → 创建 DRAFT 版本（可编辑）
     │
     ├─ 编辑（PUT /workflow-versions/{id}）──► 仅 DRAFT 可写
     │                                          发布后返回 40900
     │
     └─ 发布（POST /publish）──► 冻结：status=PUBLISHED，不可改不可删
                                 设为 currentVersion，设 isDefaultVersion
```

**草稿机制**：`hasDraftChanges` 标记——从已发布版本「基于此版本新开草稿」时，**复制一份新版本记录**，原版本保持冻结。

**为什么不可变**：任务强绑定 `workflowVersion`（PRD §7.2），若版本可改，历史任务的「当时执行的是什么」就无从考证，审计与排障失效。

### 4.3 workflow 域：DAG 校验（8 条规则，PRD §10.8）

`DagValidator` 在**发布前**逐条校验，返回 `errors[]{rule, stepId, message}`：

| # | 规则 | 实现 |
|---|---|---|
| 1 | 至少一个入度 0 步骤，且所有执行步骤可达（备注除外） | 邻接表 + 拓扑遍历（BFS），收集不可达步骤 |
| 2 | 所有执行步骤必须选算子+版本 | 遍历 steps，`stepType=TASK` 时校验 `operatorId/operatorVersion` |
| 3 | 必填参数必须填写 | 按算子版本的 `paramTemplate[].required` 比对步骤 `params` |
| 4 | 变量引用必须有效（存在且为可达上游） | 反向可达集计算 + 引用解析（§4.4） |
| 5 | 连线不能形成环 | Kahn 算法拓扑排序，剩余节点即环成员 |
| 6 | 资源要求不超过目标集群/队列上限 | 聚合步骤资源 vs `cluster`/`queue` 上限 |
| 7 | 已停用算子/版本不能发布 | join operator_version 校验 `publishStatus` |
| 8 | 必须声明并发控制配置 | 校验 `concurrencyPolicy` + `maxParallelRuns` 非空 |

> 规则 1 特别说明：V0.2 明确**不引入特殊"开始节点"类型**，改用入度 + 可达性判断（PRD §10.8 脚注）。

### 4.4 task 域：变量解析链（PRD §10.0.1，6 层覆盖）

**这是让 DAG 具备真实数据流转能力的核心**，也是最容易出错的部分。

**解析优先级**（低 → 高，后者覆盖前者）：

```
1. 平台变量       ${taskId} ${workflowVersion} ${machineIp} ...
2. 项目参数       ${project.dataRoot}
3. 工作流参数     ${workflow.bizDate}
4. 触发时参数     （手动/定时填写）
5. 上游步骤输出   ${step.数据清洗.output.file_path}
6. 步骤参数       （最高）
```

**`VariableResolveManager` 设计**：

```java
// 有序 Map 逐层覆盖：底层先放，高层后放 put
Map<String,Object> ctx = new LinkedHashMap<>();
ctx.putAll(platformVars(task));         // 1
ctx.putAll(projectParams(project));     // 2
ctx.putAll(workflowVersion.getWorkflowParams()); // 3
ctx.putAll(triggerRunParams);           // 4
ctx.putAll(upstreamStepOutputs(task));  // 5（从已完成上游 taskStep.outputVars 取）
ctx.putAll(step.getParams());           // 6

String cmd = TemplateEngine.render(version.getStartCommand(), ctx);
```

**变量引用语法（D-20，已定案）**：`${step.{步骤名}.output.{变量名}}`

> **v3 评审修订**：此处原写「需业务确认统一」。该分歧已由 **D-20 定案**（见 `07 §9.1`），结论是采用 SPEC / `07` 的 `${step.{步骤名}.output.{变量名}}`，**理由**：① `step` 与 `output` 是字面量关键字，解析器可精确锚定，而 PRD 版 `${步骤标识.输出标识}` 的两个占位符之间用 `.` 分隔，与「变量名本身可含点」冲突；② 步骤名可含中文，用户在画布上看到的就是步骤名；③ 预留扩展（`${trigger.x}` / `${project.x}` / `${platform.x}`）。
>
> **不兼容 PRD 旧写法**（双语法会让解析器与校验器复杂度翻倍）。**PRD §10.0.3 已于 2026-09-24 回写为 `${step.{步骤名}.output.{变量名}}`（R-2），两端一致**。本节的示例 `${steps.数据清洗.outputFilePath}` 亦按 D-20 同步为 `${step.数据清洗.output.file_path}`。

**解析时机与快照**：
- 解析发生在**步骤即将下发执行前**（此时上游输出已就绪）；
- 解析结果写入 `task.variableSnapshot`（Map），供任务详情展示「实际解析后的参数」（PRD §10.0.4）；
- **敏感参数在快照中脱敏**（`MaskUtil`）。

**必填输出未产出** → 该步骤判失败（PRD §10.0.2）。

### 4.5 task 域：日志存储与实时推送

**双通道**：

```
Agent 采集 stdout/stderr
   │
   ├──► ① 落库（热存）  task_log 表（按 step_instance_id + seq 分区）
   │                    · 单步骤上限 100MB，超出截断并追加提示（PRD §13.1）
   │                    · 「大日志模式」：仅保留尾部 N 行（算子可配）
   │
   └──► ② Redis Pub/Sub ──► WebSocket 推送（前端按 offset 续传）
```

**WebSocket 协议**：

```
连接：WS /ws/tasks/{taskId}/steps/{stepInstanceId}/logs?offset=1234&token=...
服务端：按 seq 顺序推送；断线重连时按 offset 补发未收到的部分（不重复推送，PRD §13.2）
```

**脱敏在服务端执行**（PRD §13.3 硬要求：脱敏不可绕过，前端不接触原文）。

**分层归档**：热存 30 天（在线检索）→ 冷存 90 天（仅下载）→ 到期删除。一期可用**同一张表 + `storage_tier` 字段**实现，量大再拆分表/引入对象存储。

## 5. 调度内核（模块概览）

> 详细设计见 [06-调度引擎详细设计](./06-调度引擎详细设计.md)，此处仅给架构定位。

### 5.1 独立进程与选主

```
flowops-scheduler 启动
   │
   ├─ 尝试获取 Redisson 分布式锁 "flowops:scheduler:leader"
   │     ├─ 成功 → LeaderElector.isLeader = true → 启动全部调度线程
   │     └─ 失败 → 成为 Standby，仅维持心跳，定期尝试抢锁
   │
   ├─ RecoveryService.recover()   # 关键！从 PG 重建 Redis 派生态
   │     ├─ 扫描 status ∈ (PENDING, SCHEDULING, RUNNING) 的任务
   │     ├─ 重建就绪队列 ZSet
   │     └─ 重建互斥锁持有点（对有 mutexGroup 的运行中步骤）
   │
   └─ 调度主循环（单线程 tick，默认 1s）
         ├─ CronTriggerScanner   扫描到期的触发器
         ├─ DagAdvancer          推进入度 0 的步骤
         ├─ ReadyQueueManager    出队 + 优先级重估
         ├─ NodeMatcher          节点选择
         └─ LifecycleScanners    心跳/超时/重试
```

### 5.2 与 server 的协作边界

| 关注点 | server | scheduler |
|---|---|---|
| 对外 REST API | ✅ 全部 | ❌ 无 |
| 建任务实例 | ✅（手动触发/回填） | ✅（定时触发） |
| 并发检查 | ✅ 调用 `ConcurrencyGuard` | ✅ 调用同一个 |
| DAG 推进 | ❌ | ✅ |
| 节点匹配下发 | ❌ | ✅ |
| 任务停止/重跑 | ✅ 改状态，**由 scheduler 感知** | ✅ 检测状态变化 |
| 日志接收 | ✅（WebSocket 出口） | ✅（Agent 上报入口） |

> **协作契约**：scheduler 不认 HTTP 请求，只认 **DB 状态变化**。server 的「停止任务」= 把状态改成 `STOPPING`，scheduler 下一 tick 扫描到并执行终止。

## 6. 线程模型与并发

### 6.1 server 侧

| 场景 | 模型 |
|---|---|
| REST 请求 | **虚拟线程**（Java 21 `spring.threads.virtual.enabled=true`） |
| 审计异步落库 | 独立线程池（有界队列 + 拒绝策略记录日志） |
| WebSocket 推送 | Netty 事件循环（Spring WebSocket） |
| 定时聚合任务（看板缓存刷新） | `@Scheduled` + 分布式锁（避免多副本重复） |

### 6.2 scheduler 侧

| 线程 | 数量 | 职责 |
|---|---|---|
| 调度主循环 | **1**（单线程） | 保证调度决策的**顺序性**，避免并发决策冲突 |
| 心跳检查 | 1 | 扫描节点心跳超时 |
| 超时扫描 | 1 | 扫描步骤/任务超时 |
| 执行下发 | N（可配） | IO 密集（SSH/HTTP），**可并发** |
| Agent 上报接收 | N | 处理退出码/资源/输出变量回传 |

> **为什么主循环单线程**：调度决策涉及队列/资源/并发的一致视图，多线程会产生竞态（如两个线程同时把同一节点分配给不同步骤）。单线程 tick + IO 下发并发，是简单且安全的组合。
