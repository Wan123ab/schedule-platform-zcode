## 1. 设计目标与约束

### 1.1 引擎必须满足的硬要求（来自 PRD）

| # | 要求 | 出处 |
|---|---|---|
| G1 | 优先级数值越大越优先；同优先级 FIFO；**入队排序 + 出队重新评估** | §12.2 |
| G2 | **不支持抢占式调度**，仅靠队列隔离 + 手动插队 | §12.2 |
| G3 | 节点选择：运行任务数最少 → 剩余 CPU 最多 → 最近分配时间最早；**明确排除随机** | §12.2 |
| G4 | 心跳 15s / **连续 3 次（45s）判离线**；离线不直接判失败，保留 **5 分钟恢复窗口** | §12.2 |
| G5 | 单次心跳缺失 → 界面标「心跳异常」但**状态不变、不告警** | §12.2 |
| G6 | 手动/定时/API/回填**必须同一套并发检查**，不允许绕过 | §12.3 |
| G7 | 互斥锁：同名锁全平台串行；锁在步骤结束后自动释放；**持锁超时保护** | §12.3 |
| G8 | 无可用节点 → `WAITING_RESOURCE` + **记录阻塞原因**（供诊断） | §12.2 |
| G9 | 超等待超时 → 步骤标记调度失败 | §12.2-6 |
| G10 | 集群亲和：任务内所有步骤优先同集群；不可满足允许跨集群并**在诊断中说明** | §12.2 |
| G11 | 失败重试：按 `retryCount` / `retryIntervalSeconds` / `failureStrategy` | §10.8 |
| G12 | 错过触发补跑：默认开启，**单个触发器最多补 3 次** | §10.9-8 |

### 1.2 引擎**不做**的事（边界）

- ❌ 暴露 REST API（只有 server 有，`03 §5.2`）；
- ❌ 解析 Cron 表达式本身（用 `cron-utils` 库，见 02 §1.9）；
- ❌ 执行命令（下发给执行节点/Agent，`flowops-executor-client` 负责）；
- ❌ 保存日志原文（只写 `task_log`，推送走 Redis Pub/Sub）；
- ❌ 权限判定（不做 HTTP，无用户上下文）。

## 2. 状态机

### 2.1 任务状态机（9 态）

```
                       ┌──────────┐
   触发（手动/定时/回填）│ PENDING  │
   ──────────────────►└────┬─────┘
                          │ 并发检查通过 + 入队
                          ▼
                    ┌─────────────┐
                    │ SCHEDULING  │◄─────┐
                    └──────┬──────┘      │ 出队但节点不足 → 回退
                           │ 首个步骤下发  │
                           ▼              │
                    ┌─────────────┐       │
              ┌────►│   RUNNING   │───────┘
              │     └──────┬──────┘
              │            │
              │     ┌──────┴───────┬──────────┬──────────┐
              │     │              │          │          │
              │     ▼              ▼          ▼          ▼
              │ ┌────────┐  ┌────────┐ ┌────────┐ ┌────────┐
              │ │SUCCESS │  │ FAILED │ │STOPPED │ │TIMEOUT │
              │ └────────┘  └────────┘ └────────┘ └───┬────┘
              │                  │                   │
              │                  ▼                   ▼
              │            ┌──────────┐        ┌──────────┐
              └────────────┤ PARTIAL  │◄───────┤ PARTIAL  │
                （重跑失败  └──────────┘        └──────────┘
                  步骤后）
```

**状态转移表**（**唯一权威**，实现时逐行对照）：

| 当前 | 事件 | 目标 | 触发方 | 附加动作 |
|---|---|---|---|---|
| `PENDING` | 并发检查通过 | `SCHEDULING` | 调度器 | 入队 ZSet；开始 DAG 推进 |
| `PENDING` | 并发检查不通过（FORBID） | `FAILED` | 调度器 | 写 `fail_reason`；**触发告警「工作流并发触达上限」**（提示级） |
| `PENDING` | 并发检查不通过（QUEUE） | `PENDING` | 调度器 | 保持等待；记录队列位置 |
| `SCHEDULING` | 首步骤成功下发 | `RUNNING` | 调度器 | 设 `start_time` |
| `SCHEDULING` | 无可用节点（超等待超时） | `FAILED` | 调度器 | `fail_reason = 队列等待超时` |
| `RUNNING` | 所有步骤成功 | `SUCCESS` | 调度器 | 设 `end_time`、`duration`；写 `last_run_status` |
| `RUNNING` | 有步骤失败且策略=TERMINATE | `FAILED` | 调度器 | 停止未开始步骤（`STOPPED`）；触发告警 |
| `RUNNING` | 有步骤失败且策略=RETRY 且重试耗尽 | `FAILED` | 调度器 | 同上 |
| `RUNNING` | 有步骤失败且**部分**分支成功 | `PARTIAL` | 调度器 | 用于「允许部分成功」的 DAG（分支场景） |
| `RUNNING` | 用户停止 | `STOPPED` | server 改状态 → 调度器执行 | 设 `stopped_by`/`stop_reason`；终止运行中进程 |
| `RUNNING` | 任务超时 | `TIMEOUT` | 调度器 | 终止所有运行中步骤 |
| `RUNNING` | 任务级重跑（rerun-failed） | `RUNNING` | server 改状态 → 调度器接管 | 复用上游成功结果（见 §9.3） |
| `FAILED`/`STOPPED`/`TIMEOUT`/`PARTIAL` | 整任务重跑 | 新建任务 | server | **原任务不变**（新任务实例） |

> **铁律**：**终态不可回退**。`SUCCESS` 一旦写入，任何操作都不能改回 `RUNNING`——只能新建任务。这是审计可信度的根基。

### 2.2 步骤实例状态机（11 态）

```
┌───────────────┐
│ NOT_STARTED   │
└───────┬───────┘
        │ DAG 推进：入度未满足
        ▼
┌──────────────────┐
│WAITING_DEPENDENCY│
└───────┬──────────┘
        │ 上游全部成功（或按策略跳过）
        ▼
┌──────────────────┐   资源/锁不足    ┌───────────────────┐
│WAITING_RESOURCE  │◄─────────────────│ （节点匹配失败）    │
└───────┬──────────┘                  └───────────────────┘
        │ 资源 + 互斥锁均获得
        ▼
┌───────────────┐
│  SCHEDULING   │  ← 条件更新为 RUNNING（防重复下发）
└───────┬───────┘
        ▼
┌───────────────┐
│    RUNNING    │
└───────┬───────┘
        │
   ┌────┴─────┬──────────┬──────────┬───────────┐
   ▼          ▼          ▼          ▼           ▼
┌────────┐┌────────┐┌────────┐┌────────┐┌────────────┐
│SUCCESS ││ FAILED ││TIMEOUT ││STOPPED ││  RETRYING   │
└────────┘└────┬───┘└────────┘└────────┘└──────┬─────┘
               │                                │ 间隔到达
               │ 重试耗尽                       └──────┐
               ▼                                       │
        ┌────────────┐        （回到 WAITING_RESOURCE）│
        │  FAILED    │◄───────────────────────────────┘
        └────────────┘

        ┌────────────┐
        │  SKIPPED   │（V1.1：跳过失败步骤的下游）
        └────────────┘
```

| 当前 | 事件 | 目标 | 判定依据 |
|---|---|---|---|
| `NOT_STARTED` | DAG 推进 | `WAITING_DEPENDENCY` | 该步骤入度 > 0 |
| `NOT_STARTED` | DAG 推进（入度 0） | `WAITING_RESOURCE` | 直接可调度 |
| `WAITING_DEPENDENCY` | 全部上游 `SUCCESS` | `WAITING_RESOURCE` | 上游状态集合 |
| `WAITING_DEPENDENCY` | 上游有 `FAILED` 且策略=TERMINATE | `STOPPED` | 不再执行 |
| `WAITING_RESOURCE` | 节点 + 锁均获得 | `SCHEDULING` | 见 §5 / §6 |
| `WAITING_RESOURCE` | 等待超时 | `FAILED` | `queue.wait_timeout_seconds` |
| `SCHEDULING` | 命令下发成功 | `RUNNING` | CAS 更新（§4.3） |
| `SCHEDULING` | 下发失败（SSH 连不上等） | `WAITING_RESOURCE` | 释放节点占用，回退重试 |
| `RUNNING` | 退出码 ∈ `success_codes` | `SUCCESS` | 算子版本配置 |
| `RUNNING` | 退出码 ∉ `success_codes` 且 `retryCount < max` | `RETRYING` | 写 `task_step_retry` |
| `RUNNING` | 退出码 ∉ `success_codes` 且重试耗尽 | `FAILED` | 触发告警 |
| `RUNNING` | 超过 `timeout_seconds` | `TIMEOUT` | 超时扫描（§8.3） |
| `RUNNING` | 节点失联 > 5 分钟恢复窗口 | `FAILED` | `fail_reason = 执行节点失联` |
| `RUNNING` | 用户的停止指令 | `STOPPED` | 任务级停止 |
| `RETRYING` | 间隔到达 | `WAITING_RESOURCE` | 重新参与调度 |

### 2.3 状态机的实现方式

**不给每个状态写一个类**（过度设计）。用**状态转移表 + 守卫条件**的声明式实现：

```java
// 声明式转移表：from -> (to, guard, sideEffect)
public enum StepTransition {
    DEP_READY(NOT_STARTED, WAITING_RESOURCE, ctx -> ctx.inDegree() == 0),
    DEP_WAIT(NOT_STARTED, WAITING_DEPENDENCY, ctx -> ctx.inDegree() > 0),
    UPSTREAM_DONE(WAITING_DEPENDENCY, WAITING_RESOURCE, ctx -> ctx.allUpstreamSuccess()),
    UPSTREAM_FAIL(WAITING_DEPENDENCY, STOPPED, ctx -> ctx.anyUpstreamFailed() && ctx.policy() == TERMINATE),
    RESOURCE_OK(WAITING_RESOURCE, SCHEDULING, ctx -> ctx.nodeAvailable() && ctx.mutexAcquired()),
    WAIT_TIMEOUT(WAITING_RESOURCE, FAILED, ctx -> ctx.waitedSeconds() > ctx.waitTimeout()),
    DISPATCH_OK(SCHEDULING, RUNNING, ctx -> true),
    DISPATCH_FAIL(SCHEDULING, WAITING_RESOURCE, ctx -> true),
    EXIT_OK(RUNNING, SUCCESS, ctx -> ctx.successCodes().contains(ctx.exitCode())),
    EXIT_RETRY(RUNNING, RETRYING, ctx -> ctx.retryLeft() > 0),
    EXIT_FAIL(RUNNING, FAILED, ctx -> ctx.retryLeft() == 0),
    STEP_TIMEOUT(RUNNING, TIMEOUT, ctx -> ctx.elapsed() > ctx.timeoutSeconds()),
    NODE_LOST(RUNNING, FAILED, ctx -> ctx.recoveryWindowExpired()),
    USER_STOP(RUNNING, STOPPED, ctx -> ctx.stopRequested()),
    RETRY_READY(RETRYING, WAITING_RESOURCE, ctx -> ctx.retryIntervalElapsed());
    // ...
}
```

**收益**：① 状态机可被单测穷举（每个转移一条用例）；② PRD 改规则时改表不改代码结构；③ 非法转移自然被拒绝（表里没有的转移不可能发生）。

## 3. 调度主循环

### 3.1 单线程 tick（为什么）

`03 §6.2` 已定：**主循环单线程**。理由是调度决策涉及队列 / 资源 / 并发的一致视图。举一个具体竞态：

```
❌ 双线程：
   T1 读到 node-A 剩余 CPU = 8，决定把 step-1 分给它
   T2 同时读到 node-A 剩余 CPU = 8，决定把 step-2 分给 node-A
   → 两步骤都要求 8 核 → 超分 → 节点被打爆

✅ 单线程：
   T1 处理 step-1 → 分配 node-A，内存中更新 node-A 余量 → 同一 tick 内 T1 处理 step-2 时看到余量 0
```

**性能账**：单线程每 tick 的工作量 = 扫描活跃任务数 × 步骤数。以 500 个活跃任务 × 平均 10 步 = 5000 次判定/tick，纯内存+缓存判定约 5~20ms，1s tick 有 50 倍余量。**只有 IO（下发命令）才并发**。

### 3.2 tick 的九个阶段（与 `01` §5.1 主链路的对应）

```
每 tick（默认 1s）：

  ① TriggerScanner      扫描到期触发器 → 创建任务（走 TriggerDispatcher 统一入口）
  ② QuotaScanner        项目/工作流并发检查 → PENDING 任务推进到 SCHEDULING
  ③ DagAdvancer         推进入度满足的步骤 → WAITING_RESOURCE
  ④ ReadyQueueManager   维护 ZSet：入队 / 优先级重估 / 超时清理
  ⑤ NodeMatcher         为 WAITING_RESOURCE 步骤选节点（§5）
  ⑥ MutexAcquirer       尝试获取互斥锁（§6.3）
  ⑦ Dispatcher          并发下发命令（独立线程池，本 tick 只提交任务）
  ⑧ LifecycleScanner    心跳 / 超时 / 恢复窗口（§8）
  ⑨ RetryHandler        到期的 RETRYING → WAITING_RESOURCE
```

**阶段顺序不可调换**：③ 必须在 ④ 之前（先推进再入队），④ 必须在 ⑤ 之前（先定序再匹配）。⑤/⑥ 顺序可互换但**必须都通过才转移**到 `SCHEDULING`。

### 3.3 tick 的幂等性要求

**每个阶段必须幂等**——同一 tick 因异常重跑，不产生副作用：

```java
// ❌ 非幂等：直接 INCR
redis.incr("queue:" + queueId + ":waiting");
// ✅ 幂等：SET 到计算值
redis.set("queue:" + queueId + ":waiting", computeWaitingCount(queueId));
```

**下发的幂等**（最关键）：用 `dispatch_token` 做 CAS（见 §4.3）。

## 4. 就绪队列（Redis ZSet）

### 4.1 数据结构

```
Key:   flowops:queue:ready:{queueId}
Type:  ZSET
Member: taskStepId（字符串，如 "6023"）
Score: 复合分数（见 §4.2）
```

### 4.2 复合 Score 设计（G1 的核心）

需求：**优先级降序 + 同优先级 FIFO**。ZSet 是**升序**取（`ZRANGE`），所以要构造一个"越小越先出队"的分数：

```java
// 分数构造：优先级越高 → 分数越小；同优先级 → 入队越早 → 分数越小
// ⚠️ 用整数序号右对齐，避免浮点精度问题
long score = (long) (MAX_PRIORITY - priority) * SEQ_WEIGHT + enqueueSeq;

// MAX_PRIORITY = 100（优先级范围 0~100）
// SEQ_WEIGHT    = 1L << 40（≈1.1e12，保证序号不溢出到优先级区间）
// enqueueSeq    = Redis INCR 的全局递增序号（非时间戳！）
```

> **⚠️ 为什么序号用 `INCR` 而不用时间戳？**
> 时间戳（毫秒）在同一毫秒内入队的多个步骤会**并列**，ZSet 按 member 字典序排序 → 顺序不确定。`INCR` 返回严格单调递增的整数，FIFO 严格保证。这是本设计最容易被忽略但影响最大的细节。
>
> **⚠️ `SEQ_WEIGHT` 为什么是 `1L << 40` 而不是 10 亿**（v3 评审修订）：
> 序号溢出到相邻优先级区间会导致**低优步骤排到高优步骤前面**——这是静默的正确性事故，没有任何报错。按 100 次/秒的入队速率估算：
>
> | `SEQ_WEIGHT` | 溢出到下一优先级所需时间 |
> |---|---|
> | `1_000_000_000`（原值） | **约 116 天** ❌ 一年不到就出事 |
> | `1L << 40`（≈1.1e12） | 约 348 年 ✅ |
>
> 且 `100 × 2^40 ≈ 1.1e14` 远小于 `Long.MAX_VALUE`，优先级区间不溢出。

### 4.3 出队与 CAS（防重复下发）

```
取出（⚠️ 每次出队是「一批」，不是「一个」）：
  freeSlots = queue.max_concurrent_tasks - queueCurrentRunning(queueId)   // 队列剩余并发槽位
  if (freeSlots <= 0) → 本队列本 tick 不出队（见 §4.4，队列隔离）
  batch = min(freeSlots, TICK_DISPATCH_BATCH)     // 默认 64，避免单 tick 下发风暴
  candidates = ZRANGE flowops:queue:ready:{queueId} 0 (batch-1) WITHSCORES

  逐个走 CAS 占位（下略，见 ①）：
  ...
```

**每 tick 出队量的定义（v3 评审补充，原文档缺失）**：

| 项 | 取值 | 说明 |
|---|---|---|
| `freeSlots` | `queue.max_concurrent_tasks − 该队列当前 RUNNING/SCHEDULING 步骤数` | 队列并发额度在**出队时**检查（`§6.1`） |
| `TICK_DISPATCH_BATCH` | **64**（可配） | 单 tick 单队列最多尝试出队数；防止一次 tick 提交上千条下发把下发池打满 |
| `SCAN_LIMIT` | **256**（可配） | 队头阻塞诊断时向后扫描的最大条数（见下） |

> 原文档此处写的是 `ZRANGE 0 0`（每次只取 1 个），与 `§3.2` ⑤「NodeMatcher 为 WAITING_RESOURCE 步骤选节点」的批量语义矛盾——单 tick 只出队 1 个的话，在 300~1200 并发目标下（`08 §1.2`）吞吐上限被这个数字锁死。

**队头阻塞（head-of-line blocking）必须可诊断**：

高优队列里队头步骤因「无匹配节点」或「等互斥锁」反复失败时，会持续占住出队尝试，后面的步骤即使可调度也只能干等。处理原则与实现：

```
每个 ZSet member 附带失败计数（Redis Hash: flowops:queue:retrycount:{queueId}）
  出队后若因「节点匹配失败 / 互斥锁未获取」回退：
    failTicks[member] += 1
    score 保持不变（保留原 enqueue_seq，防饥饿，见 §4.5）
  否则（真正下发成功）清除 failTicks[member]

当队头 failTicks >= HEAD_BLOCK_THRESHOLD（默认 10）：
  ① 该步骤仍留在队列（**不删除、不降级**——删除会让用户的任务凭空消失）
  ② 向后扫描 SCAN_LIMIT 条，跳过 failTicks >= 阈值的 member，尝试出队后面的步骤
  ③ 写诊断：queue_head_blocked{queueId, taskStepId, reason, failTicks, since}
  ④ 指标 + 告警（见 §14.1）
```

> **"保留队列 + 向后扫描"而非"取出放回"**：后者会造成每个 tick 的抖动（取出→失败→放回→再取出），且放回时若重排 score 会破坏 FIFO。留在队列里、按失败计数跳过，是代价最小的方案。

**CAS 占位（防重复下发）**：

```
⚠️ 关键：不能直接 ZREM 后下发。若 ZREM 成功但进程崩溃，该步骤就丢了。
   正确顺序（"先占位，后处理"）：

   ① CAS 占位（DB，防重复）：
      UPDATE task_step
         SET status = 'SCHEDULING', dispatch_token = :uuid, version = version + 1
       WHERE id = :taskStepId
         AND status = 'WAITING_RESOURCE'
         AND dispatch_token IS NULL
      → 受影响行数 = 0 → 已被他方处理，跳过（ZREM 后继续下一个）

   ② ZREM（从队列移除）
      → 返回 0 说明已被移除（并发场景），回滚 ① 的状态（改回 WAITING_RESOURCE）

   ③ 提交到下发线程池（异步）
```

> **① → ② 的顺序不可颠倒**：先 ZREM 再 CAS 会出现"从队列消失但状态没改"的窗口（步骤凭空消失）；先 CAS 再 ZREM 最坏情况是"状态改了但还在队列里"，下次出队时 CAS 失败自然跳过——**安全的方向**。

### 4.4 出队时的优先级重估（G1-3）

```
问题：高优任务在低优任务入队后提交。若队列头是低优任务（已占位），高优任务排在后面。
      ZSet 的 score 已按优先级排序，所以「排序」是自动正确的。
      那为什么 PRD 还要求"出队时重新评估"？

答案：因为「手动插队」和「优先级变更」会改变 score。两个场景：
  ① 插队（PRD §10.10-5）：运维对 PENDING 任务插队 → ZADD 更新 score → 下次出队自动生效
  ② 队列隔离（G2-4）：队列并发满时，步骤虽在 ZSet 中也不能出队
```

**实现**：出队前先检查队列并发（§6.1），不足则**不看队列**直接跳过（不是取出来再放回，避免抖动）。

### 4.5 队列清理

| 场景 | 动作 |
|---|---|
| 步骤进入 `SCHEDULING` 后又失败回退 | 重新 `ZADD`（score 用**原 `enqueue_seq`**，保持 FIFO 公平性，不重新排到队尾） |
| 步骤被用户停止 | `ZREM` |
| 任务超时 | 该任务所有步骤 `ZREM` |
| 队列被禁用 | 整 key 保留但不参与出队（不删，启用后立即恢复） |
| 调度器重启 | **全量重建**（§10.2） |

> **回退时保留原序号**是公平性的关键细节。若回退时用新序号，节点抖动期间反复回退的步骤会被无限推后（饥饿）。

### 4.6 下发语义：at-least-once 与执行侧幂等键（⭐ v3 评审新增，A-5）

**必须显式声明的语义**：本调度器的下发保证是 **at-least-once（至少一次），不是 exactly-once**。

**为什么做不到 exactly-once**：下发命令发出后，执行侧（Agent / SSH 执行器）可能已经启动进程但**回执丢失**（网络中断、调度器在等待回执时重启）。此时调度器只知道"下发过了，不知道有没有成功"。要区分二者，需要执行侧提供事务性的"执行登记 + 回执"，这在跨进程、跨机器、可能被 `kill -9` 的场景下无法保证。

**因此正确的做法是：把幂等责任下沉到执行侧，并给执行侧提供可用的幂等键。**

```
下发命令携带三元组（作为执行侧幂等键）：
  (step_instance_id, attempt_no, dispatch_token)

  step_instance_id —— 步骤实例 ID，唯一标识"这次任务的这一步"
  attempt_no       —— 尝试序号（重试时 +1），区分同一步骤的不同尝试
  dispatch_token   —— 本次下发的 UUID（§4.3 CAS 阶段生成），区分同一次尝试的重复下发
```

**注入方式**：三者以环境变量形式注入算子进程：

```bash
FO_STEP_INSTANCE_ID=6023
FO_ATTEMPT_NO=2
FO_DISPATCH_TOKEN=8f2c41ab-...
```

**各方的责任边界（必须写进算子开发规范）**：

| 方 | 责任 |
|---|---|
| 调度器 | 保证同一次下发重复到达时，三元组**完全相同**（不重新生成 `dispatch_token`）；重试时 `attempt_no` 递增 |
| 执行侧（Agent） | 收到下发时先按 `dispatch_token` 查本地执行登记表；已存在 → **直接回"已接收"，不重复启动进程** |
| 算子 | **若算子本身有副作用**（写数据库、传文件、调外部 API），必须自行按 `(step_instance_id, attempt_no)` 做业务幂等（如用唯一键/临时文件+原子 rename）。平台无法替算子保证这一点 |
| 平台侧最小兜底 | 算子发布时声明 `idempotent: true/false`（`07 §9.1` 的算子元信息）；声明为非幂等的算子，在"下发回执丢失"场景下**不自动重下发**，而是标记为 `UNKNOWN` 并告警，由人工确认后再决定重跑——**静默重跑一个非幂等算子是数据事故** |

**下发回执丢失的处理流程**（补充 `§8.3` 的"调度中卡住"）：

```
SCHEDULING 超过 2 分钟仍未收到回执：
  ① 查执行侧执行登记表（若 Agent 在线且可查）→ 已启动 → 转 RUNNING，正常继续
  ② Agent 不可查 / 明确无记录 → 视算子 idempotent 声明分流：
       idempotent = true  → 重新下发（执行侧按 dispatch_token 去重）
       idempotent = false → 步骤置 UNKNOWN，告警，等人工介入（不做自动重跑）
  ③ 两种情况都必须写审计 + 指标 scheduler.dispatch.receipt_lost
```

> 这一步是"静态正确、动态未闭环"的另一处：`§8.3` 原写「`SCHEDULING` 超过 2 分钟 → 回退 `WAITING_RESOURCE`（下发已失败）」——**"回退"默认了下发失败**，但真实情况是"可能失败也可能已经跑起来了"。直接回退会让一个正在运行的步骤被再次下发，产生重复执行。

## 5. 节点匹配（NodeMatcher）

### 5.1 候选集过滤（硬约束，G3）

```java
List<ExecutorNode> candidates = nodes.stream()
    .filter(n -> n.getClusterId().equals(step.getTargetClusterId()))
    .filter(ExecutorNode::isEnabled)
    .filter(n -> n.getOnlineStatus() == ONLINE)                 // 在线
    .filter(n -> n.getCredentialRefId() != null)                // 凭据有效
    .filter(n -> osMatch(n.getOsType(), step.getOsConstraint())) // 操作系统
    .filter(n -> tagsMatch(n.getTags(), step.getTagConstraint()))// 标签约束（G10）
    .filter(n -> cpuEnough(n, step))                            // CPU 余量
    .filter(n -> gpuEnough(n, step))                            // GPU 余量
    .filter(n -> diskEnough(n, step))                           // 磁盘余量
    .filter(n -> memoryEnough(n, step))
    .toList();
```

**余量计算（⭐ 必须用「预留账本」，不能用实时实际用量）**：

```java
// ✅ 正确口径：reserved = Σ 该节点上所有「非终态」步骤的资源申请量
double reservedCpu = reservedLedger.cpu(nodeId);   // 调度器内存账本，权威副本
double availCpu    = node.getCpuTotal() - reservedCpu;
return availCpu >= step.getCpu();                  // >= 而非 >，余量恰好满足也应匹配

// 分配成功后立即记账，步骤进入终态时扣回
reservedLedger.acquire(nodeId, step.getCpu(), step.getMemory(), step.getGpu(), step.getDisk());
```

> **v3 评审修订（A-3，必修）**：原文档此处写的是「余量必须用**实时值**」（`redisCpuUsed(nodeId)`），这与后面的"调度器在内存中维护节点余量的权威副本，每次分配后立即扣减"**自相矛盾**，且按实时值实现**必然超卖**：
>
> **超卖场景**：一个算子启动后前 30 秒是加载数据阶段，实际 CPU 只有 0.5 核，但它申请了 4 核。节点心跳上报的"实际用量"仍是低的 → 调度器认为余量充足 → 连发 10 个同类步骤 → 30 秒后全部进入计算密集阶段 → **节点被打爆，10 个步骤一起 OOM/超时**。这是"峰值滞后"导致的经典超卖，靠调低心跳间隔无法解决（加载到计算的切换是秒级的）。
>
> **统一口径（三处对齐）**：
>
> | 概念 | 用途 | 载体 |
> |---|---|---|
> | **reserved（预留量）** | **准入判定的唯一依据** | 调度器内存账本 = Σ 非终态步骤的 `request`；`05` 需补 `executor_node.max_concurrent_steps` |
> | **actual（实际用量）** | 只做**资源画像、偏差告警、容量规划** | 节点心跳上报，落 `05` 的资源画像表 |
> | 偏差告警 | `actual` 持续 > `reserved × 1.5` → 说明步骤申请值偏低，需调参；`actual` 持续 < `reserved × 0.3` → 说明申请值虚高，浪费调度容量 | 见 `08 §3.2` |
>
> **为什么不是反过来**：用实际用量做准入，等于把"已经发生了的过载"当作准入依据；用预留量做准入，是"还没发生就已经算进去"。调度器的职责是**不制造过载**，不是**观测到过载后再反应**。
>
> **账本的可靠性**：`reserved` 是派生态，因此——① 调度器启动时由 DB 全量重建（Σ 该节点上 `status NOT IN (终态)` 的 `task_step` 资源申请量，见 `§10.2`）；② 每次分配/释放**先改 DB 状态再改账本**（若先改账本后改 DB 且进程崩溃，账本会永久少算）；③ Redis 只做跨进程共享，不是权威源。

### 5.2 三级排序（G3，明确排除随机）

```java
Comparator<ExecutorNode> byScheduling = Comparator
    .comparingInt(ExecutorNode::getRunningTaskCount)          // ① 运行任务数最少
    .thenComparing(Comparator.comparingDouble(ExecutorNode::availCpu).reversed())  // ② 剩余 CPU 最多
    .thenComparing(ExecutorNode::getLastAllocatedAt,          // ③ 最近分配时间最早（最长未用）
                   Comparator.nullsFirst(Comparator.naturalOrder()));

ExecutorNode chosen = candidates.stream().min(byScheduling).orElse(null);
```

> **③ 的语义**：`last_allocated_at` 为 `null`（从未分配）视为**最早**（优先使用），符合"冷节点先用"的直觉，也让新加入的节点立刻参与负载。

### 5.3 集群亲和（G11）

```
工作流配置 cluster_affinity_enabled = true：

  ① 取任务内**已完成/运行中**步骤的集群集合 pinnedClusters
  ② 若 pinnedClusters 非空且 size == 1：
       优先在 pinnedClusters 内匹配
  ③ 若匹配失败 → 跨集群匹配，并在 diagnosis_info 中记录：
       { "affinityBroken": true,
         "reason": "亲和集群 CL-0001 无满足 [CPU>=8, tag=gpu] 的节点",
         "fallbackCluster": "CL-0002" }
  ④ 若 pinnedClusters 有多种集群（本身已跨）→ 不再约束，正常匹配
```

**必须记录降级原因**——否则用户看到"说好同集群却跨了"会困惑（PRD §12.2 明确要求"在调度诊断中说明"）。

### 5.5 预计开始时间（ETA）估算

**问题**：ETA 是用户最关心的信息，但排队时长受节点释放时间影响，理论上不可精确预测。

**方案**：**基于该队列近 7 天平均排队时长的统计估算**（PRD §10.10 明确采用此法）。

```sql
-- 每 10 分钟刷新一次，缓存到 Redis（key: flowops:eta:{queueId}）
SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY (start_time - submit_at))
  FROM task
 WHERE queue_id = :queueId
   AND submit_at > now() - interval '7 days'
   AND start_time IS NOT NULL
   AND trigger_type <> 'BACKFILL';      -- 回填任务会污染统计
```

```
eta = avgWaitPerTask(queueId) × (当前队列位置 / 平均并发度)
```

**展示口径必须是"约 X 分钟后"**，且必须标注依据（"基于该队列近 7 天平均排队时长估算"）——**不要给出精确到秒的时间**，那是不可信的承诺。样本不足（< 20 条）时显示"数据不足，无法估算"。

## 6. 并发与互斥控制（G6/G7）

### 6.1 四级并发控制总表

| 级别 | 配置来源 | 检查时机 | 超限行为 |
|---|---|---|---|
| **项目级** | `project.max_concurrent_tasks` | 提交时（PENDING → SCHEDULING） | 保持 PENDING，记录队列位置 |
| **工作流级** | `workflow.max_parallel_runs` + `concurrency_policy` | 提交时 | FORBID → FAILED + 告警；QUEUE → 保持 PENDING；ALLOW → 放行 |
| **队列级** | `queue.max_concurrent_tasks` | 出队时 | 不出队（跳过该队列） |
| **步骤级（互斥锁）** | `workflow_step.mutex_group` | 节点匹配成功后 | 进 `WAITING_RESOURCE`，阻塞原因=等待互斥锁 |

### 6.2 `ConcurrencyGuard`：统一入口（D-12 单点收敛）

**所有触发路径必须调用同一个方法**（G6）：

```java
public interface ConcurrencyGuard {
    /**
     * 检查工作流级 + 项目级并发。
     * @return CheckResult(allowed, actualCount, limit, policy, action)
     */
    CheckResult checkBeforeSubmit(Long workflowId, Long projectId);

    /** 出队前检查队列级并发 */
    boolean tryAcquireQueueSlot(Long queueId);

    /** 步骤执行前获取互斥锁 */
    boolean tryAcquireMutex(String mutexGroup, Long taskStepId, String holderDesc);

    /** 释放（步骤结束统一调用，幂等） */
    void release(String mutexGroup, Long taskStepId);
}
```

**统一入口的强制手段**（不能只靠"大家都记得调"）：

```java
// 任务创建收敛到唯一个方法，内部强制走并发检查
@Service
public class TaskSubmitService {
    @Transactional
    public Task createTask(TaskSubmitCmd cmd) {
        // ⭐ 唯一入口：任何触发方式（手动/定时/API/回填）都必须走这里
        CheckResult r = concurrencyGuard.checkBeforeSubmit(cmd.workflowId(), cmd.projectId());
        if (!r.allowed()) {
            return handleExceeded(r, cmd);   // 按 policy 处理
        }
        return doCreate(cmd);
    }
}
```

> **防绕过的工程手段**：① `TaskMapper.insert` 只在 `TaskSubmitService` 内被调用（ArchUnit 单测断言）；② 定时触发与回填也调 `createTask`，不直接 insert。**这条规则用单测守住，不靠 code review**。

### 6.3 互斥锁实现

```
Key:   flowops:mutex:{mutexGroup}
Type:  Redisson RLock（可重入、看门狗自动续期）
Value: 持有者描述 "task:{taskId}/step:{stepName}"

获取（tryLock）：
  ① SETNX + 记录 holder → 成功：写 task_step.mutex_holder = true，写 holder 信息
  ② 失败：读 holder → 构造阻塞原因
       "等待互斥锁 etl_lock（当前持有者：任务 TASK-20260921-0003 / 步骤 数据同步）"

释放：
  ① 步骤进入终态（SUCCESS/FAILED/TIMEOUT/STOPPED）时**必须释放**
  ② 释放是幂等的（Redisson 已解锁再 unlock 不报错）
  ③ 释放时同步 DB：task_step.mutex_holder = false

超时保护（G7-4）：
  ① 锁 TTL 设定为 max(步骤超时时间, 1 小时) 的 1.5 倍
  ② 独立扫描线程：对 mutex_holder = true 且已超时的步骤，强制释放 + 写异常记录
  ③ 强制释放必须写审计 + 告警（这是数据可能被并发写入的危险信号）
```

**为什么 TTL 要大于步骤超时**：步骤执行时锁必须有效；若 TTL < 超时时间，步骤还在跑锁却过期了 → 另一个步骤拿到同名锁 → **并发写同一资源**，正是互斥锁要防的事故。用 1.5 倍留出安全边界。

**调度器重启的锁恢复**：进程崩溃时 Redisson 锁因 TTL 到期自动释放，但 `task_step.mutex_holder = true` 还在 DB 里（脏标记）。`RecoveryService` 启动时必须：① 对有 `mutex_holder=true` 但锁已不存在的步骤，重新加锁（若步骤仍在 RUNNING）；② 若步骤已终态，清理标记。

### 6.3.1 等待者队列：拿锁失败后如何回到可调度状态（⭐ v3 评审新增，A-1）

**问题**：按 `§4.3`，步骤在**出队时就已经 `ZREM`** 了。若它在 ⑤/⑥ 阶段拿不到互斥锁，会退回 `WAITING_RESOURCE`——**此时它不在任何队列里，也没有任何唤醒机制**。结果：

- 步骤只能干等 `wait_timeout`（默认 3600s，见 `§8.3`）才被判调度失败；
- `§6.3` ② 精心构造的"当前持有者：任务 xxx / 步骤 xxx"根本没机会展示（因为诊断是查的时候才构造，但任务会先超时失败）；
- **唯一的救命路径是重启调度器**（`§10.2` 启动重建会把它重新入队）——这不能作为正常路径。

**修复：为每个互斥组维护一个等待者 ZSet**。

```
Key:   flowops:mutex:{mutexGroup}:waiters
Type:  ZSET
Member: taskStepId
Score: 该步骤原始的 enqueue_seq（★ 复用原序号，保持 FIFO 与跨队列公平性）
```

**流程**：

```
⑥ MutexAcquirer.tryAcquire(group, stepId):
   成功 → 正常下发
   失败 →
     ① ZADD waiters  (score = task_step.enqueue_seq)
     ② 状态回退 WAITING_RESOURCE，写阻塞原因（含 holder 与 waiters_count）
     ③ 不回 ready 队列（避免与"队列并发额度"语义混淆）

锁释放时（步骤终态 / 强制释放 / 恢复清理）：
   ① unlock
   ② ZPOPMIN waiters → 取 seq 最小的等待者
   ③ 若取到 → 该步骤直接尝试 tryLock 并下发（同 tick 内完成，不等下一轮全量匹配）
       失败（被插队的别人抢到）→ 重新 ZADD 回 waiters（保留原 seq）
   ④ 若 waiters 为空 → 无动作
```

**为什么必须复用原 `enqueue_seq` 作 score**：等待者之间是"谁先来谁先拿"，用原序号而不是新发号，才能保证一个已经等了 10 分钟的步骤不会被刚提交的步骤插到前面（与 `§4.5` 回退保序是同一条公平性原则）。

**并发安全**：`unlock → ZPOPMIN → tryLock` 必须放在同一个 Lua 脚本里执行（否则两个释放者会 pop 到同一等待者，或 pop 出来后锁被第三方抢走）。脚本只需保证"原子地 pop 一个 member 并写入 holder"，拿到 member 后的实际下发仍走常规路径。

**防泄漏（三条必须同时成立）**：

| 风险 | 兜底 |
|---|---|
| waiters 里有已终态/已停止的步骤 | 步骤进入终态时**无条件 `ZREM`** waiters（幂等）；`RecoveryService` 启动时按 DB 全量重建 waiters |
| 锁被强制释放但 waiters 未消费 | `§6.3` 的超时扫描线程在强制释放后**必须走同一条唤醒路径** |
| Redis 重启导致 waiters 丢失 | `§10.2` 启动恢复按 `mutex_holder` + `WAITING_RESOURCE` 全量重建（同 ZSet 就绪队列的重建逻辑） |

**可观测性**：`waiters_count` 进入 `blocking_reasons[]`（`07 §6.6` 的诊断结构），并暴露指标 `scheduler.mutex.waiters{group}` 与 `scheduler.mutex.holding_seconds{group}`（后者超 30min 告警，见 `08 §3.2`）。

### 6.4 队列并发与"队列隔离优先于优先级"（G2-4）

```
队列 A（高优队列，max_concurrent = 3）：已满
队列 B（低优队列，max_concurrent = 3）：空闲

队列 B 中有个 priority = 100 的任务
→ 它**不能**占用队列 A 的槽位
→ 只能在队列 B 中等待（若队列 B 也满则一起等）

实现：并发槽位属于队列，不是全局。ZSet 按 queueId 分 key，天然隔离。
```

> **PRD 明确"队列隔离优先于优先级"**，这是有意的设计：避免低优队列通过提高任务优先级来占用高优队列资源，破坏队列作为资源隔离边界的作用。

## 7. DAG 推进（DagAdvancer）

### 7.1 图结构的内存表示

```java
public class DagGraph {
    private final Map<Long, StepNode> nodes;         // stepId -> node
    private final Map<Long, List<Long>> successors;  // 邻接表（出边）
    private final Map<Long, Integer> inDegree;       // 入度（剩余未完成上游数）
    private final Set<Long> roots;                   // 入度 0（NOTE 步骤排除）
}
```

**加载时机**：任务创建时从 `workflow_step` + `workflow_edge` 加载一次，缓存在调度器内存（`Map<taskId, DagGraph>`），任务完成后移除。任务数 × 步骤数可控（500 × 10 = 5000 节点），无需持久化缓存。

### 7.2 推进算法

```
每 tick 对每个活跃任务的 DagGraph 执行：

for (Long stepId : graph.pendingSteps()) {
    TaskStep st = loadStep(stepId);

    if (st.status == NOT_STARTED) {
        if (graph.inDegree(stepId) == 0) → 转移 WAITING_RESOURCE
        else                            → 转移 WAITING_DEPENDENCY
    }
    else if (st.status == WAITING_DEPENDENCY) {
        if (graph.allUpstreamSuccess(stepId))  → 转移 WAITING_RESOURCE
        else if (graph.anyUpstreamFailed(stepId)
                 && strategy == TERMINATE)      → 转移 STOPPED（不再执行）
    }
    else if (st.status == SUCCESS) {
        // 上游完成 → 递减下游入度（只做一次！）
        if (!graph.consumed(stepId)) {
            graph.successors(stepId).forEach(graph::decrementInDegree);
            graph.markConsumed(stepId);
        }
    }
}
```

**`consumed` 标记的必要性**：入度递减必须**恰好一次**。若 tick 重复处理同一 SUCCESS 步骤（比如状态更新成功但本 tick 提前返回），入度会被多减 → 步骤被提前触发。用内存标记（任务级，不需要持久化）保证幂等。

### 7.3 任务级终结判定

```
每 tick 检查：
   若所有**可执行步骤**（stepType = TASK）均处于终态：
      ① 全部 SUCCESS                        → 任务 SUCCESS
      ② 存在 FAILED 且无 PARTIAL 语义需求     → 任务 FAILED
      ③ 存在 SUCCESS + FAILED（分支 DAG）    → 任务 PARTIAL
      ④ 存在 TIMEOUT                        → 任务 TIMEOUT
      ⑤ 存在 STOPPED 且由用户触发            → 任务 STOPPED
   注意：NOTE 步骤不参与判定（PRD §10.8 规则 1"备注除外"）
```

**优先级**：`STOPPED > TIMEOUT > FAILED > PARTIAL > SUCCESS`。用户主动停止的语义最强（用户意图明确）。

## 8. 生命周期扫描

### 8.1 心跳与在线判定（G4/G5，PRD §12.2 表）

```
节点 Agent 每 15s 上报：POST /internal/nodes/{nodeId}/heartbeat
  → 更新 executor_node.last_heartbeat_at, heartbeat_miss_count = 0
  → 写 Redis: flowops:node:hb:{nodeId} = now（TTL 60s）
  → 上报资源用量（更新 Redis 余量）

HeartbeatMonitor 每 5s 扫描：

  ① 单次缺失（距上次心跳 15s~45s）：
       heartbeat_miss_count++，online_status 保持 ONLINE
       前端展示「心跳异常」标记（G5：状态不变、不告警）

  ② 连续 3 次缺失（> 45s）：
       online_status = OFFLINE
       → 触发「执行节点离线」告警（PRD §10.12）
       → 处理该节点上的运行中步骤（见 ③）

  ③ 离线节点上的运行中步骤：
       status 保持 RUNNING，但设置 recovery_deadline = now() + 5min
       在诊断中标注「等待执行节点恢复」
       ⚠️ 不直接判失败（G4）

  ④ 恢复窗口内节点恢复上报：
       → 步骤继续执行（状态不变，清除 recovery_deadline）
       → 恢复在线告警可发（可选，V1.1）

  ⑤ 恢复窗口到期（> 5min 无心跳）：
       → 步骤 FAILED，fail_reason = "执行节点失联"
       → 释放该步骤持有的互斥锁（关键！否则锁永久占用）
       → 触发「步骤失败」告警
```

> **⑤ 中释放锁是易漏项**：节点失联的步骤永远不会自己释放锁。若不显式释放，同名互斥锁会被永久占用（虽然后续有 TTL 保护，但 TTL 到期前的等待是纯粹的资源浪费）。
>
> **v3 评审补充（两处口径固化）**：
>
> 1. **`recovery_deadline` 是推导值，不是独立列**。`05` 的 `task_step` 没有该列（也不需要有）：统一定义为 **`recovery_deadline = 该步骤所在节点的 `last_heartbeat_at` + 5min`**，由 `LifecycleScanner` 每次扫描时计算，不落库。若将来确需落库（例如要展示"还剩多久判失败"），再在 `05` 补列并同步本文。
> 2. **⑤ 的释放锁必须走 `§6.3.1` 的唤醒路径**——即"强制释放 + `ZPOPMIN waiters` 唤醒下一个等待者"，否则等待该互斥组的步骤会卡到 `wait_timeout`（A-1 的同一类问题）。

### 8.2 单次心跳缺失不触发状态变化（G5 的实现细节）

**为什么这样设计**：公网/跨机房网络抖动会导致偶发丢包，若立即判离线会引发大量误报告警和步骤误判失败。45s（3 次）阈值给了 3 次重试机会。

**前端如何区分**：

| 条件 | 状态 | 展示 |
|---|---|---|
| 距心跳 < 15s | `ONLINE` | 绿点 |
| 15s ≤ 距心跳 < 45s | `ONLINE` | 绿点 + 黄色"心跳异常"角标 |
| ≥ 45s | `OFFLINE` | 灰点 + 告警已触发 |

### 8.3 超时扫描

| 对象 | 超时来源 | 处理 |
|---|---|---|
| 步骤实例 | `workflow_step.timeout_seconds`（继承链解析后） | 终止进程 → `TIMEOUT` → 释放锁 → 释放节点资源 |
| 任务 | `sum(步骤超时)` + 缓冲，或工作流级配置 | 终止所有运行中步骤 → `TIMEOUT` |
| 队列等待 | `queue.wait_timeout_seconds` | `WAITING_RESOURCE` → `FAILED`（G9） |
| 互斥锁持有 | `max(步骤超时, 1h) × 1.5` | 强制释放 + 告警（§6.3） |
| 调度中卡住 | `SCHEDULING` 超过 2 分钟 | 按 `§4.6` 的回执丢失流程处理（**不可一律回退重下发**） |

**"终止进程"的实现**：调度器通知执行侧（Agent / SSH 执行器）`kill -TERM` → 等待 10s → 若仍在则 `kill -KILL`。**必须在 DB 记录 `kill` 动作**，供排障。

### 8.4 恢复窗口的时序图

```
t=0    节点最后一次心跳
t=15s  miss=1  （状态 ONLINE，标心跳异常）
t=30s  miss=2  （状态 ONLINE，标心跳异常）
t=45s  miss=3  → OFFLINE + 触发离线告警
                 步骤标 recovery_deadline = t=345s，诊断显示"等待节点恢复"
t=100s 节点恢复 → miss=0，ONLINE，步骤清除 deadline，**继续执行**
       （若此时步骤进程实际已死，会因无输出而在步骤超时后判 TIMEOUT——这是可接受的）

── 另一条路径 ──
t=345s 仍无心跳 → 步骤 FAILED（执行节点失联）+ 释放锁 + 触发告警
```

## 9. 失败与重试

### 9.1 步骤级重试

```
判定：exit_code ∉ operator_version.success_codes（默认 {0}）
     且 retry_count < (继承链解析后的 retry_count)

动作：
  ① 写 task_step_retry（attempt_no = retry_count + 1，记录本次失败的机器/退出码/耗时）
     ⚠️ 重试历史在「每次执行开始时」写还是「失败时」写？
        正确做法：**每次执行开始时写一条 RUNNING 记录，结束时更新为终态**。
        否则失败的瞬间崩溃会丢掉这次尝试的记录。
  ② status = RETRYING
  ③ 计算 next_retry_at = now() + retry_interval_seconds
     ★ 落库到 task_step.next_retry_at（v3 新增列，见 05 §3.5）
       RetryHandler 按 WHERE status='RETRYING' AND next_retry_at <= now() 扫描
       （原实现靠内存定时器，调度器重启后重试就丢了）
  ④ 释放节点资源与互斥锁（让其他步骤可用）——释放锁时同样走 §6.3.1 的唤醒路径
  ⑤ RetryHandler 扫描到 next_retry_at 到达 → status = WAITING_RESOURCE（重新参与调度）
     ★ 重新入队时沿用原 enqueue_seq（§4.5 的防饥饿原则）
```

**重试是否换节点？** —— **默认换**（重新参与节点匹配）。原因：同一节点上同样的步骤失败，很可能是节点环境问题，换节点能规避。若算子版本需要考虑"状态残留"，应由算子自身保证幂等（这是算子侧责任，平台不提供"固定节点重试"配置）。

### 9.2 失败策略（G11）

| 策略 | 语义 | 实现 |
|---|---|---|
| `TERMINATE` | 步骤失败后**终止整个任务** | 该步骤 `FAILED` → 所有 `NOT_STARTED`/`WAITING_*` 步骤 → `STOPPED` → 任务 `FAILED` |
| `RETRY` | 按 `retryCount` 重试；**耗尽后等同于 TERMINATE** | 注意 `RETRY` 不等于"失败也继续"——PRD 无"忽略失败继续"语义 |

> **PRD 未定义"忽略失败继续执行（continue-on-error）"**。若一期出现此需求，需新增 `failureStrategy = IGNORE`，且**必须**在 UI 上强提示（否则下游步骤拿到空数据会静默产出错误结果）。当前**不实现**。

### 9.3 任务级重跑与重跑失败步骤（PRD §10.10）

| 操作 | 语义 | 实现 |
|---|---|---|
| **重跑任务**（`retry`） | 生成**新任务实例** | 新 `task_id`；原任务不变（保持终态） |
| **重跑失败步骤**（`rerun-failed`） | **不产生新任务编号**，仅重跑失败及其下游 | 见下方详述 |

**重跑失败步骤的实现**：

```
① 校验任务已终结（RUNNING 状态不允许）
② 找出目标步骤集合：
   targets = 指定的 stepInstanceIds
             或（缺省）所有 FAILED/TIMEOUT 步骤 + 它们的**所有下游**（拓扑可达）
③ 对 targets 中每个步骤：
     - 若状态是 SUCCESS：**保留结果**（复用 output_vars，不重跑）
       ⚠️ 但若它在 targets 内（作为失败步骤的下游），必须重跑——否则拿到的是坏数据
     - 若状态是 FAILED/TIMEOUT/STOPPED：reset → NOT_STARTED
       清空 start_time/end_time/duration/exit_code/fail_reason，retry_count 保留（累加）
       output_vars 清空（重新产出）
④ 任务 status → RUNNING，重新加载 DagGraph，清空 executed 标记
⑤ task.finished_steps / current_step_* 重算
```

**"复用上游成功结果"的关键**：`task_step.output_vars` 是持久化的，重跑时不清理非目标步骤的 `output_vars` → 变量解析链（`03 §4.4`）第 5 层自然拿到旧值。**这是不需要额外机制的设计收益**。

**一个必须处理的坑**：重跑失败步骤时，若目标步骤的上游是 SUCCESS 但**上游上游**是失败的（不可能，因为失败会阻断下游）——由 DAG 语义天然保证，无需额外校验。

### 9.4 尝试次数上限（防无限重试）

`retry_count` 由继承链解析，若用户在工作流级配了 `retry_count = 100`：
- 平台硬上限 **`MAX_RETRY = 10`**（超出则截断为 10 并在 DAG 校验时告警）；
- 校验**规则 9**（`07 §9.2`，PRD §10.8 的 8 条 + 2 条实现补充）包含此项检查。
  > v3 评审：原写「校验规则 8（`03 §4.3`）」，但 `03 §4.3` 的规则 8 是「必须声明并发控制配置」；`MAX_RETRY ≤ 10` 在 `07 §9.2` 编号为**规则 9**。

## 10. 选主与恢复（⭐ 引擎可靠性核心）

### 10.1 选主

```
Redisson 分布式锁：flowops:scheduler:leader
  ├─ 获取成功 → LeaderElector.isLeader = true → 启动全部调度线程
  └─ 获取失败 → Standby：仅维持心跳（写 flowops:scheduler:standby:{instanceId}，TTL 10s），
                每 3s 尝试抢锁

锁续期：Redisson 看门狗（默认 30s TTL / 10s 续期）
  ⚠️ 不要自己实现续期。看门狗在进程卡 GC 时会停止续期 → 锁自动释放 → Standby 接管。
     这是有意的：宁可切换也不要双主。

网络分区（脑裂）防护：
  ① Redisson 锁本身基于 Redis 单点/Failover，不会双主；
  ② Leader 每 tick 校验自己是否仍持有锁（isHeldByCurrentThread）
     → 若丢失，立即停止所有调度线程并转为 Standby
  ③ 所有状态更新走 CAS，即使出现短暂双主也不会产生重复执行
     （这是 §4.3 CAS 设计的额外收益）
```

### 10.2 启动恢复（`RecoveryService`，D-09）

**原则：PG 是唯一真源，Redis 是可重建的派生态。启动时从 PG 重建 Redis。**

```
recover() 步骤：

① 从 PG 加载所有活跃任务（status ∈ PENDING/SCHEDULING/RUNNING）及其步骤
   索引：idx_task_active（部分索引，快速）

② 重建就绪队列 ZSet
   对每个 WAITING_RESOURCE 步骤：
     ZADD flowops:queue:ready:{queueId} score=原score member=stepInstanceId
     score 用 task.enqueue_seq 重算（保证 FIFO 顺序与重启前一致）

③ 重建互斥锁持有点
   查 task_step WHERE mutex_holder = true AND status = 'RUNNING'
     → 逐个 tryAcquireMutex（若锁已因 TTL 过期，重新获取）
     → 若获取失败（其他进程持有？不可能，单活）→ 记录异常并告警

④ 重建节点余量视图（内存）
   ✅ **按 §5.1 的预留账本口径重建**（v3 修订）：
     reserved[nodeId] = Σ 该节点上 status ∉ (SUCCESS/FAILED/STOPPED/TIMEOUT/SKIPPED)
                        的 task_step 的 cpu/memory/gpu/disk 申请量
   ⚠️ 这不是"实际用量"——实际用量只做画像与偏差告警，不参与准入判定。
   ⚠️ 防御：若某步骤的资源申请字段为空（历史数据），按算子版本 default_resource 兜底，
        仍为空则记 WARN 并按 0 计（宁可少算，不可因此拒绝所有调度）

④b 重建互斥锁等待者 ZSet（v3 新增，§6.3.1）
   对每个 mutex_group：
     waiters = 该组下 status='WAITING_RESOURCE'
               且 blocking_reason.type='MUTEX_GROUP' 的步骤
     ZADD flowops:mutex:{group}:waiters  score=task_step.enqueue_seq  member=stepInstanceId
   ⚠️ 保留原 enqueue_seq，保证重启前后等待顺序一致

⑤ 处理"僵尸步骤"（status=SCHEDULING 但无 dispatch_token 或超过 2 分钟）
   → 回退 WAITING_RESOURCE（可能是崩溃瞬间正在下发）

⑥ 处理"孤儿运行中步骤"（status=RUNNING 但机器上进程已死）
   → 这是一期难点：平台无法知道远程进程是否还活着
   → 一期策略：**等步骤超时**（超时后 terminate 并判 TIMEOUT）
   → 二期优化：Agent 侧维护进程 PID，重启后主动查询进程存活

⑦ 重建内存 DagGraph（从 workflow_step + workflow_edge）
   ⚠️ 入度需要考虑"已完成步骤"：
      实际入度 = 该步骤的原始入度 - (已完成上游数)
      简化实现：保留原始入度，遍历时对已完成上游立即 decrement
             （等价，但需要 §7.2 的 consumed 标记从"已完成步骤"初始化）

⑧ 恢复完成 → 记日志 + 更新指标（恢复耗时、恢复任务数/步骤数）
```

**⑧ 的指标很重要**：恢复耗时是判断"这套架构是否健康"的核心信号。若恢复越来越慢（30s → 5min），说明活跃数据在膨胀或索引失效。

### 10.3 恢复的幂等与安全性

| 风险 | 防护 |
|---|---|
| 恢复期间新任务创建 | 恢复在**启动时同步完成**，调度主循环在恢复后才启动（不并发） |
| 重复恢复 | `recover()` 加分布式锁（同一时刻只有一个实例恢复） |
| 恢复慢导致长时间无调度 | 恢复只做**内存 + Redis 重建**，不加载历史数据（快速，通常 < 5s） |
| Redis 全丢 | 从 PG 全量重建（这就是 D-09 的价值） |
| 恢复中崩溃 | 幂等：ZSet 重建用 `ZADD`（重复执行结果一致）；锁用 `tryAcquire`（幂等） |

### 10.4 Standby 的作用

**不做热备（不共享状态、不做双写）**——Standby 只做两件事：① 维持进程存活；② 抢锁。

**切换时间**：Leader 崩溃 → 看门狗停止续期 → 30s 后锁释放 → Standby 抢到 → 执行恢复（< 5s）。**总切换时间约 30~40s**。

> **能否更快？** 可以让 Leader 主动释放（优雅关闭时），把切换缩到秒级。但**崩溃场景无法加速**（这是看门狗 TTL 的固有代价）。若要求 < 10s 切换，需改为基于 PG 的租约表（`scheduler_lease` 表 + 3s 心跳），代价是多一张表和一轮 DB 往返。**一期接受 30~40s**（调度中断 30s 对这类系统是可容忍的）。
>
> **v3 评审修订**：`08` 曾把选主写成「PG 租约表（`06 §16`）+ `scheduler_lease` 表 + ≤30s 切换」，三样都不存在（本文没有 §16，`05` 没有 `scheduler_lease` 表，且 Redisson 实测 30~40s 必然超过 ≤30s 的承诺）。**已统一为本文的 Redisson 方案**：`08` 的 N-2 改为 **≤45s**、Runbook 改为查 Redis、compose 改为 `replicas: 2`。
>
> 另：**Standby 必须是常驻进程**（`08 §2.3` 的 compose 已改为 2 副本）。若只有 1 个副本，崩溃后要先等编排层重新拉起容器（数十秒~数分钟），"30~40s 切换"在物理上不成立——因为没有进程在等着抢锁。

## 11. Cron 扫描与错过触发补跑

### 11.1 CronTriggerScanner

```java
// 每 tick 执行（1s 粒度足够，PRD §7.1-4 要求分钟级精度）
List<Trigger> due = triggerMapper.findDue(now, batchSize = 100);
// SQL: SELECT * FROM trigger
//      WHERE enabled = true AND deleted = false AND next_fire_time <= :now
//      ORDER BY next_fire_time LIMIT 100
//      索引：idx_trigger_next_fire（部分索引）

for (Trigger t : due) {
    // ① 取版本（锁定版本 or 跟随最新）
    Long versionId = t.getLockedVersionId() != null
                   ? t.getLockedVersionId()
                   : workflowMapper.currentPublishedVersion(t.getWorkflowId());

    // ② 走统一入口（G6）
    TaskSubmitCmd cmd = TaskSubmitCmd.fromTrigger(t, versionId, t.getNextFireTime());
    taskSubmitService.createTask(cmd);      // ← 内部强制并发检查

    // ③ 计算下次触发时间（见下方「推进基点」）
    trigger.setLastFireTime(t.getNextFireTime());
    trigger.setNextFireTime(cronUtils.nextExecutionAfter(
        t.getCronExpression(), t.getNextFireTime()));   // ★ 基点 = 本次 fire_time
}
```

### 11.1.1 触发幂等：`trigger_fire_log` 唯一键（⭐ v3 评审新增，A-4）

**问题**：上面的循环里，"创建任务"与"推进 `next_fire_time`"是两步。若调度器在两者之间崩溃：

- **重启后 `next_fire_time` 未推进** → 同一个触发点被**再次点火**，产生重复任务；
- 若反过来先推进再创建 → 崩溃后**静默丢掉一个触发点**（更糟，且完全无感知）。

**修复：为「触发点火」这件事本身加唯一键**。

```sql
-- 05 §3.5 新增（与 audit_log 同域）
CREATE TABLE trigger_fire_log (
    id              bigserial PRIMARY KEY,
    trigger_id      bigint      NOT NULL,
    fire_time       timestamptz NOT NULL,     -- 触发点（Cron 计算出的理论时刻，非实际执行时刻）
    task_id         bigint,                   -- 成功创建则为任务 ID；创建失败为 NULL
    status          varchar(16) NOT NULL,     -- FIRED / SKIPPED / FAILED
    skip_reason     varchar(32),              -- CATCHUP_LIMIT_EXCEEDED / WORKFLOW_DISABLED / ...
    created_at      timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uq_trigger_fire UNIQUE (trigger_id, fire_time)   -- ★ 幂等的唯一支点
);
CREATE INDEX idx_trigger_fire_recent ON trigger_fire_log (trigger_id, fire_time DESC);
```

**点火流程改为**：

```
① INSERT INTO trigger_fire_log(trigger_id, fire_time, status='FIRED') 
     ON CONFLICT (trigger_id, fire_time) DO NOTHING
  → 受影响行数 = 0：该触发点已点火过（崩溃重入）→ 跳过，只推进 next_fire_time
② 创建任务（走 TaskSubmitService）
③ UPDATE trigger_fire_log SET task_id = :taskId WHERE ...
④ 推进 last_fire_time / next_fire_time
```

> 先写 `FIRED` 再创建任务（而非先创建再写日志），是因为**"已点火但任务创建失败"**比**"任务创建了但没人知道"**容易处理：前者可查 `task_id IS NULL` 做补偿，后者只能靠对账发现。

**`next_fire_time` 的推进基点（必须定死）**：

| 场景 | 基点 | 理由 |
|---|---|---|
| 正常触发 | **本次 `fire_time`**（不是 `now()`） | 用 `now()` 会因调度延迟累积漂移：一个每天 02:00 的触发器若每次都按 `now()`（02:00:03）推算，几个月后会漂到 02:0x |
| 补跑（§11.2） | 逐个按各自的 `fire_time` 循环推进 | 保证跳过的触发点不会在下次补跑中复活 |
| 停机很久后恢复 | 从 `last_fire_time` 循环推进到 `> now`，受 `catch_up_max_times` 约束 | 见 §11.2；超出上限的部分显式写 `SKIPPED` 而不是静默丢弃 |

**保留期**：`trigger_fire_log` 只用于幂等判定与排障，保留 90 天后按 `created_at` 清理即可（不进冷存）。

### 11.2 错过触发补跑（G12）

```
问题：平台重启/维护期间，若 next_fire_time 已过多次，恢复后会怎样？
      若只取下一次，会丢掉维护期间的触发点；若全补，可能一次涌入几十个任务。

PRD 规则（§10.9-8）：默认开启补跑，**单个触发器最多补 3 次**。

实现：
  ① 恢复后扫描 next_fire_time < now 的触发器
  ② 计算错过的触发点列表（cron-utils 的 between 方法）
  ③ 取**最近 3 个**（不是最早 3 个！最近的对业务更有意义）
  ④ 逐个创建任务，biz_date 用对应的原触发日期
  ⑤ 跳过的次数记日志 + 在触发器详情展示"已跳过 N 次补跑"
  ⑥ next_fire_time 更新为"未来第一个触发点"
```

> **为什么取最近 3 个**：若停机 3 天，日调度器错过 3 个触发点，补这 3 个正好；若停机 1 个月（30 个触发点），补最近 3 个比补最早 3 个更符合业务直觉（数据时效性）。**且必须显式告知用户跳过了多少次**——静默跳过是数据可信度的隐患。

### 11.3 触发器与工作流启停联动（PRD §10.9-3/4）

```sql
-- 停用工作流时：记录每个触发器的原状态，然后暂停
UPDATE trigger
   SET enabled_before_disable = enabled,
       enabled = false,
       version = version + 1
 WHERE workflow_id = ? AND deleted = false;

-- 重新启用时：恢复到停用前状态
UPDATE trigger
   SET enabled = COALESCE(enabled_before_disable, enabled),
       enabled_before_disable = NULL,
       next_fire_time = <重算>,      -- 关键：恢复后必须重算下次触发时间
       version = version + 1
 WHERE workflow_id = ? AND deleted = false;
```

**`next_fire_time` 必须重算**：停用期间 `next_fire_time` 停在过去，若不重算，启用瞬间会被当成"错过触发"而补跑（用户没要求补跑）。

## 12. 回填批次调度（PRD §10.11）

### 12.1 批次执行模型

**回填不是"一次性创建所有任务"，而是"按窗口逐步投放"**：

```
BackfillScheduler（独立扫描线程，5s 周期）

for (batch : RUNNING 的批次) {
    ① 计算当前允许的在途任务数：
         inflight = 批次内 status ∈ (PENDING,SCHEDULING,RUNNING) 的 task 数
         allowed  = min(batch.eff_concurrency - inflight, 每次投放上限)
    ② 若 allowed <= 0 → 跳过（等下一轮）
    ③ 从 WAITING 日期队列取出 allowed 个 biz_date → 创建任务
    ④ 更新 batch.waiting_count / success_count / failed_count
    ⑤ 若所有日期已投放且所有任务终结 → batch.status = DONE
}
```

**为什么不预先建全部任务**：补 120 天 = 120 个任务，若一次全建，全部进 PENDING 队列 → 队列积压 + 项目额度被占满 → 影响正常调度。**按 `eff_concurrency` 滚动投放**是唯一正确做法。

### 12.2 并发度收敛公式（CONTRACT §8 明确）

```java
int effConc = batch.sequential
            ? 1
            : (workflow.concurrencyPolicy == FORBID
               ? 1
               : Math.min(batch.concurrency, workflow.maxParallelRuns));
```

**三层收敛**：① 用户选"顺序执行"→ 1；② 工作流策略是 FORBID（不允许并行实例）→ **必然降到 1**（否则任务会被并发检查拒绝，全部失败）；③ 否则取用户设定与工作流上限的较小值。

> **② 是关键**：用户在回填页设了 `concurrency = 10`，但工作流配了 `FORBID` —— 若前端不提示，用户会看到"提交了 10 并发但任务全部因并发超限失败"。因此 preview 接口**必须返回 `policyConflict` 让前端渲染收敛提示**（CONTRACT §8-2）。

### 12.3 时间冲突检测（±30 分钟窗口）

```sql
-- 判定：同工作流 + 同业务日期 + 计划投递时刻落在已有任务 ±30 分钟
SELECT t.task_id, t.status
  FROM task t
 WHERE t.workflow_id = :workflowId
   AND t.biz_date = :bizDate
   AND t.submit_at BETWEEN :plannedAt - interval '30 minutes'
                       AND :plannedAt + interval '30 minutes'
   AND t.deleted = false
   AND t.status <> 'STOPPED'
 LIMIT 1;
-- 索引：idx_task_conflict(workflow_id, biz_date, submit_at)
```

命中 → preview 响应返回 `conflict{taskId, status}`，前端标黄。

### 12.4 批次暂停/继续/取消

| 操作 | 语义 |
|---|---|
| 暂停 | `status = PAUSED` → BackfillScheduler 跳过该批次（**在途任务继续执行**，不中断） |
| 继续 | `status = RUNNING` → 恢复投放 |
| 取消 | `status = CANCELLED` → 停止投放；在途任务**保持运行**（PRD §10.11-5 允许用户选择，一期默认保持） |

> **暂停/取消都不中断在途任务**——这是有意的：中断正在跑的计算任务会浪费已消耗的算力，且可能留下脏数据。若用户需要立即停止，应单独去任务列表停止具体任务。

## 13. 线程模型与资源

### 13.1 线程清单（scheduler 进程）

| 线程/池 | 数量 | 职责 | 阻塞特性 |
|---|---|---|---|
| **主循环** | **1** | tick 九阶段（§3.2） | CPU 密集（短） |
| 心跳扫描 | 1 | 每 5s 检查心跳 | IO（读 Redis） |
| 超时扫描 | 1 | 每 5s 检查超时 | IO（DB 查询） |
| 回填调度 | 1 | 每 5s 投放批次任务 | IO（DB） |
| Cron 扫描 | 1 | 每 1s 扫描触发器 | IO（DB） |
| **命令下发池** | 8~32（可配） | SSH/WinRM/Agent 下发 | **IO 密集（秒级）** |
| Agent 上报接收池 | 8~16 | 处理退出码/资源/输出变量 | IO |
| 恢复 | 1（启动时同步） | RecoveryService | IO |
| 看门狗校验 | 1 | 每 5s 校验 leader 锁 | IO |

**总计常驻线程 < 60**，与任务量无关（关键：主循环单线程，工作量随活跃任务数增长但仍是内存操作）。

### 13.2 下发池的背压

```java
// 有界队列 + 拒绝策略：不丢弃，而是回退状态
ThreadPoolExecutor dispatcher = new ThreadPoolExecutor(
    coreSize, maxSize, 60, SECONDS,
    new ArrayBlockingQueue<>(1000),
    new RejectedExecutionHandler() {
        public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
            // ⭐ 不丢弃：把步骤状态回退到 WAITING_RESOURCE，下次 tick 重试
            DispatchTask dt = (DispatchTask) r;
            rollbackToWaitingResource(dt.taskStepId());   // 清 dispatch_token
            metrics.increment("dispatch.rejected");
        }
    });
```

**为什么不能简单丢弃**：丢弃会造成"步骤状态是 SCHEDULING 但永远不会下发"的僵尸步骤。必须回退状态让它重新参与调度。

### 14.2.1 调度决策留痕：`schedule_decision_log` 的写入点（⭐ v3 评审新增，A-20）

`08 §3.4` 给出过该表的 DDL 并要求"每次调度决策记录输入与结果"（PRD §15.5-2），但 `05` 无表、`06` 无写入时机 → 任务详情「调度诊断」面板（PRD §10.10）声称"直接查此表"，而该表不会被建也不会被写。**DDL 已迁至 `05 §3.5`，本文固化四类决策的写入点**：

| decision | 写入时机（代码位置） | 关键字段 |
|---|---|---|
| `DISPATCHED` | `§4.3` ③ 提交下发线程池成功后 | `node_id`、`score`、`enqueue_seq`、`wait_ms` |
| `DEFERRED` | `§4.4` 队列并发满而本次不出队 | `queue_id`、`running`、`max_concurrent_tasks` |
| `BLOCKED` | `§5.4` 匹配失败 / `§6.3` 拿锁失败 | `reason_code`（`NO_MATCHING_NODE` / `MUTEX_GROUP` / `QUOTA_*`）、`input_snapshot`（当时的约束与节点余量） |
| `SKIPPED` | `§4.3` CAS 失败（已被他方处理）、`§11.2` 补跑超限 | `reason_code`、`ref_task_id`（若已由他人创建） |

**写入纪律**：

- **只写"决策"，不写"心跳"**——每个步骤每次 tick 都写会瞬间撑爆表。规则是：**状态发生转移或有明确判定结论时写一条**，纯等待不重复写。
- **`input_snapshot` 必须包含判定当时的输入**（节点余量、队列占用、约束条件），否则事后无法回答"为什么当时没让我跑"。这是这张表存在的唯一理由。
- **写入失败不阻断调度**，但计 `scheduler.decision_log.write_failures` 并告警——诊断数据缺失不是 P0，但持续缺失会让排障能力失效。
- 保留 **7 天**后按 `created_at` 清理（与 `08 §4.2` 的保留期一致；`08` O-06 记录"排障常查历史可延长到 30 天"）。

## 15. 与其它模块的契约

### 15.1 调度器 ← 依赖的输入

| 输入 | 来源 | 提供方式 |
|---|---|---|
| 任务创建 | server（手动/回填） | **DB（写 task 表）**，调度器扫描 |
| 定时触发 | 调度器自己 | `trigger` 表 |
| 停止任务指令 | server | **DB（task.status = 'STOPPING'→STOPPED）** |
| 节点心跳 | Agent / 执行节点 | HTTP（内网端点）→ Redis + DB |
| 步骤退出码/输出变量 | Agent / 执行器 | HTTP（内网端点） |
| 配置变更（并发/队列） | server | DB（调度器每次使用时读取，或短 TTL 缓存） |

> ⚠️ **`STOPPING` 中间态**：用户在页面点停止，server 不能直接把状态改成 `STOPPED`（进程还在跑）。正确流程：
> ```
> ① server: task.status = 'STOPPING'（新增中间态）+ 写审计
> ② 调度器下一 tick 扫描到 STOPPING
> ③ 调度器终止所有运行中步骤的进程
> ④ 所有步骤终结后 → task.status = 'STOPPED'，设 stopped_by/stop_reason
> ⑤ 前端轮询/WebSocket 看到 STOPPED，按钮态恢复
> ```
> **`STOPPING` 需要加入任务状态枚举**（`05` 的表结构 CHECK 需同步——这是本文件对 `05` 的一处修正建议，见 §17）。

### 15.2 调度器 → 输出的副作用

| 输出 | 接收方 | 方式 |
|---|---|---|
| 步骤下发 | 执行节点 / Agent | `flowops-executor-client`（SSH/WinRM/Agent） |
| 日志推送 | 前端 | Redis Pub/Sub → server WebSocket |
| 告警事件 | 告警引擎（governance 域） | Redis Stream 或 DB 表（一期：直接调 service，因同库） |
| 审计（调度动作） | audit_log | DB 直写（如"强制释放互斥锁"） |
| 指标 | Prometheus | Micrometer |

## 16. 测试策略（引擎侧）

| 层次 | 覆盖点 | 方式 |
|---|---|---|
| **状态机单测** | 每个转移（§2.1/§2.2 表逐行）+ 非法转移拒绝 | 纯 JUnit，无 DB |
| **Score 构造单测** | 优先级/FIFO 组合、边界（同优先级同毫秒、优先级 0/100） | 纯 JUnit |
| **DAG 推进单测** | 线性/菱形/多分支/含 NOTE/含环（应拒绝） | 内存 DagGraph |
| **节点匹配单测** | 三级排序、约束过滤、余量边界（== 恰好满足） | Mock 节点列表 |
| **互斥锁单测** | 获取/释放/超时/幂等释放/重启恢复 | Testcontainers Redis |
| **并发控制单测** | 四级并发 + 各策略（FORBID/QUEUE/ALLOW）+ 防绕过 | Testcontainers PG+Redis |
| **恢复集成测试** | 构造活跃任务 → 崩溃模拟 → 重启 → 断言队列/锁重建正确 | Testcontainers |
| **补跑测试** | 停机模拟（改 next_fire_time 到过去）→ 断言补 3 次 + 跳过计数 | Testcontainers |
| **压力测试** | 500 活跃任务 / tick 耗时 < 200ms | 本地 + JMH |
| **故障注入** | Redis 重启、节点批量掉线、下发失败率 50% | 见 08 |

**必测的边界用例清单**（这些是最容易出 bug 的地方）：

1. 步骤余量恰好满足（`availCpu == step.cpu`）→ 必须匹配成功；
2. 同一毫秒入队两个同优先级步骤 → FIFO 顺序必须确定；
3. 回退重入队 → 保持原 `enqueue_seq`（不饥饿）；
4. 节点失联 → 5 分钟内恢复 → 步骤继续（不误判失败）；
5. 节点失联 → 超 5 分钟 → 步骤失败 + **锁被释放**；
6. 重跑失败步骤 → 上游 SUCCESS 的 `output_vars` 被复用；
7. 回填 `concurrency=10` + 工作流 `FORBID` → `effConc` 收敛为 1；
8. Leader 崩溃 → Standby 接管 → 无重复执行（用 `dispatch_token` 断言）。
