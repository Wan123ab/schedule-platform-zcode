## 1. 系统定位与设计目标

### 1.1 一句话定位

**一个有资源约束的 DAG 工作流调度平台**：用户把算子（可执行程序）编排成工作流，平台按依赖关系、资源余量、队列并发、节点标签等约束，把每一步调度到合适的执行节点上运行，并全程可观测、可干预、可追溯。

与通用任务调度框架的本质差异：

| 维度 | 通用调度框架（XXL-JOB 等） | 本平台 |
|---|---|---|
| 调度单元 | 单个任务 / 分片 | **DAG 工作流 + 步骤实例** |
| 资源模型 | 弱（线程池/执行器） | **强**：CPU/GPU/内存/磁盘申请-实际对比、标签约束、队列配额 |
| 多租户 | 弱 | **强**：租户→项目→集群/队列 M:N 隔离 |
| 可观测 | 执行日志 | **调度诊断**（为什么没跑起来）、变量快照、字段级审计 diff |
| 特殊语义 | — | **并发四级控制（项目 / 工作流 / 队列 / 互斥锁）+ 回填双闸门**（互斥锁为**步骤级、出队后竞争**，PRD §12.3 v3 回写 R-5） |

### 1.2 设计目标（可验证）

| 目标 | 量化指标 | 来源 |
|---|---|---|
| 调度实时性 | 触发到任务进入 RUNNING ≤ 5s（正常情况下） | 推导自缺口 #22 |
| 日志实时性 | 端到端延迟 ≤ 5s | PRD §13.2 |
| 离线判定准确性 | 连续 3 次（45s）未心跳才判离线，避免网络抖动误判 | PRD §12.2 |
| 并发安全 | 同一工作流不允许超并发实例；同名互斥锁全平台串行 | PRD §12.3 |
| 数据可追溯 | 已发布版本不可改；任务强绑定版本快照；审计含字段级 diff | PRD §7.2 / CONTRACT §10 |
| 规模支撑 | 集群 5→15、执行节点 200→800、并发运行任务 300→1200、工作流 ≤ 100 步骤（一期/三年） | **以 `08 §1.2` 的容量规划为准**（此处原写"单集群 ≤500 节点 / ≤2000 并发"，与 `08` 是两套数字） |

### 1.3 非目标（一期明确不做）

- ❌ 抢占式调度（PRD §12.2 明确）
- ❌ 步骤级强制停止（缺口 #9，V1.1）
- ❌ 算子审批流 / 安全扫描（缺口 #3）
- ❌ 资源画像与超量申请预警（PRD §13.4，V1.1）
- ❌ API / 事件触发（缺口 #7，V1.1，界面保留置灰）
- ❌ 移动端适配（SPEC §2.1 明确不做）

### 3.2 部署单元（三个进程 + 中间件）

| 单元 | 职责 | 可水平扩展 | 说明 |
|---|---|---|---|
| `flowops-server` | 全部 REST 接口、业务逻辑、WebSocket 日志通道 | ✅ 无状态，多副本 | 只处理「请求-响应」与聚合查询 |
| `flowops-scheduler` | 触发扫描、DAG 推进、队列管理、资源匹配、并发/互斥、心跳判定、超时处理 | ⚠️ 主备（单活）或分片 | **有状态决策中心**，需选主避免重复调度 |

| PostgreSQL | 业务、版本快照、任务、审计 | 主从 | 强一致数据源 |
| Redis | 队列、锁、缓存、会话、心跳 | Sentinel/Cluster | 高性能易失态 |

## 4. 关键架构决策

### 4.1 为什么 server 与 scheduler 分离（D-08）

| 方案 | 问题 |
|---|---|
| 单体：定时任务写在 server 里 | 多副本 server 会导致**重复调度**（每副本都跑一遍扫描）；要加分布式锁又让请求链路与调度链路互相拖累 |
| **拆分独立调度进程** ✅ | 调度单活（选主），server 无状态可随意扩容；两者通过 **DB 状态 + Redis 队列** 解耦，互不阻塞 |

**协作方式**：调度器不直接对外提供 API；server 写「待调度」状态到 DB，调度器轮询/订阅推进。

### 4.2 调度状态的唯一真源是 PostgreSQL，Redis 只做加速（D-09）

风险：Redis 是易失的，若把「任务状态」只放 Redis，宕机即丢。
**约定**：
- **任务/步骤实例的权威状态存 PG**（可审计、可回溯、可恢复）；
- Redis 只放**可重建的派生态**：就绪队列、互斥锁、心跳、缓存；
- 调度器启动时**从 PG 重建 Redis 队列**（recovery）。

### 4.3 日志走 WebSocket，不进主链路（D-10）

日志量是业务数据量的百倍级，若走 HTTP 轮询：
- 大量请求打在主库上；
- 轮询周期决定了「看起来卡不卡」。

**方案**：Agent 采集 → 调度器/日志服务 → ① 落库（热存 30 天）② **Redis Pub/Sub 推送 WebSocket**；前端断线重连用 `offset` 续传（PRD §13.2）。

### 4.4 版本快照不可变（D-11）

`任务 → 强绑定 workflowVersion`，版本发布后**不可修改、不可删除**（PRD §7.2 硬约束）。
**实现**：工作流编辑操作的永远是**草稿版本**；发布即冻结。否则历史任务无法回溯（这是审计与排障的根基）。

### 4.5 并发控制必须收敛到单点（D-12）

PRD §12.3：手动/定时/API/回填触发**必须走同一套并发检查**。
**实现**：所有触发路径都调用同一个 `ConcurrencyGuard.check(workflowId)`，用 Redis 分布式锁 + PG 计数双保险，**不允许任何路径绕过**。

## 5. 核心数据流

### 5.1 触发 → 调度（主链路）

```
① 定时触发   scheduler: Cron 扫描（秒级 tick）
   手动触发   server: POST /tasks
        │
        ▼
② 并发检查   ConcurrencyGuard: 查 workflow.maxParallelRuns
        │    超限 → 按策略（跳过+告警 / 排队 / 并行）
        ▼
③ 建任务实例  INSERT task (status=PENDING) + 快照 variableSnapshot
        │    绑定 workflowVersion（冻结快照）
        ▼
④ DAG 推进   scheduler: 计算入度为 0 的步骤 → 创建 taskStep(等待依赖)
        │    依赖满足 → 状态转「等待资源」→ 入 Redis 就绪队列 ZSet
        ▼
⑤ 出队+匹配  按优先级 ZSet 出队 → 队列并发检查 → 节点选择策略
        │    节点选择：运行任务最少 → 剩余CPU最多 → 最早分配
        ▼
⑥ 下发执行   Agent(或 SSH/WinRM) → 生成命令（注入参数/平台变量）→ 启动进程
        │    taskStep: RUNNING；task: RUNNING
        ▼
⑦ 采集回传   日志流（WebSocket）· 心跳（15s）· 退出码 · 资源峰值 · 输出变量
        │
        ▼
⑧ 收敛      成功/失败 → 释放互斥锁 → 推进后继步骤 or 按失败策略处理
        │    全部步骤结束 → task 终态 → 审计留痕（traceId 贯穿）
        ▼
⑨ 聚合刷新   工作台 / 任务列表缓存失效 → 前端轮询取新值
```

### 5.2 失败与重试链路

```
步骤失败
  ├─ 退出码非 0（默认失败）
  ├─ 超时 → 终止进程 → TIMEOUT
  └─ 节点失联 → 「等待执行节点恢复」保留 5 分钟窗口
        ├─ 节点恢复 → 继续执行
        └─ 窗口超时 → FAILED（原因：执行节点失联）
  │
  ▼
按 step.failureStrategy 处理
  ├─ RETRY：重试 retryCount 次（间隔 retryIntervalSeconds），记入 retryHistory[]
  └─ TERMINATE：终止整个任务；或按工作流配置「重跑失败步骤」
```
