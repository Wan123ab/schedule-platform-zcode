## 1. 实施策略

### 1.1 三条原则

| # | 原则 | 具体含义 |
|---|---|---|
| P1 | **纵切优先于横切** | 不做「先全部建表 → 再全部写接口 → 再全部做前端」。按**业务闭环**切：第一个里程碑就交付「能提交一个任务并看到日志」的端到端通路 |
| P2 | **契约先行** | 每个里程碑开工前，接口契约（`07` + CONTRACT-API）必须先冻结；冻结后变更需走「变更记录 + 双方确认」 |
| P3 | **可运行即交付** | 每个里程碑结束时系统处于**可演示、可试点**状态，不留「半成品分支」 |

### 1.2 为什么不按「先基础设施→再业务」排

工作流调度平台的**技术风险集中在调度内核与状态机**，而非 CRUD。如果先花 2 个月做完全部 CRUD，再做调度，风险会在最晚期才暴露且无法返工。

因此第一个里程碑（M1）就以「最小可用调度闭环」为目标：**一个硬编码工作流 → 提交任务 → 调度到节点 → 执行 → 采集日志 → 状态回写**。这条通路打通后，其余全是「往骨架上挂肉」。

### M1 · 最小调度闭环（**技术风险最高的里程碑**）

**目标**：把最不确定的部分先做出来。

**交付物**：

| 模块 | 内容 |
|---|---|
| 调度内核 | `06` 的状态机（任务 9 态 + 步骤 11 态）、单线程 tick、Redis ZSet 就绪队列、`ConcurrencyGuard`、`NodeMatcher` 三级排序、DAG 推进、心跳与超时扫描、选主与恢复 |
| 执行器 | SSH 连接（凭据解密 → 建立连接 → 命令下发 → 流式读取 stdout/stderr → 退出码） |
| 日志链路 | 日志采集 → Redis Stream 缓存 → WebSocket 推送（offset 续传）→ 落 `task_log` 分区表 |
| 最小接口 | `POST /tasks`（硬编码工作流）、`GET /tasks/{id}`、`GET /tasks/{id}/steps`、日志 WebSocket |
| 最小前端 | 一个任务详情页（DAG 只读 + 日志窗口），不做编辑器 |

**完成定义（DoD）**：

1. **端到端**：提交一个 3 步骤串行工作流 → 派发到真实节点 → 执行 → 日志实时显示 → 任务状态变 `SUCCESS`
2. **失败路径**：步骤返回非 0 → 按 `failureStrategy` 处理 → 状态正确、失败原因结构化写入
3. **并发闸门**：设 `maxParallelRuns=1`，连续提交 2 次 → 第二个按策略排队或拒绝（`40901`/`40902`）
4. **选主恢复**：`kill -9` 调度器 → 备进程 **≤ 45s** 接管（N-2，v3 修订：Redisson 看门狗 TTL 30s + 恢复 < 5s，原写 ≤30s 无法达成）→ 原运行中任务的步骤不误判失败
   > ⚠️ 前置条件：**scheduler 必须常备 2 副本**（`08 §2.3`）。单副本时崩溃后要等编排层拉起容器，本条在物理上不成立。
5. **重启恢复**：重启 scheduler → 从 PG 重建队列 → 任务状态 0 丢失（N-3）
6. **幂等 tick**：人为制造重复 tick → 不产生重复派发（`06 §3.3`）
7. 单测覆盖：状态机、队列 CAS、节点匹配打分为**重点覆盖对象**（目标行覆盖 ≥ 70%）

**风险（高）**：

| 风险 | 影响 | 缓解 |
|---|---|---|
| 调度内核设计缺陷 | 后期返工成本极高 | M1 期间就做混沌测试（kill 进程、断网、时钟偏移） |
| SSH 流式读取的编码/粘包问题 | 日志错乱 | 明确按行 + 超长行截断策略；用真实算子验证（含中文输出） |
| WebSocket 在企业网络被阻断 | 日志不可用 | M1 就实现 HTTP 降级通道（`07 §7.5`），并早测 |
| 选主脑裂 | 重复派发 | **Redisson 锁 + CAS**（`06 §10.1`）；**M1 必须完成时钟一致性检查**（v3：原写「租约表 + 06 §16」，两者均不存在） |

## 4. 测试策略

### 4.1 分层与配比

| 层次 | 范围 | 工具 | 覆盖目标 |
|---|---|---|---|
| 单元测试 | 状态机、变量解析、DAG 校验、节点匹配打分、`ConcurrencyGuard`、错误码 | JUnit 5 + AssertJ | **核心域 ≥ 75%** 行覆盖 |
| 集成测试 | Repository + 事务 + 分区表行为 | Testcontainers（PG + Redis） | 关键 SQL 全覆盖 |
| 接口测试 | 全部 83 端点 + 错误码矩阵 | REST Assured / MockMvc | 每端点至少：正常 + 1 个错误路径 |
| 权限测试 | 45 权限点 × 6 角色 × DataScope | 参数化测试 | **矩阵遍历**（§20.1-6） |
| 前端单测 | composable、store、工具函数 | Vitest | ≥ 60% |
| E2E | 核心业务闭环（6 条主链路） | Playwright | 主链路 100% |
| 混沌测试 | 调度器崩溃、Redis 抖动、节点断网、时钟偏移 | 自研脚本 | 6 个场景（`08 §5.1`） |
| 性能测试 | N-5/N-6/N-7/N-9/N-10 | k6 / JMeter | 达标即通过 |

**6 条 E2E 主链路**：

1. 登录 → 创建项目 → 加成员 → 切项目（权限隔离验证）
2. 建集群 → 加节点 → 绑定凭据 → 连通测试
3. 上传算子 → 配参数模板 → 试运行 → 发布
4. 编辑工作流（含变量引用）→ 校验 → 发布 → 手动触发 → 成功
5. 定时触发 → 自动运行 → 失败 → 告警 → 重跑失败步骤 → 成功
6. 回填：preview → 冲突提示 → 提交 → 暂停 → 继续 → 采集进度

### 4.2 测试数据与环境保护

| 项 | 约定 |
|---|---|
| 命名隔离 | 测试数据统一前缀 `_test_`，便于清理 |
| 事务回滚 | 单元/集成测试默认回滚；E2E 用独立 schema |
| 环境 | `dev`（本地）→ `test`（CI/联调）→ `uat`（试点前）→ `prod` |
| 真实节点 | `test` 环境接 2 台真实 Linux 节点（不能只用 mock——SSH 与日志是风险点） |
| 数据脱敏 | `uat` 环境使用真实结构 + 脱敏数据 |

### 6.1.1 API 接入排期（v0.2d 并行子轨）

> **并行策略**：API 接入是独立子轨，不与 M5 审计/健康页争人力。由 **1 名后端 + 1 名前端**并行承担，从 M5 第 2 周启动（M4 结束后即可开工，Webhook 推送引擎依赖 M4 告警渠道基础设施），M5 结束时交付。

| 周 | 后端（1 人） | 前端（1 人） |

| W1 | 4 张新表 Flyway DDL + API Key CRUD（SHA-256/作用域/限流令牌桶） | 第 20 页骨架 + API Keys 列表 + 创建弹窗（一次性明文展示） |
| W2 | `/openapi/v1` 四端点 + ConcurrencyGuard 接入 + 幂等键强制 | 接入文档页（curl 示例 + 错误码表）+ 调用记录表 |

| 联调 | 端到端联调 + 安全测试（越权/限流/幂等/重放） + 混沌测试（Key 服务不可用/Redis 抖动） | ← 同左 |
