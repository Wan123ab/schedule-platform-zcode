# 10 · 编码规范与注释约定

> **来源**：项目负责人 2026-10-06 提出的四条代码要求（已登记决策 D-26，见 docs/00 §2）。
> **定位**：本文件是全部前后端代码的**风格与注释约定**，Code Review 以此为验收清单。
> **效力**：新增代码必须遵守；存量代码在触碰时逐步向此对齐（不做一次性无意义重写）。

---

## 1. 四条原则（D-26）

| # | 原则 | 一句话解释 | 反例（禁止） |
|---|---|---|---|
| 1 | **优雅如诗** | 代码表达的是意图，不是操作步骤；读起来像在描述业务，而不是在描述机器 | 一眼看不出在做什么的长方法、深嵌套布尔表达式 |
| 2 | **能复用就复用，能封装就封装** | 同一知识只写一处（DRY）；变化的方向封装成边界（接口/组件/函数） | 复制粘贴一小段逻辑改两个字母；跨层直接摸内部字段 |
| 3 | **必要的注释 + 设计思路说明** | 注释写「为什么」与「约束」，不写「下一行在做什么」；公开单元必须有意图说明 | `// 遍历列表` 这类复述代码的注释；零注释的公共类 |
| 4 | **前端注释尤其重要** | 前端代码同时承担「教学」职责：注释要讲清 Vue/TS 机制本身，让不熟悉前端的读者能看懂 | 只写业务不写机制的注释；炫技式语法无解释 |

> 原则 1 与 2 的张力：**不要为了复用而复用**。两段相似但变化原因不同的代码，重复好过错误的抽象（宁可第二写，不可第一抽象——Rule of Three）。

## 2. 注释的三个层次（全栈统一）

| 层次 | 写什么 | 放哪 | 示例 |
|---|---|---|---|
| **意图层** | 这个单元为什么存在、设计取舍是什么 | 类/组件/模块顶部 | 「为什么主循环单线程：调度决策需要队列/资源/并发的一致视图」 |
| **约束层** | 什么条件下这段代码会出错、不变式是什么 | 易错点行内 | 「⚠️ version 不是可选项：调度器 CAS 更新依赖它」 |
| **指路层** | 规范出处、关联决策、TODO 的去处 | 关键位置 | 「依据：docs/06 §4.6（D-23）」 |

**禁止**：复述代码的注释（`// 设置用户名`）、过时注释（改代码必须同步注释）、注释掉的死代码（要历史去 git 找）。

**引用文档的格式**：注释里引用规范一律带出处编号（`docs/06 §4.6`、`PRD §12.3`、`D-23`），保证可反查。

## 3. 后端细则（Java 21 / Spring Boot 3.3）

| 项 | 约定 |
|---|---|
| 方法长度 | 一屏内（≈40 行）为佳；超长的第一反应是**提取有名字的私有方法**，让主流程读起来像目录 |
| 命名 | 类名名词、方法名动词；布尔用 `is/has/can` 前缀；禁止 `data2`、`handle` 这类无信息名 |
| 异常 | 业务失败抛 `BizException(ErrorCode)`；禁止吞异常；捕获后必须要么处理要么带上下文重抛 |
| 复用 | 跨域逻辑进 `flowops-common`；实体/Mapper 进 `flowops-domain`；**禁止复制粘贴域间逻辑** |
| 封装 | 横切关注点（鉴权/审计/幂等/traceId）只允许以注解 + 切面/过滤器的形式出现，业务代码不得手写 |
| 状态更新 | 一律 CAS（`UPDATE ... WHERE status = :expected AND version = :v`，docs/03 §3.4） |
| 枚举 | 四注解模式（docs/07 §3.5）；新增枚举值先改 docs/05 CHECK 再改代码 |
| 注释 | 公开类必须有意图层注释（含设计依据出处）；公共 API 方法说明语义与失败行为 |

## 4. 前端细则（Vue 3 + TS）—— 教学优先

**给不熟悉前端的读者**：前端代码的注释额外承担讲清机制的责任。以下机制在使用处必须就地解释（一两句即可，不求系统教程）：

| 机制 | 注释要讲清什么 |
|---|---|
| `<script setup>` | 这是 Vue 3 的组合式写法：顶层变量/函数直接就是模板可用项 |
| `ref / reactive / computed` | 响应式数据：值变了，用到它的模板自动更新；computed 是「由其他值推导出的值」且自带缓存 |
| `defineProps / defineEmits` | 组件的入参（props 向下传数据）与事件（emit 向上报动作） |
| Pinia store | 跨页面共享的少数状态（登录态/主题/当前项目）；**列表与详情数据不进 store**，用 useRequest 局部管理 |
| 路由守卫 | `beforeEach` 在每次跳转前运行，是权限与登录检查的唯一入口 |
| axios 拦截器 | 请求/响应的「统一关卡」：token 注入、键名转换、错误分流都在这里，业务代码不重复处理 |
| TS 泛型/联合类型 | `Record<TaskStatus, Tone>` 这类写法为什么能防漏项（缺一项编译失败） |

| 项 | 约定 |
|---|---|
| 视觉 | 只准引用 `styles/tokens.css` 令牌（F-2）；组件内出现十六进制色值即违规 |
| 结构 | 同一段模板结构出现第二次必须抽组件（F-4） |
| 枚举 | 标签/颜色只能来自 `useDict` / `types/enums.ts` 映射表（F-5） |
| 权限 | 一律取 `constants/permissions.ts` 常量，禁止字面量 |
| 请求 | 只有 `api/modules/*.ts` 可以 import `http.ts`（F-1）；视图不直接发请求 |
| 组件命名 | 多词名（`StatusTag` 而非 `Tag`）；业务组件 `biz/`，通用基础件 `base/` |

## 5. Review 清单（PR 自检）

1. 有没有「一眼看不出意图」的方法？→ 提取命名方法
2. 同一知识是否出现在两处？→ 抽公共（先确认两处变化原因相同）
3. 公开单元有没有意图层注释与出处引用？
4. 前端新用到的 Vue/TS 机制有没有就地注释？
5. 是否引入了新依赖？→ 先在 docs/02 补选型记录
6. 有没有绕过横切层（手写鉴权/审计/键名转换）？
7. 状态更新是否走 CAS 与统一响应包？
