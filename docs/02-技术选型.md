## 1. 后端技术栈

### 1.1 语言与框架：Java 21 + Spring Boot 3.3

**选它**：
- 团队既有 das-fly / yndky 均为 Java + Spring Boot，**人力零学习成本**；
- Java 21 的**虚拟线程（Virtual Threads）**对「大量执行节点心跳 + 日志流 + 轮询」这类高并发 IO 场景收益明显，可显著提升单机吞吐；
- Spring Boot 3 生态：Actuator（健康检查）、Validation、WebSocket、Scheduling 齐备。

**否掉了什么**：

| 候选 | 否掉理由 |
|---|---|
| Go（gin/kratos） | 调度器性能与部署简洁性确实更好，但**团队栈不符**，双语言维护成本高；调度瓶颈在本系统中主要是 DB 与 IO 等待，而非语言 |
| Node.js / NestJS | 与前端同语言便于共享类型，但 CPU 密集（DAG 计算、日志解析）与生态不适合核心调度 |
| Python（FastAPI） | 开发快，但调度器需要长期稳定运行与高并发，GIL 与部署运维不如 JVM 稳妥 |

**版本锁定**：

```xml
<java.version>21</java.version>
<spring-boot.version>3.3.4</spring-boot.version>
```

### 1.2 数据库：PostgreSQL 16

**选它**：
- **JSONB** 完美承载本系统大量「快照类」字段（`variableSnapshot`、`dagDefinition`、`condition`、`envVars`、`outputDeclarations`）——既保留结构，又不必为每种形态建表；
- **强一致性 + 事务** 是调度状态机的底线（并发检查、状态流转必须可靠）；
- **原生分区表**（`task`/`taskStep`/日志表按时间分区）应对数据增长；
- **窗口函数** 便于「资源画像 Top N」「趋势统计」类查询；
- 已在 yndky 项目中使用，团队熟悉。

**否掉了什么**：

| 候选 | 否掉理由 |
|---|---|
| MySQL 8 | 亦可胜任，但 JSON 能力弱于 PG（本系统快照字段多），分区与 CTE 特性也逊色 |
| MongoDB | 快照字段友好，但**调度状态需要强事务**，且审计/权限关系模型是典型关系型 |
| 达梦/人大金仓等信创库 | 若客户有信创要求需专项评估（PG 兼容度较高，可作备选），**本方案以 PG 为基线** |

**关键表设计原则**（详见 05）：
- 快照类字段用 `jsonb`；
- `task_log` **按日**分区（`log_time`）；`audit_log` **按月**分区；`task` / `task_step` **一期单表**，达到阈值（`task` > 5000 万行）后再分区——**以 `05 §7.1` 为准**；
  > v3 评审：此处原写「`task` / `task_step` / `audit_log` / 日志表按月分区」，与 `05 §7.1` 不符，并导致 `08 §4.2` 的「年度 DROP PARTITION 清理」在一期无分区可操作。
- 所有枚举用 `varchar + CHECK` 或 `smallint + 字典表`（团队约定为 `varchar` 便于排查）。

### 1.3 缓存与队列：Redis 7

**一物五用**（v3 评审：原标题写「三用」，但表格实际列了 5 项）：

| 用途 | 数据结构 | 说明 |
|---|---|---|
| 就绪队列（D-13） | **ZSet**（score=优先级+时间） | 天然支持「优先级降序 + 同优先级 FIFO」，出队时重新评估；插队 = 改 score |
| 分布式锁 | **Redisson**（或 SET NX + Lua） | 并发检查、互斥锁 `mutexGroup`、调度器选主 |
| 心跳与在线态 | **Hash / String + TTL** | 15s 上报，45s 无心跳判离线 |
| 会话 | **String + TTL** | Sa-Token 集成 |
| 日志实时推送 | **Pub/Sub** | WebSocket 通道 |

**为什么队列不用 MQ（RabbitMQ / Kafka）？**

| 考量 | 结论 |
|---|---|
| 本系统队列需要「按优先级 + 时间排序取」 | ZSet 精确匹配；MQ 的优先级队列能力弱（RabbitMQ 仅 10 级、Kafka 不支持） |
| 需要「出队时重新评估」 | MQ 消息出队即定序，无法重排；ZSet 可随时重排 |
| 需要「等待资源」状态挂起再放回 | ZSet 天然支持 remove/re-add |
| 运维复杂度 | 少一个中间件（一期） |

> **演进预留**：若未来任务量级需要削峰解耦，可在「任务完成事件 → 告警/审计」这条**旁路**上引入 Kafka，主调度链路仍用 Redis ZSet + PG。

### 1.4 ORM：MyBatis-Plus 3.5

**选它**：复杂调度查询（多表 join + 动态条件 + 分页 + 分区裁剪）用 MyBatis 手写 SQL 最可控；Plus 提供的 CRUD 与分页插件减少样板代码。

**否掉 JPA/Hibernate**：隐式行为多（懒加载、脏检查、N+1），在**高频状态更新 + 复杂组合查询**场景下容易出性能事故且难排查。

### 1.5 会话认证：Sa-Token 1.39.0

**选它**：与 das-fly / yndky 完全一致，团队熟悉；配置范式已沉淀。

**锁定配置**（与既有项目对齐）：

```yaml
sa-token:
  token-name: Authorization
  token-prefix: Bearer
  token-style: uuid
  timeout: 604800          # 7 天（对应 rememberMe）
  is-concurrent: false     # 单端登录（可配置）
  is-share: false
  login-type: flowops      # ⚠️ 必须独立，避免与 das-fly / yndky 会话串号
```

> **ADR-003 延续**：即便共用同一 Redis 实例，也必须使用独立 `loginType` 与独立 key 前缀，保证登录态互不影响。

### 1.6 数据库迁移：Flyway 10

**选它**：DDL 以 SQL 文件版本化，**可评审、可回滚、可追溯**——本系统表结构复杂（30+ 表），必须避免「人肉改库」。

**约定**：
- 命名 `V{版本}__{描述}.sql`，如 `V001__init_schema.sql`；
- **生产环境禁止 `flyway clean`**；
- 每个变更脚本必须在 test 环境跑通后才进 prod。

### 1.7 参数校验与错误处理

| 项 | 选型 | 说明 |
|---|---|---|
| 校验 | **Jakarta Validation** (`@Valid` + 自定义注解) | 统一在 Controller 层拦截 |
| 统一响应 | 复用 `com.das.fly.common.api` 约定（`code/message/data/traceId`） | 见 CONTRACT §0.2 |
| 异常 | `@RestControllerAdvice` 全局处理 | 业务异常 → 错误码；系统异常 → 50000 + traceId |
| 幂等 | Redis + 请求指纹 | 回填提交、任务重复提交 |

### 1.8 可观测性

| 项 | 选型 | 说明 |
|---|---|---|
| 日志 | **Logback + JSON encoder** | 结构化日志，含 traceId |
| 链路追踪 | **Micrometer Tracing (+ traceId 贯穿)** | 与审计 `traceId` 同一标识 |
| 指标 | **Micrometer + Prometheus** | 调度队列深度、任务成功率、节点在线数 |
| 健康检查 | **Actuator** | `/actuator/health` 供 Nginx/编排探活 |
| 慢 SQL | **p6spy**（dev/test）+ PG `pg_stat_statements`（prod） | 定位调度查询性能问题 |
| **调度决策留痕** | **PG 表 `schedule_decision_log`**（非日志） | 每次调度决策（DISPATCHED/DEFERRED/BLOCKED/SKIPPED）写入结构化的输入与结果，供「调度诊断」面板查询（PRD §15.5-2 / `08 §3.4` / `05 §3.5`）；**不走日志文件**——日志无法按任务聚合查询 |

> **v3 评审补充**：一期不做全链路 APM，但**调度决策必须结构化留痕**（`schedule_decision_log`）。调度是"为什么这个任务还没跑"这类问题的核心场景，靠日志文本检索无法回答。这与一期不做 APM 并不矛盾：APM 解决"慢在哪"，决策日志解决"为什么没跑"。

### 1.9 调度内核相关：自研 + Quartz 仅取 Cron 解析

**核心决策 D-02：自研调度内核，不基于 XXL-JOB / PowerJob 二开。**

| 方案 | 优势 | 否掉理由 |
|---|---|---|
| **自研** ✅ | 完全贴合 PRD §12 算法定义；无框架概念阻抗 | 需自己实现调度循环、容错、选主 |
| XXL-JOB 二开 | 调度中心 + 执行器成熟，运维界面现成 | 其模型是**「任务 → 执行器分片」**，无 DAG、无队列优先级、无资源约束、无节点标签；要改造成本高于自研 |
| PowerJob 二开 | 支持工作流（DAG）、有 MapReduce 思想 | 工作流是「内嵌脚本/处理器」模型，与「算子文件 + 参数模板 + 输出声明」差异大；并发/互斥语义需大改 |
| Quartz 直接做调度 | Cron 解析成熟 | Quartz 只解决「按时间触发」，不解决队列/资源/依赖推进 |

**复用边界**：
- ✅ **Cron 表达式解析**：可用 `cron-utils`（或 Quartz 的 `CronExpression`）——纯计算，无需自己写；
- ❌ 不用 Quartz 的 JobStore / 集群调度（其 DB 锁机制与本系统的调度模型冲突）。

**自研范围**（详见 06）：
1. 触发扫描器（Cron tick）
2. DAG 推进器（依赖计算）
3. 就绪队列管理（Redis ZSet）
4. 资源匹配器（节点选择策略）
5. 并发/互斥控制器
6. 心跳与离线判定
7. 超时与失败重试

## 2. 前端技术栈

### 2.1 Vue 3 + TypeScript + Vite

**选它**：团队主栈（yndky 项目同栈）；Vite 冷启动与 HMR 快；TS 让接口契约类型化，**大幅降低联调期的字段错配成本**。

**否掉 React**：生态同样成熟，但与团队栈不符；原型设计系统（深空控制台）为自绘 CSS，框架差异对视觉落地影响不大，故以**团队熟练度**为决策依据。

### 2.2 UI 组件库：Element Plus（**按需 + 变量覆盖**）

**关键判断**：原型是**高度定制的深空控制台**（五级明度背景、发光状态、等宽数字），不是 Element 默认视觉。

**落地策略**：
1. **按需引入**（`unplugin-vue-components`）控体积；
2. **深度覆盖 CSS 变量**：把 DESIGN-01 的令牌映射到 Element 变量

   ```scss
   :root {
     --el-color-primary: var(--pri);          // #2E90FA
     --el-bg-color: var(--bg-panel);
     --el-text-color-primary: var(--t1);
     --el-border-radius-base: var(--r-sm);
     // ...
   }
   ```
3. **复杂组件自绘**：表格（sticky 列 + 状态发光）、DAG 画布、日志查看器——这些 Element 无法满足，直接按原型实现；
4. **禁止**在业务代码里写硬编码颜色（沿用 DESIGN-01 §9.4 负面清单）。

**否掉**：
- Ant Design Vue：视觉改造量与 Element 相当，但 Element Plus 在团队中使用更广；
- 纯自绘（不用组件库）：表单/弹窗/日期选择器重复造轮子成本过高。

### 2.3 状态管理：Pinia

按**域**划分 store（与后端六域对齐）：`useAuthStore` / `useProjectStore` / `useTaskStore` 等。
> 约定：**服务端数据不长期驻留 store**（避免陈旧），列表/详情以「请求即刷新」为主，store 只存跨页共享的轻量态（当前用户、当前项目、主题）。

### 2.4 请求层：Axios 封装

统一拦截器处理：

| 拦截器 | 职责 |
|---|---|
| 请求 | 注入 `Authorization`；注入 `traceId`（UUID）；当前项目上下文 |
| 响应 | 解包统一响应（`code!==0` 抛业务异常）；`40100` → 跳登录；`40101` → 渲染锁定倒计时；`40300` → 无权限态 |
| 错误 | 统一 toast + 错误码文案映射 |

**类型化**：按 `CONTRACT-API.md` 生成 `types/api.d.ts`，接口返回值全部强类型。

### 2.5 实时通道

| 场景 | 方案 |
|---|---|
| 任务日志 | **WebSocket**（`/ws/tasks/{taskId}/steps/{stepId}/logs?offset=`）；断线重连按 offset 续传 |
| 列表/看板 | **轮询** 5–10s（带 `If-None-Match` 之类的轻量优化可选） |
| 任务状态 | 轮询（详情页 3s） |

> 为什么不全部 WebSocket？列表页的实时性要求低，轮询实现简单、易排查；日志量大且要求 ≤5s，必须 WebSocket。

### 2.6 图表：ECharts

工作台趋势图、资源占用、集群健康分布。**按需引入**（`echarts/core` + 具体图表）控体积。
> 与原型的关系：原型是内联 SVG 手绘；正式实现用 ECharts 以支持交互与大数据量。

### 2.7 Mock：MSW（联调后退役）

**阶段策略**（与 yndky 项目一致的经验）：

| 阶段 | Mock 状态 |
|---|---|
| 前端先行开发 | **MSW 全量 mock**（按 CONTRACT-API 契约），前后端并行 |
| 联调期 | **逐域切换真实接口**，MSW 保留未完成域 |
| 联调完成 | **MSW 退役**（保留为单测/Storybook 用） |

## 3. 工程规范

### 3.1 后端工程规范

| 项 | 约定 |
|---|---|
| 构建 | **Maven**（与既有项目一致，Maven 3.9.9） |

### 3.3 统一线协议约定（D-05）

| 层 | 风格 | 例 |
|---|---|---|
| 前端 TS | camelCase | `folderId` |
| 后端 Java | camelCase | `folderId` |
| **HTTP JSON（线协议）** | **snake_case** | `folder_id` |

**实现方式**（Java 侧全局配置，**不用局部 Converter 类**）：

```java
// Jackson 全局命名策略
@Bean
public Jackson2ObjectMapperBuilderCustomizer snakeCaseCustomizer() {
    return builder -> builder
        .propertyNamingStrategy(PropertyNamingStrategies.SNAKE_CASE)
        .serializationInclusion(JsonInclude.Include.NON_NULL);
}
```

> ⚠️ **注意**：DB 列名同样用 snake_case（PG 惯例），故 MyBatis-Plus 的 `map-underscore-to-camel-case=true` 保持开启，**三段风格自动对齐**：
> `DB(snake) ←→ Java(camel) ←→ JSON(snake)`

**前端 Axios 侧**（D-15，**以 `04 §4.4` 为准**）：

- 请求出口 `deepSnake`、响应入口 `deepCamel`，转换**只在 axios 拦截器一处**发生；
- TS 类型（`api/types/*`）与业务代码**全 camelCase**，不按 snake_case 书写。

> **v3 评审修订**：本节原写「前端 Axios 侧不做键名转换、TS 类型按 snake_case 书写」，与 `04 §4.4` 的 D-15 及 `00 §2` 记录的 D-15 冲突。**以 `04 §4.4` 为准**（TS 类型必须与运行时一致，否则静态检查对 `Record`/解构一类的场景全部失效）；`07 §3.1` 的效果矩阵也与之呼应。
>
> 「不引入双向转换库」这个**初衷仍然成立**——`deepCamel` / `deepSnake` 是 `04 §4.4` 里两个合计不到 10 行的纯函数，不是第三方库，不存在"隐性 bug"的来源。真正要避免的是**散落在业务代码里的逐字段转换**，而拦截器方案恰好把转换收敛到了唯一一处。

## 4. 选型补充说明

### 4.1 为什么不用微服务

**判断**：本系统虽模块多，但**模块间耦合度高**（任务强依赖工作流版本、工作流强依赖算子、所有域都写审计），且团队规模有限。

**一期采用「模块化单体 + 独立调度进程」**：
- server 内部按六域分模块，**边界清晰、可独立演进**；
- 但**同进程部署**，避免分布式事务与跨服务调试成本；
- 调度器拆出（见 01 §4.1）解决了「多副本重复调度」这个真正的问题。

**演进预留**：若未来某域（如日志服务）压力显著，可单独拆出，因为模块边界已经清晰。

### 4.2 为什么用 Docker Compose 而非直接 K8s

一期交付目标是**可上线、可运维、可交接**，而非弹性伸缩。Docker Compose：
- 部署简单（一条命令）；
- 依赖清晰（镜像 + 编排文件即全部交付物）；
- 团队无需 K8s 运维能力。

**但**：镜像构建、健康检查、配置外置（env/卷）均按 K8s 可迁移的方式设计，未来上 K8s 无需重构。

> **v3 评审补充（部署约定）**：**单活组件的副本数 = 2**（一主一备）。调度器是单活组件（`01 §6.1`：scheduler 单活，另一副本待选主），若只部署 1 副本，进程崩溃后要靠编排层重新拉起容器（数十秒~数分钟），`08` 的 N-2（切换 ≤45s）与 99.9% 可用性在物理上无法达成。**两个副本竞争同一把锁，实际只有 1 个活跃**（`06 §10.1`），多副本不会导致重复调度。该约定在 compose 与 K8s 下一致。
