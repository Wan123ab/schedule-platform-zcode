## 3. 传输层规范

### 3.1 序列化（D-05 的落地形式）

**目标**：数据库 `snake_case` ↔ Java 属性 `camelCase` ↔ 线协议 `snake_case`，三段自动对齐，**不写任何局部 Converter**。

```yaml
# application.yml —— 全局配置，一处生效
spring:
  jackson:
    property-naming-strategy: SNAKE_CASE      # Java camelCase ⇄ JSON snake_case
    default-property-inclusion: non_null       # null 字段不下发（减小报文）
    date-format: yyyy-MM-dd HH:mm:ss
    time-zone: GMT+8
    serialization:
      write-dates-as-timestamps: false
      fail-on-empty-beans: false
    deserialization:
      fail-on-unknown-properties: false        # 前后端版本漂移时向前兼容
```

**MyBatis-Plus 侧**（DB snake ↔ Java camel）：

```yaml
mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true         # 默认已是 true，显式声明防误改
  global-config:
    db-config:
      table-underline: true
```

**效果矩阵**：

| 层 | 命名 | 示例 |
|---|---|---|
| PostgreSQL 列 | snake_case | `workflow_id`, `created_at` |
| Java 字段 | camelCase | `workflowId`, `createdAt` |
| JSON 线协议 | snake_case | `"workflow_id"`, `"created_at"` |
| TypeScript | camelCase（`interface`） | `workflowId: string` |
| TS 边界转换 | 仅在 axios 拦截器 | `04 §4.4`（D-15） |

**⚠️ 三个必须小心的地方**：

1. **`@JsonProperty` 覆盖全局策略**：只在「字段名与策略冲突」时使用，例如 `OS` 类型需要序列化成 `"os"` 而非 `"o_s"`（SNAKE_CASE 策略会把连续大写字母拆开）。这类字段单独标注并在 §3.2 登记。
2. **`Map<String,Object>` 不受命名策略影响**：`data` 里的动态结构（`condition` JSON、`dag_definition`）原样透传，前端不得假设其键名大小写。凡跨端消费的动态结构，**键名一律 snake_case 并在契约里显式声明**。
3. **枚举值的序列化不走命名策略**：`@JsonValue` 显式指定，见 §3.5。

### 3.2 需 `@JsonProperty` 特判的字段（白名单）

| Java 字段 | 默认策略产出 | 期望线协议 | 处理 |
|---|---|---|---|
| `osType` | `os_type` ✅ | `os_type` | 无需特判 |
| `cpuUsed` | `cpu_used` ✅ | `cpu_used` | 无需特判 |
| `gpuTotal` | `gpu_total` ✅ | `gpu_total` | 无需特判 |
| `ipAddress` | `ip_address` ✅ | `ip_address` | 无需特判 |
| `maxParallelRuns` | `max_parallel_runs` ✅ | `max_parallel_runs` | 无需特判 |
| `vmId` | `vm_id` ✅ | `vm_id` | 无需特判 |
| `p95LatencyMs` | `p95_latency_ms` ✅ | `p95_latency_ms` | 无需特判 |

> **结论**：当前字段清单**无需任何特判**（首字母单字母/数字开头的字段已排查完毕）。此表登记为「检查留痕」——新增字段若命中 `aB` 型缩写模式（如 `xAxis`→`x_axis`，符合预期，无需特判；但 `s3Bucket`→`s3_bucket`，符合预期），仍按本节流程核对一次即可。

### 3.3 统一响应包（回写 F-01）

```json
{
  "code": 0,
  "message": "ok",
  "data": { },
  "trace_id": "0af7651916cd43dd8448eb211c80319c"
}
```

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `code` | int | 否 | `0` = 成功；非 0 见 §4 |
| `message` | string | 否 | 面向开发者的摘要（**非**用户提示文案；用户文案由前端按 `code` 映射，见 §4.3） |
| `data` | object/array/null | 是 | 业务载荷；`default-property-inclusion: non_null` 下失败响应不含该键 |
| `trace_id` | string | 否 | 32 位小写 hex（**无连字符**，对齐 W3C Trace Context 的 `trace-id` 规范） |

**Java 定义**（复用既有 `com.das.fly.common.api` 结构，字段名保持 camelCase，序列化交给全局策略）：

```java
public class ApiResult<T> {
    private int code;
    private String message;
    private T data;
    private String traceId;      // → trace_id

    public static <T> ApiResult<T> ok(T data) { ... }
    public static <T> ApiResult<T> fail(ErrorCode ec) { ... }
}
```

**分页结构**：

```json
{
  "code": 0, "message": "ok",
  "data": {
    "total": 1284, "page": 2, "page_size": 20,
    "records": [ ]
  },
  "trace_id": "..."
}
```

**⚠️ 与 `04` 的差异说明**：`04 §4.3` 中 `ApiResult` 类型写成 `{ code, message, data, trace_id }`，与此一致。原 CONTRACT-API 的 `pageSize` 按 D-05 应为 `page_size`——**这是第 9 处回写项**，一并登记到 §12。

### 3.4 请求约定

| 项 | 约定 |
|---|---|
| Base URL | `/api/v1` |
| Content-Type | `application/json; charset=utf-8`（文件上传 `multipart/form-data`） |
| 认证头 | `Authorization: Bearer {uuid-token}` |
| 追踪头 | `X-Trace-Id`（可选，客户端传入则沿用；不传由服务端生成） |
| 项目上下文 | `X-Project-Id`（可选，**仅作提示，不作为授权依据** —— 授权只看服务端会话中的数据范围） |
| 幂等键 | `Idempotency-Key`（见 §7.2，写操作建议携带） |
| 时间格式 | 入参出参一律 `yyyy-MM-dd HH:mm:ss`（**绝对时间**，不返回「3 分钟前」；相对时间由前端渲染） |
| 日期（业务日期） | `yyyy-MM-dd`（`.bizDate` 类字段） |
| 布尔 | 真布尔 `true/false`，**不用 0/1** |
| 金额/百分比 | 百分比用 0–100 的数值（非 0–1 小数），字段名带单位后缀（如 **`success_rate`**） |
| 分页 | `page`（1 起）+ `page_size`（默认 20，上限 200，超限 `40001`） |
| 排序 | `order_by` + `order_dir(ASC/DESC)`；**白名单校验**，非白名单字段 `40001`；默认 `created_at DESC`。白名单**必须在 Controller 方法上用 `@Sortable({...})` 声明**（AOP 读取该注解校验），禁止在 service 里零散 `if` 判断，否则白名单会散落各处、漏配无法被发现 |
| 空值语义 | 请求中省略 = 不修改；显式 `null` = 置空（`PUT` 部分更新场景） |

### 3.5 枚举规范（四要素，实体层与协议层一致）

所有枚举必须有：**持久化值（`@EnumValue`）+ 线协议值（`@JsonValue`）+ 反序列化（`@JsonCreator`）+ 文档（`@Schema`）**。

```java
public enum TaskStatus {
    PENDING("PENDING"), SCHEDULING("SCHEDULING"), RUNNING("RUNNING"),
    STOPPING("STOPPING"),            // ← 第 9 态（M-08）
    SUCCESS("SUCCESS"), FAILED("FAILED"), STOPPED("STOPPED"),
    TIMEOUT("TIMEOUT"), PARTIAL("PARTIAL");

    @EnumValue                     // MyBatis-Plus 落库值
    @JsonValue                     // JSON 出参值
    private final String code;

    @JsonCreator                   // JSON 入参反序列化
    public static TaskStatus of(String code) { ... }
}
```

**步骤实例状态（11 态）补齐 `code`**（回写 CONTRACT-API §0.4 第 6 项）：

| 中文 | `code` | 终态 | 说明 |
|---|---|---|---|
| 未开始 | `NOT_STARTED` | ✗ | 依赖未满足 |
| 等待依赖 | `WAITING_DEPENDENCY` | ✗ | 上游步骤未成功 |
| 等待资源 | `WAITING_RESOURCE` | ✗ | 已就绪，无匹配节点/并发受限 |
| 调度中 | `SCHEDULING` | ✗ | 已选定节点，下发中 |
| 运行中 | `RUNNING` | ✗ | 节点已确认启动 |
| 成功 | `SUCCESS` | ✓ | — |
| 失败 | `FAILED` | ✓ | — |
| 重试中 | `RETRYING` | ✗ | 上次失败，等待重试 |
| 已跳过 | `SKIPPED` | ✓ | 上游失败且策略为跳过 |
| 已停止 | `STOPPED` | ✓ | 人工停止 |
| 超时 | `TIMEOUT` | ✓ | 超 `timeoutSeconds` |

> 与 `06 §2.2` 状态机一一对应，`05 §3` 的 DDL 中 `task_step.status` 的 CHECK 约束按此表写。

## 4. 错误码体系

### 4.1 编码规则（本次定案）

**五段式**：`{HTTP语义}0{域}{序号}`

```
4 0 3 0 0
│ │ │ └┴─ 序号（域内自增）
│ │ └──── 域编号（见下表）
│ └────── 保留位
└──────── HTTP 语义：4=客户端错误, 5=服务端错误
```

| 域编号 | 域 | 说明 |
|---|---|---|
| 0 | 通用 | 参数、认证、权限、资源、冲突 |
| 1 | 资产域 | 项目/集群/节点/凭据 |
| 2 | 编排域 | 算子/工作流/版本/触发器 |
| 3 | 执行域 | 任务/步骤/回填 |
| 4 | 治理域 | 告警/审计 |

> **兼容性约束**：CONTRACT-API §12 已定义的 12 个错误码**保持不变**（前后端原型已按此联调），新增码遵循上述规则并避开已占用号段。

### 4.3 前后端分流原则（`04 §4.2` 的规范侧）

| 阶段 | code 范围 | 前端处理 |
|---|---|---|
| 认证 | `40100` / `40101` / `40102` | **拦截器统一处理**：清会话跳登录 / 渲染锁定 / 顶号提示。视图层不感知 |
| 授权 | `40300` / `40301` / `40302` | 渲染权限态组件（`<NoPermission>` / 授权申请弹窗），**不弹全局错误** |
| 校验 | `40001` / `40002` / `4220x` / `4221x` | 表单/局部错误提示（`errors[]` 定位到字段） |
| 冲突 | `4090x` | 明确提示 + 提供「刷新后重试」动作 |
| 闸门 | `42231`（回填预览） | 引导回预览步骤（页面级流程修正，非错误弹窗） |
| 服务端 | `5000x` / `5030x` | 全局错误 + `trace_id` 可复制 + 重试按钮 |

**关键约定**：**用户可见文案不由后端下发**。后端 `message` 是开发者摘要（便于日志排查）；用户文案在前端 `src/utils/errorMessage.ts` 按 `code` 映射，支持 i18n 与文案迭代而不需要后端发版。

### 5.3 DataScope：与权限点正交（D-19）

**核心思想**：权限点回答「**能不能做**」，DataScope 回答「**对哪些数据做**」。两者独立组合。

```java
public enum ScopeType {
    ALL,            // 全平台（平台管理员、只读审计）
    AUTHORIZED_CLUSTER,  // 被授权集群范围（运维人员）
    PROJECT,        // 本项目（项目管理员、业务人员）
    SELF_CREATED,   // 本人提交/本人维护（算子维护者、业务人员的部分操作）
    NONE            // 无数据范围
}
```

**判定链**（`DataScopeInterceptor` 在 Mapper 层注入 SQL 条件）：

```
1. 取当前用户 + 角色
2. 取角色对应的 ScopeType（多角色取并集，宽者优先）
3. 取运维视角开关（platform:view:ops）
4. 生成 SQL 条件：
   - ALL                 → 无条件
   - AUTHORIZED_CLUSTER  → AND cluster_id IN (授权集群)
   - PROJECT             → AND project_id = 当前项目
   - SELF_CREATED        → AND (creator_id = 当前用户 OR operator_owner = 当前用户)
5. 记录到审计上下文（跨项目访问必留痕）
```

> **⭐ 2026-10-07（M2）落地口径补充**——判定链第 4 步在本轮才真正接上：
>
> - **`role.scope_type` 的取值必须与本节的 5 个命名逐字一致**。V1~V5 曾用历史命名
>   （`'CLUSTER'/'SELF'`），与 `ScopeType` 枚举永不匹配 → OPS 与 SELF 类角色被解析为 `NONE`，
>   而 `NONE` 的语义是"不过滤"，属**静默越权**。已由 **V6 迁移**修正（同时回写 `05 §3.1` 的 CHECK）。
>   这是"枚举值分布在两处就一定会漂移"的实例：**改命名必须同时改种子数据**。
> - **`AUTHORIZED_CLUSTER` 的数据来源**：`05` 全量 DDL 中没有 user→cluster 的直接授权表，
>   故本期定义为 **"该用户所属项目被授予的集群并集"**（`project_cluster ⨝ project_member`，
>   见 `ClusterMapper#findAuthorizedClusterIds`）。语义自洽且完全由现有表推导；
>   未来若引入独立集群授权表，只需替换该 SQL，解析器与拦截器零改动。
> - **注入维度与列的对应**（登记制，见 `FlowopsDataPermissionHandler`）：
>   `project` → `id`、`task/workflow/workflow_version/operator/project_member` → `project_id`；
>   `cluster` → `id`、`executor_node/queue/task/task_step` → `cluster_id`。
>   列名一律带表限定，避免 `task_step ⨝ task` 时同名 `cluster_id` 歧义。
> - **40400 与 40301 的区分**：行级过滤会让"越权"与"不存在"在查询结果上完全一样，
>   故 Service 层在取不到行时做一次**无过滤的存在性探测**（`ScopeContext.withoutScope`，
>   只取 boolean、不取数据）→ 存在则 `40301`，不存在则 `40400`（`ScopeGuard`）。
> - **外键字段的线协议口径：一律出业务编号，不出内部自增主键**（与 D-15 的"线协议只认一种命名"
>   同源：让"哪个是内部 id"这件事在网络边界上无歧义）。本轮据此调整三处：
>   `ExecutorNodeVO/SaveExecutorNodeRequest.credentialRefId(Long)` → `credentialId(CR-xxx)`、
>   `CredentialVO/SaveCredentialRequest.projectId(Long)` → `projectId(PRJ-xxx)`（VO 另加只读
>   `projectName` 便于列表直接展示）。内部 `bigint` 主键仅在实体与外键列上存在，由 Service 负责
>   翻译；翻译不到即 `40400`（"引用不存在的目标"属早失败范围）。
>   ⚠️ **遗留**：`SubmitTaskRequest.projectId` 仍是 `Long`（M1 旧口径），M3 任务域重构时一并统一。

**运维视图与业务视图的字段级差异**（PRD §11.3，**在序列化层实现**）：

### 6.1 项目停用（影响面闸门）

```
GET /projects/{projectId}/impact        → 前置统计
  data: { workflow_count, running_task_count, member_count, trigger_count, blocking[] }

PUT /projects/{projectId}/status        → 停用
  约束：running_task_count > 0 → 42203（含 blocking[] 明细，前端展示"受影响任务"清单）
```

**语义**：停用是**软停用**——不删数据、不中断运行中任务；停用后不可提交新任务、触发器自动置 `enabled=false`（并发安全）。

### 6.2 凭据：明文永不出网

| 端点 | 出参中的密钥类字段 |
|---|---|
| `GET /credentials` | `secret_fingerprint` = **仅后 4 位**（如 `****a1b2`） |
| `GET /credentials/{id}` | 同上；**永远不返回 `secret`** |
| `POST/PUT /credentials/{id}` | 入参 `secret`（write-only）；出参不含 |
| `POST /credentials/{id}/rotate` | 入参 `secret`；出参 `last_rotated_at` |

**服务端**：`secret` 经 AES-256-GCM 加密后入 `credential.secret_encrypted`（`03 §4.1`、`05 §3.3`；早期版本曾写作 `secret_cipher`，**字段名以 `05` DDL 为准**），主密钥来自环境变量 `FLOWOPS_CRED_MASTER_KEY`（缺失则拒绝启动，M-06）。
**日志**：请求体日志过滤器对 `secret`、`password`、`token` 字段自动打码（`08 §4.3`）。

### 6.3 算子版本上传（multipart + 校验失败态）

```

  multipart:
    file                    二进制
    meta                    JSON 字符串（description / os_type / start_command / work_dir /
                            env_vars[] / param_template[] / output_declarations[] / default_resource{}）
  →
  成功: 201 + operator_version{..., file_checksum(SHA-256 服务端计算)}
  失败: 42210 + errors[]{field, message}      ← 原型含校验失败演示态
```

**校验项**：文件类型白名单（`.jar/.py/.sh/.bat/.exe/.zip`）、大小上限（默认 500MB）、SHA-256 去重（同算子同 checksum 已存在 → 提示「该文件已上传为版本 v3」）、`start_command` 非空、`output_declarations[].var_name` 符合 `[a-zA-Z_][a-zA-Z0-9_]*`。

### 6.4 任务提交（并发闸门，D-12）

```
POST /tasks
  body: { workflow_id, version_id?, run_params{}, target_queue_id?, priority?, biz_date? }
  headers: Idempotency-Key（强烈建议）

响应分流：
  201 + task{PENDING}                      正常入队（queue_position 缺省为 0/不返回）
  201 + task{PENDING, queue_position: N}   策略=QUEUE，超并发进等待（**注意：非错误**）
  40901 + running_task_id                  策略=FORBID 且已在运行
  40902 + max_waiting                      策略=QUEUE 但**等待数**已满
  40300 / 40301                            无权限 / 越权
```

**⚠️ 关键语义**：`QUEUE` 策略下「排入等待」是**成功**（`code=0`），不是错误。前端据此渲染「已排队，前方 N 个任务」，而非错误提示。这一点在原型 `workflow-detail` 的提交结果里已体现，契约需明确。

> **v3 评审修订（两处）**
>
> 1. **删除 `QUEUED_WAITING` 状态**。它不在 `05 §3.5` 的 `task.status` CHECK（9 态）里，也不在 `06 §2.1` 转移表与 `07 §3.5` Java 枚举里——落库会违反 CHECK 约束。排队语义统一表达为 **`PENDING` + `queue_position`**（`06 §2.1`：「并发检查不通过（QUEUE）→ 保持 `PENDING`，记录队列位置」）。因此两个分支都是 `201`（任务确实已创建），**用 `queue_position` 而非状态码区分**。
> 2. **删除提交时的 `40904`**。互斥锁是**步骤级、在出队后节点匹配成功时才竞争**（PRD §12.3 / `06 §6.1`），不是任务提交级。按旧写法，一个加锁步骤排在 DAG 末端（几小时后才执行）的任务，会在提交瞬间被拒，产生大量"根本没到那一步"的 409。`40904` 保留，但改由**诊断查询**返回（见 §6.6）。

`ConcurrencyGuard` 判定链（`06 §6.2`）：**提交时**只检查**项目额度 → 工作流额度**两层；**队列并发额度在出队时检查**（`06 §6.1`），互斥锁在**步骤执行前**检查。

**两个队列额度不可混为一谈**：

| 额度 | 字段 | 检查时机 | 超限行为 |
|---|---|---|---|
| 等待数上限 | `queue.max_waiting_tasks` | **提交时** | `40902` |
| 并发上限 | `queue.max_concurrent_tasks` | **出队时**（`06 §6.1`） | 该队列本次不出队，任务保持 `PENDING` |

### 6.5 回填：双闸门（预览 → 提交）

```
POST /backfills/preview        （不落库）
  body: { workflow_id, biz_from, biz_to, concurrency, sequential, overrides{} }
  data: {
    tasks: [{ biz_date, planned_task_id, planned_at, conflict:{task_id,status}|null }],
    skipped_dates: [...],          // 越窗：< 今天-180 或 > 昨天
```

### 6.6 互斥组（步骤级锁，不在提交路径上）

`mutex_group` 是**全平台级串行锁**，作用于**步骤实例**而非任务（PRD §12.3 / `06 §6.3`）。

**正确的竞争时机**：任务出队 → 节点匹配成功 → `tryAcquireMutex(...)`（步骤执行前）。拿不到锁的步骤进入 `WAITING_RESOURCE`，阻塞原因记为 `MUTEX_GROUP`；**任务本身状态保持 `PENDING`/`RUNNING` 不变**，不会在提交时返回错误。

> **v3 评审修订**：本节原写「提交时若组被占用则 `40904` / 进等待」，与 PRD §12.3 及 `06 §6.1` 冲突，已按上游回退。`40904` 不再是提交接口的错误码。

**`40904` 的保留用途**：由**诊断查询**返回（不是提交接口）——当调用方查询「某任务/步骤为何还没跑」时，若当前阻塞原因是互斥锁，返回：

```
GET /tasks/{id}/diagnosis
  200 + {
    task_id, status, queue_position,
    blocking_reasons[]: [
      { type: "MUTEX_GROUP",
        mutex_group: "db-migration",
        step_name: "schema_sync",
        holder_task_id: 10087, holder_step_id: 53210,
        holding_since: "2026-09-24T10:02:11Z",
        holding_seconds: 7413,
        waiters_count: 3 }        // 见 06 §6.3 的 waiters ZSet
    ]
  }
  40904 + mutex_group          仅当调用方显式要求「现在能否立即执行」的判定（如 dry-run / 试运行）时使用
```

**运维可观测性要求**：`holding_seconds` 与 `waiters_count` 必须可查——`06 §6.3` 的锁等待者 ZSet 提供了 `waiters_count`，`holding_since` 来自锁的 value。互斥锁长期占用（建议 > 30 min）应触发告警（见 `08 §3.2`）。

**禁止**在互斥组上做优先级插队（会破坏串行语义）——`POST /tasks/{id}/enqueue-front` 对互斥组任务返回 `42200 + rule:"MUTEX_GROUP_NO_PRIORITY"`。

## 7. 横切关注点

### 7.1 trace_id 贯穿（回写 F-01）

```
客户端（可选 X-Trace-Id）
   ↓
网关/过滤器 TraceFilter：无则生成（UUID 去连字符，32 位 hex）
   ↓ 放入 MDC.put("traceId", ...)
Controller → Service → Mapper → 日志（logback pattern 含 %X{traceId}）
   ↓
ApiResult.traceId = MDC.get("traceId")  →  JSON 出参 "trace_id"
   ↓
审计表 audit_log.trace_id 落库
   ↓
GET /trace/{trace_id} 串联查询
```

**规范**：
1. 一个 HTTP 请求 = 一个 `trace_id`，全链路复用，**不新建**；
2. 定时触发/调度器内部动作：调度决策时生成 `trace_id`，贯穿整个任务的步骤执行（任务详情页「追踪链」能看到触发→调度→执行→结束全链）；
3. `trace_id` 在响应头 `X-Trace-Id` 同时回写（便于前端在 5xx 时展示）；
4. 日志格式：`%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level [%X{traceId}] %logger{36} - %msg%n`。

### 7.2 幂等（D-17，新增）

**为什么需要**：提交任务、提交回填、发布版本这三类操作重复点击/网络重试会造成重复业务对象。

| 项 | 约定 |
|---|---|
| 请求头 | `Idempotency-Key: {client_uuid}` |
| 服务端存储 | Redis `idem:{user_id}:{key}` → 响应体快照，**TTL 24h** |
| 命中同 key + 同请求体 | 返回**首次的响应**（含首次的 `code`），不重复执行 |
| 命中同 key + 不同请求体 | `40903` |
| 未带 key | 正常执行（不强制） |
| 必带场景 | `POST /tasks`、`POST /backfills`、`POST /workflows/{id}/publish`、`POST /operator-versions/{id}/publish` |

**前端/后端职责口径（v3 评审明确）**：**前端必带、后端不强拒**。上述 4 个高危端点前端一律生成并携带 `Idempotency-Key`（`04 §4.2`），其余写操作也建议带；后端在一期仅对这 4 个端点强制校验，未带 key 的其它写操作正常执行。这样后端将来若收紧为"全部写操作强制"，前端不会大面积 `40903`。

**实现**：`@Idempotent(ttl = 86400)` 注解 + AOP；AOP 在方法执行前 `SETNX`，执行后写入响应快照。

### 7.5 轮询与 WebSocket（D-07 / D-10）

| 场景 | 通道 | 参数 |
|---|---|---|
| 列表/看板 | HTTP 轮询 | 工作台 5s；任务列表 5s（有运行中任务时）/ 30s（空闲时） |
| 任务详情步骤状态 | HTTP 轮询 | 5s（任务终态后停轮询） |
| 步骤实时日志 | **WebSocket** | `ws://{host}/ws/tasks/{taskId}/steps/{stepInstanceId}/logs?offset={n}` |
| 平台健康度 | HTTP 轮询 | 10s |

**WebSocket 协议**：

```jsonc
// 服务端 → 客户端
{ "type": "LOG",   "seq": 1024, "content": "...", "stream": "stdout" }
{ "type": "EOF",   "seq": 2048, "exit_code": 0 }          // 步骤结束
{ "type": "ERROR", "code": 50301, "message": "调度器切换中" }

// 客户端 → 服务端
{ "type": "ACK",  "seq": 1024 }      // 确认已渲染，服务端据此清理 Redis Stream 缓存
{ "type": "SEEK", "offset": 512 }    // 回看历史（断线重连后续传）
```

**续传语义**：服务端保留日志于 Redis Stream（`task:log:{taskId}:{stepSid}`，TTL 2h），客户端断开时记录 `seq`，重连传入 `offset` 从该位置继续。**断线不丢日志、不重复推送**。

**降级**：WebSocket 握手失败（企业代理阻断）→ 自动降级为 `GET /tasks/{id}/steps/{sid}/logs?offset=` 轮询（1s）。前端在 `useLogStream` composable 内封装，视图无感。

## 9. 变量体系实现规范（回写 B-01）

### 9.1 引用语法定案（D-20）

**冲突回顾**：

| 出处 | 语法 |
|---|---|
| PRD §10.0.3 **（v3 已回写）** | `${step.{步骤名}.output.{变量名}}`（原为 `${步骤标识.输出标识}`） |
| SPEC-02 §6.12 | `${step.{步骤名}.output.{变量名}}` |

**定案：采纳 SPEC 版** `${step.{步骤名}.output.{变量名}}`。

**理由**：
1. **可校验收紧**：`step` 与 `output` 是字面量关键字，解析器可精确锚定；PRD 版的两个占位符之间用 `.` 分隔，与「变量名本身可含点」的场景冲突。
2. **步骤名可含中文/数字**：`${step.数据清洗.output.row_count}`，语义直观，用户在画布上看到的就是步骤名。
3. **预留扩展**：未来增加变量来源只需新关键字（`${trigger.xxx}`、`${project.xxx}`、`${platform.xxx}`），与 PRD §15.2-5「变量解析器需可扩展」一致。

**完整语法（EBNF 简版）**：

```ebnf
var_ref      = "${" source "." path "}" ;
source       = "step" | "trigger" | "project" | "platform" | "task" ;
path         = step_path | plain_path ;
step_path    = step_name ".output." var_name ;
step_name    = ident | quoted ;           (* 含特殊字符时用引号 *)
var_name     = ident ;
ident        = [a-zA-Z_] [a-zA-Z0-9_]* | CJK+ ;
```

**示例**：

```
${step.数据清洗.output.row_count}
${step.数据清洗.output.file_path}
${step."步骤-2".output.result}          ← 步骤名含特殊字符时引号包裹
${trigger.fire_time}
${project.param.biz_date}
${platform.base_dir}
```

### 9.2 DAG 发布前校验（PRD §10.8 的 8 条规则 + 2 条实现补充，落地为 `42213`）

> **v3 评审修订（重要）**：本节原表与 PRD §10.8 / `03 §4.3` 是**两套规则**——原表自创了「至少 1 个步骤 / 入口唯一性 / 出口可达 / 步骤名唯一 / 重试次数 ≤ 10」，并**丢掉了 PRD 的「必填参数必须填写」「资源要求不超集群队列上限」「必须声明并发控制配置」三条**。丢掉的三条里有两条是硬约束（必填参数空着也能发布 = 明确的线上事故）。现按上游回退，**规则编号以 PRD §10.8 为准**，`errors[].rule` 直接使用下表编号（前后端共用）。

| # | 规则（= PRD §10.8 / `03 §4.3` 编号） | 实现要点 | 错误信息模板 |
|---|---|---|---|
| 1 | 至少一个入度 0 步骤，且**所有执行步骤可达**（备注除外） | 邻接表 + BFS 拓扑遍历，收集不可达步骤 | `步骤「X」不可达` |
| 2 | 所有执行步骤必须选择算子 + 版本 | `stepType=TASK` 时校验 `operator_id` / `operator_version` | `步骤「X」未选择算子或算子版本` |
| 3 | **必填参数必须填写** | 按算子版本 `param_template[].required` 比对步骤 `params` | `步骤「X」缺少必填参数「Y」` |
| 4 | 变量引用必须有效（存在且为**可达上游**） | 反向可达集计算 + 引用解析（§9.1）；UI 只展示可达上游供引用（PRD §20.3-3） | `步骤「X」引用了不可达的变量 ${...}`（`42214`） |
| 5 | 连线不能形成环 | Kahn 拓扑排序，剩余节点即环成员 | `检测到循环依赖：A → B → C → A` |
| 6 | 步骤资源要求不超过目标集群/队列上限 | 聚合步骤资源 vs `cluster` / `queue` 上限（**需后端**，前端无全量配额数据） | `步骤「X」资源要求超出队列「Y」上限（申请 8 核 / 上限 4 核）` |
| 7 | 已停用算子/版本不能发布 | join `operator_version` 校验 `publish_status` | `步骤「X」引用了未发布的算子版本`（`42218`） |
| 8 | 必须声明并发控制配置 | 校验 `concurrency_policy` + `max_parallel_runs` 非空（PRD §10.7） | `工作流未声明并发控制配置` |

**PRD 8 条之外，实现倒逼补充的 2 条**（需回写 PRD §10.8）：

| # | 规则 | 为什么必须有 | 错误信息模板 |
|---|---|---|---|
| 9 | 重试次数 ≤ `MAX_RETRY`(10) | 防止重试风暴打垮节点（E-04） | `步骤「X」重试次数超过上限 10` |
| 10 | **步骤名全局唯一** | D-20 变量语法 `${step.{步骤名}.output.{变量名}}` 以**步骤名**为引用键；重名会导致变量解析二义 | `步骤名「X」重复` |

**校验时机**：

- `PUT /workflow-versions/{id}`（保存草稿）：**只做结构校验**——规则 1（入度/可达性）、规则 5（无环）、规则 10（步骤名唯一）。
- `POST /workflows/{id}/publish`（发布）：**全量 10 条**。

> **保存草稿不做全量校验**——否则编辑中途无法保存，体验不可接受。这条不变，但注意结构校验的**规则编号已随上表变更**。

### 9.3 六层覆盖链（PRD §10.0.1 / `03 §4.4`）

```
平台变量 < 项目参数 < 工作流参数 < 触发时参数 < 上游步骤输出 < 步骤参数
（低）                                                                    （高）
```

**落库**：解析后的最终值写入 `task.variable_snapshot`（JSONB），敏感值按 `sensitive` 标记脱敏（M-07：**不落原文**）。

**运行时快照示例**（任务详情页「参数」标签）：

```json
{
  "resolved": {
    "input_path": "/data/2026-09-21/",
    "row_count": 15234,
    "api_key": "***"
  },
  "sources": {
    "input_path":  { "layer": "TRIGGER", "ref": "${project.param.biz_date}" },
    "row_count":   { "layer": "UPSTREAM_OUTPUT", "ref": "${step.数据清洗.output.row_count}" },
    "api_key":     { "layer": "STEP_PARAM", "masked": true }
  }
}
```

`data.sources` 是**排障关键**：用户能直接看到「这个值是哪一层给的」，是 PRD §10.0.4 的要求。
