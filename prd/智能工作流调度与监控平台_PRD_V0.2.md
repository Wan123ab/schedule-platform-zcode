## 2. 产品背景（V0.2 修订：补充量化现状）

### 2.1 现状问题

企业内部自动化任务、批处理任务、算法计算任务、数据处理任务和业务运维任务持续增加，目前以脚本、定时任务（crontab）、人工登录服务器执行、独立调度系统等方式承载，存在以下问题：

1. 任务分散在不同机器或系统中，缺乏统一管理。
2. 执行过程不透明，失败后排查依赖人工登录服务器查看日志。
3. 脚本、程序包、参数和版本缺少资产化管理。
4. 多个团队共用计算资源时，缺少队列、权限、配额和资源隔离。
5. 业务人员依赖开发或运维代执行，无法自助编排和触发任务。
6. 集群资源状态、任务积压、执行节点健康情况缺少统一监控视图。
7. **任务失败缺少主动通知，问题由业务侧先发现再反向追溯。**
8. **执行节点的资源申请与实际使用严重脱节，资源利用率低且无量化依据。**

## 3. 产品目标

### 3.1 总体目标

建设一个支持算子管理、可视化 DAG 编排、多集群调度、任务运行监控、日志追踪、多租户隔离和运维治理的智能工作流调度与监控平台。

### 3.2 业务目标（V0.2 修订：改为可量化表述）

| # | V0.1 表述（不可验证） | V0.2 可量化表述 |
| --- | --- | --- |
| 1 | 降低业务人员使用自动化任务和计算任务的门槛 | 业务人员无需编写任何代码或命令、无需运维介入，可独立完成一次计算任务的提交，端到端时长 ≤ 2 小时 |
| 2 | 提升运维人员对集群、节点、队列和任务的统一管控能力 | 运维在一处即可完成集群/执行节点/队列/任务的查看与干预，干预操作（停止、插队）的响应时间 ≤ 10 秒 |
| 3 | 实现算子、工作流、任务和执行日志的标准化管理 | 100% 的算子具备版本号与参数模板；100% 的任务可追溯到对应的工作流版本与算子版本 |
| 4 | 支持多团队共享平台能力，同时保障资产、任务和资源隔离 | 不同项目的资产互不可见（平台管理员除外）；跨项目访问 0 例 |
| 5 | 为未来 Docker、K8s、事件驱动和智能调度能力预留扩展空间 | 执行环境、触发器、调度策略三层均以接口抽象实现，新增一种执行环境不改动调度核心 |

### 3.3 成功指标（V0.2 新增）

**北极星指标**：平台承载的任务数占公司可执行任务总数的比例，**6 个月内达到 60%**。

支撑指标：

| 维度 | 指标 | 目标值 |
| --- | --- | --- |
| 效率 | 业务人员任务交付时长 | 从 天级 降至 ≤ 2 小时 |
| 效率 | 任务平均排障时长 | 从 30 分钟 降至 ≤ 5 分钟 |
| 质量 | 任务失败平均发现时长 | 从 小时级 降至 ≤ 5 分钟 |
| 质量 | 调度链路可用性 | ≥ 99.9% |
| 采纳 | 接入团队数 / 周活跃用户数 | 首年 10 个团队 / 100 DAU |
| 成本 | 执行节点平均 CPU 利用率 | 从现状基线提升至 ≥ 60% |

### 3.4 MVP 目标（V0.2 修订）

MVP 阶段完成从算子上传、工作流编排、任务触发、集群调度到任务日志查看的完整闭环，**并且必须包含生产可用的安全底线与通知能力**：

1. 支持项目空间与基础权限隔离。
2. 支持集群、执行节点、队列管理及资源监控。
3. 支持算子上传、详情、编辑、删除与参数模板。
4. 支持可视化工作流编排：步骤、连线、串行、并行、备注。
5. 支持手动触发与定时触发，预留 API 触发与事件触发。
6. 支持任务详情查看完整 DAG、当前执行步骤、步骤日志与执行结果。
7. 支持任务停止、**失败步骤重跑**、基础审计日志。
8. **支持凭据管理（创建、引用、轮换、失效处理）。**（V0.2 新增）
9. **支持失败告警通知（至少一种渠道）。**（V0.2 新增）
10. **支持工作流与步骤的并发/互斥控制。**（V0.2 新增）
11. **支持节点间参数传递（上游步骤输出引用）。**（V0.2 新增）

## 4. 产品定位与边界

### 4.1 产品定位

本平台定位为企业内部公共计算工作流基础设施平台，提供统一的可执行资产管理、低代码工作流编排、分布式任务调度、运行监控和资源治理能力。

### 4.2 产品不做什么

MVP 阶段暂不做以下能力：

1. 不做完整数据资产管理平台。
2. 不做复杂 BI 报表和数据血缘分析。
3. 不做完整 CI/CD 发布流水线。
4. 不做容器编排平台替代品。
5. 不做跨云资源成本优化。
6. 不做复杂机器学习训练平台能力。
7. 不保存和管理大规模任务产物文件，仅保留执行日志和基础执行结果（资源使用度量除外，见 13.4）。

### 4.3 竞品分析与本平台差异点（V0.2 新增）

> 立项评审必答问题：既然已有成熟开源方案，为什么自研？

| 方案 | 与本平台的能力重合度 | 不满足本案诉求的地方 |
| --- | --- | --- |
| **Apache DolphinScheduler** | **最高**（可视化 DAG、多租户、队列、Worker 分组、告警均有） | ① **算子资产的版本化与参数模板体系较弱**，无法把"可执行程序 + 参数定义 + 运行约束"作为一等资产沉淀；② 面向业务人员的**零代码参数表单**能力不足；③ 与公司现有项目/权限体系融合需大量改造 |
| Apache Airflow | 中（DAG 能力强） | DAG 需以 Python 代码定义，**业务人员无法自助编排**（恰是本案第 5 个痛点）；多租户与资源隔离能力弱 |
| XXL-JOB | 低 | 轻量定时任务调度，**无 DAG 编排、无资源调度、无多租户** |
| Azkaban / Oozie | 低 | 生态停滞，不再演进 |

**本平台的三条核心差异点**（若以下立论不成立，应重新评估基于 DolphinScheduler 二次开发的路径）：

1. **算子资产化**——把可执行程序/脚本作为一等公民管理（文件、版本、启动命令、参数模板、运行约束、资源画像），而不只是编排任务。
2. **面向业务人员的零代码体验**——参数模板让业务人员只需填写表单即可提交计算任务，无需理解脚本与命令。
3. **多集群统一资源池**——跨集群的队列、额度、凭据与运维干预统一管理，并具备资源使用画像与治理建议能力。

### 4.4 未来扩展方向

1. 支持 Docker 和 K8s Job 执行环境。
2. 支持文件、报告、数据集等执行产物管理。
3. 支持智能调度、异常预测和失败原因归类。
4. 支持更丰富的事件触发源。
5. 支持资源配额、计量和成本统计。

## 6. 核心业务流程

### 6.1 算子到任务执行流程

1. 算子维护者上传算子文件。
2. 算子维护者创建算子版本，配置启动命令、参数模板、运行系统和默认资源要求。
3. 算子维护者可**在目标执行节点上试运行算子版本**，验证命令正确性（V0.2 新增，见 10.6）。
4. 业务人员或项目管理员创建工作流。
5. 用户在画布中拖拽步骤，为步骤选择算子、版本和参数。
6. 用户通过连线配置步骤执行顺序，形成 DAG。
7. 用户为步骤参数引用上游步骤的输出变量（V0.2 新增，见 10.0）。
8. 用户发布工作流版本。
9. 用户手动触发、定时触发或通过外部方式触发工作流。
10. 平台生成任务实例和步骤实例。
11. 调度器根据队列、资源、执行节点状态和调度约束选择执行节点。
12. 执行器在目标服务器上运行算子。
13. 平台采集实时日志、步骤状态和执行结果。
14. 用户在任务详情页查看完整 DAG、当前执行步骤、历史日志和实时日志。
15. 任务失败时，平台按告警规则主动通知相关人（V0.2 新增，见 10.12）。

### 6.2 集群资源管理流程

1. 运维人员创建集群。
2. 运维人员为集群添加执行节点，并绑定凭据引用。
3. 平台按固定间隔采集执行节点在线状态和资源指标（规则见 12.2）。
4. 运维人员配置集群队列、并发上限、优先级规则和等待策略。
5. 任务提交后进入目标队列。
6. 调度器根据队列规则和执行节点资源分配任务。
7. 运维人员可查看集群正在执行、待执行和历史任务。
8. 运维人员可对正在执行任务进行强制停止，对待执行任务进行插队。
9. 平台持续记录步骤实例的资源使用，形成工作流与步骤的资源画像（V0.2 新增，见 13.4）。

### 6.3 多租户使用流程

1. 平台管理员创建租户或项目空间。
2. 项目管理员添加项目成员并分配角色。
3. 用户只能访问被授权项目内的算子、工作流和任务。
4. 项目可以绑定可用集群、可用队列或资源额度。
5. 运维人员可查看其被授权集群上的全部任务，但运行参数与日志默认脱敏（V0.2 修订，见 11.3）。
6. 操作行为进入审计日志，便于追溯。

### 7.2 实体关系（V0.2 新增）

> 以下基数关系为设计约束，数据库建模必须满足。

| 关系 | 基数 | 说明与约束 |
| --- | --- | --- |
| 租户 → 项目空间 | 1 : N | 一个项目必须属于且仅属于一个租户 |
| 项目空间 ↔ 用户 | **M : N** | 一个用户可属于多个项目；通过「项目成员」关联表维护，关联表携带项目角色 |
| 项目空间 ↔ 集群 | **M : N** | 一个项目可使用多个集群，一个集群可服务多个项目 |
| 项目空间 ↔ 队列 | **M : N** | 通过「队列可用项目范围」维护 |
| 集群 → 执行节点 | 1 : N | 执行节点不可跨集群 |
| 凭据 → 执行节点 | 1 : N | **凭据删除前必须校验引用计数 = 0**；轮换需支持引用反查 |
| 算子 → 算子版本 | 1 : N | MVP 阶段可只允许 1 个版本，但表结构按 1:N 设计 |
| 算子 → 项目空间 | N : 1 | 算子归属唯一项目（V1.1 增加平台级公共算子） |
| 算子版本 → 参数定义 | 1 : N | 参数定义随版本快照，版本发布后不可改 |
| 算子版本 → 输出声明 | 1 : N | 同上 |
| 工作流 → 工作流版本 | 1 : N | 已发布版本不可修改、不可删除（否则历史任务无法回溯） |
| 工作流版本 → 步骤 | 1 : N | 步骤属于版本快照 |
| 步骤 → 算子版本 | N : 1 | **删除算子版本前必须校验引用计数 = 0** |
| 步骤 → 步骤（连线） | M : N | 通过边表维护，必须做环检测 |
| 工作流 → 触发器 | 1 : N | 一个工作流可配置多个定时触发器 |
| 触发器 → 工作流版本 | N : 1 | 可配置为「锁定某版本」或「跟随最新发布版本」，默认锁定 |
| 工作流版本 → 任务 | 1 : N | 任务强绑定执行时的版本快照 |
| 任务 → 步骤实例 | 1 : N | 步骤实例数量 = 所属工作流版本的步骤数 |
| 步骤实例 → 日志 | 1 : N | 日志按步骤实例独立存储 |
| 告警记录 → 任务 / 执行节点 | N : 1 | 告警对象为任务或执行节点 |

## 10.0 参数与变量体系（V0.2 新增 · P0）

> 本章为 V0.2 最重要的新增章节。V0.1 未定义步骤间的数据流转机制，会导致 DAG 退化为"顺序执行器"。

### 功能目标

让工作流中的步骤能够安全、可校验地传递数据，使 DAG 真正具备数据流转能力。

### 10.0.1 变量分层与覆盖优先级

| 层级 | 定义位置 | 示例 | 覆盖优先级 |
| --- | --- | --- | --- |
| **平台变量** | 平台内置，不可修改 | `${taskId}` `${workflowVersion}` `${machineIp}` | 最低 |
| **项目参数** | 项目空间配置 | `${project.dataRoot}` = `/data/ecom` | 低 |
| **工作流参数** | 工作流级定义，发布时快照 | `${workflow.bizDate}`（默认取触发日） | 中 |
| **触发时参数** | 手动/定时触发时填写 | 用户指定业务日期、目标队列 | 高 |
| **上游步骤输出** | 由上游步骤的输出声明提供 | `${step.数据清洗.output.outputFilePath}` | 最高 |
| **步骤参数** | 步骤级配置 | 该步骤专属参数值 | 覆盖上述全部 |

**规则**：同层内后定义者覆盖先定义者；高优先级层始终覆盖低优先级层。

### 10.0.2 算子输出声明

算子版本需支持声明"该算子会产出哪些变量"，供下游步骤引用。

| 字段 | 说明 |
| --- | --- |
| 输出名称 | 展示用名称，如「清洗后文件路径」 |
| 输出标识 | 引用用标识，如 `outputFilePath` |
| 类型 | 文本 / 数字 / 布尔 / 日期时间 / 文件路径 |
| 取值方式 | ① 从标准输出按正则提取；② 从指定文件读取；③ 由平台自动填充（如产物路径） |
| 提取规则 | 当选择"正则提取"时填写，如 `OUTPUT_PATH=(.*)` |
| 示例值 | 用于帮助说明与参数校验提示 |
| 是否必填 | 若必填而运行未产出，该步骤判为失败 |

### 10.0.3 变量引用规则（v3 回写 R-2：语法钉死）

1. 步骤参数中通过 **`${step.{步骤名}.output.{变量名}}`** 语法引用上游步骤输出。

   > **v3 回写**：V0.2 原文写作 `${步骤标识.输出标识}`，缺少关键字锚定，当步骤名含中文、含点号（`.`）或与输出变量名重名时无法唯一解析。采纳 SPEC-02 的四段式语法（决策 **D-20**）：
   > - 固定关键字 `step` / `output` 提供解析锚点；
   > - 步骤名允许中文与空格（用 `{}` 包裹）；
   > - **其余层沿用 10.0.1 既有写法**，不引入新前缀：项目参数 `${project.{参数名}}`、工作流参数 `${workflow.{参数名}}`、平台变量 `${taskId}` 等裸名（全量见 §12）。

   示例：
   ```
   ${step.数据清洗.output.outputFilePath}     ← 上游步骤输出（10.0.1 最高优先级层）
   ${step.特征计算.output.modelPath}
   ${workflow.bizDate}                        ← 工作流参数
   ${project.dataRoot}                        ← 项目参数
   ${taskId}                                  ← 平台变量（见 §12）
   ```

2. **只能引用真上游**：编辑步骤参数时，平台自动列出"可达的上游步骤"，不可引用非上游节点（防止运行期取不到值）。
3. 引用不存在的变量 → 发布前校验失败（DAG 校验规则 4）。
4. 引用的上游步骤可能被跳过时，需设置默认值（V1.1 支持跳过语义后生效）。
5. **步骤名在工作流内必须唯一**（DAG 校验规则 10）——否则变量引用无法绑定到确定步骤。

### 10.0.4 运行时变量快照（排障必需）

任务详情页必须展示每个步骤**实际解析后**的参数值：

```
步骤「特征计算」运行参数
├ 申请集群：prod-compute-01 / high-priority
├ inputPath   = /data/ecom/20260920/cleaned/orders.parquet   ← 引用自 ${step.数据清洗.output.outputFilePath}
├ bizDate     = 2026-09-20                                    ← 引用自工作流参数
├ taskId      = TASK-20260920-0042                            ← 平台变量
└ 底层命令：/usr/bin/spark-submit --input /data/ecom/... --date 2026-09-20
```

**要求**：快照中不展示敏感参数明文（见 13.3）。

## 10.2 租户与项目空间

### 功能目标

实现多团队隔离，保证不同项目之间的算子、工作流、任务、凭据和资源权限互不干扰。

### 功能点

1. 创建、编辑、停用项目空间。
2. 项目成员管理（增删成员、分配项目角色）。
3. 项目可用集群和队列配置。
4. 项目资源额度配置：MVP 支持最大并发任务数、最大等待任务数。
5. 项目下算子、工作流、任务数据隔离。

## 10.5 凭据管理（V0.2 新增 · P0）

### 功能目标

将连接执行节点所需的认证信息作为独立、安全、可轮换的资产进行管理。V0.1 中凭据仅被提及 4 次而无任何管理设计，但它是全平台安全等级最高的资产。

### 功能点

1. **凭据列表**：名称、类型（密码 / 私钥）、归属（平台级 / 项目级）、引用执行节点数、最近使用时间、状态（正常 / 即将过期 / 已失效）。
2. **创建凭据**：填写名称、类型、认证信息；生成唯一指纹（推荐 SHA-256 前 8 位）用于识别。
3. **脱敏展示**：列表与详情页**永不回显明文**，仅展示名称 + 指纹。
4. **引用关系**：点击凭据可查看"被哪些执行节点引用"，轮换影响范围必须对操作者可见。
5. **轮换流程**：
   - 新建凭据版本 → 指定灰度执行节点（建议 1 台）→ 验证连通性 → 全量切换
   - 旧版本保留 N 天（默认 7 天）作为回滚窗口
6. **失效处理**：
   - 凭据失效或轮换失败 → 关联执行节点标记为「连接异常」并触发告警
   - **不中断正在运行的任务**（避免批量任务被误杀）
   - 新的调度任务不再派发到"连接异常"的节点
7. **删除保护**：引用计数 > 0 的凭据不可删除。

### 权限规则

| 操作 | 平台管理员 | 运维人员 | 项目管理员 | 其他角色 |
| --- | --- | --- | --- | --- |
| 查看凭据列表（脱敏） | ✓ 全部 | ✓ 被授权集群关联的 | ✓ 本项目级凭据 | ✗ |
| 创建/编辑凭据 | ✓ | ✓ | ✓ 仅项目级 | ✗ |
| 查看凭据明文 | ✗（不允许，包括管理员） | ✗ | ✗ | ✗ |
| 轮换凭据 | ✓ | ✓ | ✓ 仅项目级 | ✗ |

> 设计原则：**没有任何角色可以查看凭据明文**，平台只做引用与注入。

### 审计要求

所有凭据相关操作（创建、编辑、轮换、删除、查看引用关系）强制写入审计日志。

## 10.8 工作流编辑器（V0.2 修订：术语与校验规则）

### 功能目标

让业务人员和运维人员通过拖拽方式完成低代码 DAG 编排，并为每个步骤配置执行算子、参数、资源、超时和重试策略。

### 画布能力

1. 支持拖拽添加步骤。
2. 支持步骤之间连线。
3. 支持串行执行。
4. 支持并行执行。
5. 支持删除步骤。
6. 支持删除连线。
7. 支持移动步骤位置。
8. 支持画布缩放（0.5x ~ 2x）。
9. 支持画布拖动。
10. 支持框选多个步骤。
11. 支持添加备注。
12. 支持保存草稿。
13. 支持发布前校验。
14. **步骤数 > 20 时显示小地图**（V0.2 新增，PRD 性能要求支持 100 步骤）。

### 步骤配置

1. 步骤名称。
2. 步骤描述。
3. 算子。
4. 算子版本。
5. 算子参数（**支持变量引用**，见 10.0）。
6. 执行集群或队列。
7. 运行操作系统约束。
8. **执行节点标签约束**（V0.2 新增，如必须为 `gpu` 节点）。
9. CPU 需求。
10. GPU 需求。
11. 内存需求。
12. 磁盘需求。
13. 超时时间（留空则继承，见 12.5）。
14. 重试次数（留空则继承）。
15. 重试间隔。
16. 失败策略。
17. 自定义参数。
18. **互斥锁名称**（V0.2 新增，见 12.3）。

### 失败策略

MVP 支持：失败后终止整个工作流、失败后重试当前步骤。
后续支持：失败后跳过当前步骤、失败后进入补偿步骤、失败后人工确认继续。

### DAG 校验规则（V0.2 修订）

发布前需要校验：

1. **必须存在至少一个入度为 0 的步骤，且所有步骤均可从上一步骤到达（不存在不可达步骤，备注除外）。**
   > V0.1 表述为"必须至少包含一个开始节点"，但未定义该节点为何物，且与 DAG 允许多入口的语义冲突。V0.2 改为基于入度的可达性校验，**不在 MVP 引入特殊"开始节点"类型**。
2. 所有执行步骤必须选择算子和版本。
3. 必填参数必须填写。
4. 参数中的变量引用必须有效（引用对象存在且为可达上游）。
5. 连线不能形成环。
6. 步骤资源要求不能超过目标集群或队列上限。
7. 已停用算子或版本不能发布。
8. **工作流必须声明并发控制配置**（见 10.7）。
9. **步骤重试次数 ≤ 10**（v3 回写 R-3）。
   > 平台硬上限 `MAX_RETRY = 10`。超出时**截断为 10 并在校验结果中给出警告**（不阻塞发布），因为该值可由运维在平台配置侧调整。理由是防止无限重试把节点资源吃满。
10. **步骤名在工作流内唯一**（v3 回写 R-3）。
   > 步骤名是变量引用 `${step.{步骤名}.output.{变量名}}` 的绑定键（见 10.0.3）。重名会导致引用歧义、日志无法定位步骤、重跑无法指定步骤。校验失败信息须给出重名步骤名。

> **校验时机（实现要求）**：**保存草稿只做结构校验**（规则 2/3/5/10），**发布才做全量 10 条**。否则编辑中途无法保存，体验不可接受。该切分见 `07-接口实现规范 §9.2`。

### 串行与并行规则

1. 若步骤 B 依赖步骤 A，则 A 成功后 B 才可执行。
2. 若多个步骤依赖同一上游步骤，则上游成功后多个下游步骤可并行执行。
3. 若某步骤依赖多个上游步骤，则所有上游步骤成功后该步骤才可执行。
4. 若任一上游步骤失败，按步骤失败策略和工作流失败策略处理。

## 10.9 触发器管理（V0.2 修订：规则明确）

### 触发类型

| 触发类型 | 范围 | 说明 |
| --- | --- | --- |
| 手动触发 | MVP | 用户在页面点击运行 |
| 定时触发 | MVP | 按 Cron 或固定周期自动运行 |
| API 触发 | **一期**（原 V1.1，评审确认提前） | 外部系统经 `POST /openapi/v1/tasks` 触发；X-API-Key 鉴权 + 作用域白名单 + 限流；支持创建/详情/终止/重试四端点；Webhook 状态通知（HMAC-SHA256 签名 + 退避重试）；设计见 `prototype/DESIGN-api-trigger.md` |
| 事件触发 | V1.1 | 接收消息、Webhook 或业务事件触发 |

> **（v0.2d 回写）API 触发提前纳入一期**：原列 V1.1（§22-7 结论"不支持"），评审确认提前。新增权限点 `schedule:openapi:read/write`（47→49）、错误码 40110/40111/40112/42901、4 张新表（api_key/openapi_call_log/webhook_subscription/webhook_delivery）。API 创建的任务与页面触发完全同构（trigger_type='API'），必须经 ConcurrencyGuard（D-12）与幂等键（D-17），不允许任何旁路。

### 手动触发

1. 用户点击运行工作流。
2. 系统弹出运行参数确认面板，**按工作流参数定义动态渲染表单**。
3. 用户填写允许运行时覆盖的参数。
4. 用户选择队列或使用默认队列。
5. 系统生成任务实例；若工作流并发已达上限，按并发策略处理并明确提示用户。

### 定时触发

配置项：

1. 触发器名称。
2. Cron 表达式或固定周期。
3. **版本绑定方式**（V0.2 明确）：`锁定指定版本`（默认）或 `跟随最新发布版本`。
4. **时区**（V0.2 明确）：统一使用平台时区（Asia/Shanghai），在配置处显式展示。
5. **下次执行时间预览**（V0.2 新增）：Cron 输入框下方实时展示"接下来 5 次执行时间"，用于自查表达式正确性。
6. 生效时间范围。
7. 是否启用。
8. **错过触发处理**（V0.2 新增）：平台重启/维护期间错过触发点时，是否补触发；默认开启，单个触发器最多补 3 次。
9. 运行参数。
10. 目标队列。
11. 失败通知配置。

规则：

1. 一个工作流可配置多个定时触发器。
2. 定时触发器绑定方式二选一：锁定指定已发布版本，或跟随最新发布版本。**默认为锁定版本**（避免工作流更新后定时任务行为突变）。
3. 停用工作流时，触发器自动暂停，**并记录每个触发器的原启用状态**。
4. **重新启用工作流时，触发器自动恢复至停用前的状态**（V0.2 明确）。
5. 触发器配置变更需二次确认并写入审计日志。

未开始、等待依赖、等待资源、调度中、运行中、成功、失败、重试中、已跳过（V1.1）、已停止、超时。

### 调度诊断面板（V0.2 新增）

**目的**：解决"我的任务为什么还没跑"这一运维最高频的疑问，避免用户为此登录服务器排查。

当步骤处于「等待依赖 / 等待资源 / 调度中」时，任务详情页展示：

```
当前状态：等待资源
├ 队列位置：第 7 位（共 12 个等待任务）
├ 队列并发：3 / 3 已占满
├ 阻塞原因：等待满足 [CPU ≥ 8 核 且 标签含 gpu] 的 Linux 执行节点
├ 节点情况：prod-compute-01 有 2 台空闲（CPU 4 核，不满足）；prod-compute-02 全部在执行中
├ 预计开始时间：约 12 分钟后（基于该队列近 7 天平均排队时长估算）
└ 建议操作：
   ① 将 CPU 需求由 8 核降至 4 核
   ② 提交至 high-priority 队列
   ③ 联系运维进行插队
```

字段要求：等待位置、队列并发占用、阻塞的具体约束、各集群的可用节点情况、基于历史数据的预计开始时间、可执行的建议操作（可点击直接跳转对应操作）。

### 人工干预

MVP 支持：

1. 停止运行中任务（必须填写停止原因）。
2. 重跑失败任务（生成新任务实例）。
3. **重跑失败步骤**（V0.2 新增：仅重新执行失败及其下游步骤，复用上游已成功的步骤结果，不产生新的任务编号）。
4. 查看调度失败原因。
5. **待执行任务插队**（运维）。

后续支持：跳过失败步骤、从指定步骤继续执行、修改运行中任务优先级、手动迁移任务。

## 10.11 回填补数（V0.2 新增）

### 功能目标

支持对历史时间段批量补跑工作流，这是数据类调度场景的刚需（如"过去 7 天同步失败，需补跑"）。

### 功能点

1. **回填配置**：选择工作流 + 时间范围（起止日期）+ 周期（日 / 周 / 月 / 自定义）+ 业务日期变量。
2. **并发度控制**：设置本次回填的最大并行任务数（默认 1，防止一次补 30 天打爆集群）。
3. **冲突检测**：若时间范围内已有成功的任务实例，提示用户并允许选择"跳过已成功"或"全部重跑"。
4. **回填任务视图**：独立的回填批次列表，展示批次 ID、工作流、时间范围、总实例数、已完成、失败、进行中、进度条。
5. **批次操作**：暂停批次、继续批次、取消批次（取消后不再生成新实例，已运行的继续或按用户选择停止）。
6. **权限**：项目管理员、平台管理员、运维人员（限被授权项目）。

### 规则

1. 补数生成的任务与普通任务记录结构一致，仅额外标记 `backfillBatchId`。
2. 回填同样受项目资源额度与队列并发限制。
3. 回填批次的所有操作写入审计日志。

**项目级额度默认值**

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| 最大并发任务数 `max_concurrent_tasks` | **5** | 项目内同时处于 RUNNING 的任务上限 |
| 最大等待任务数 `max_waiting_tasks` | **50** | 超出则新任务直接被拒（`40902`），不再排队 |
| 可用算子范围 | **仅项目内** | MVP 不做跨项目算子共享（V1.1，见 §18.4） |
| 可用集群 / 可用队列 | **创建时显式指定** | 不提供"默认全选"，避免新项目意外占用全部资源 |

**队列级额度默认值**

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| 最大并发任务数 `max_concurrent_tasks` | **3** | ⚠️ 见下方说明 |
| 最大等待任务数 `max_waiting_tasks` | **50** | 同上项目级语义，作用于单队列 |
| 默认优先级 `default_priority` | **0** | 范围 0~100，越大越优先 |
| 是否允许插队 `allow_jump_queue` | **false** | 关闭；运维执行插队时按 §10.10 授权并留痕 |
| 等待超时时间 `wait_timeout_seconds` | **3600**（1 小时） | 超时后步骤标记「调度失败」（§12.2-6） |

> ⚠️ **队列级 `max_concurrent_tasks = 3` 偏保守，建议业务方重点复核**。按 §16 容量目标，首年峰值为 500 次/小时、全平台并发运行 300；若队列数量较多（如 20+ 队列），单队列并发 3 会导致大量任务长期排队、等待队列触顶被拒。**建议按"队列数 × 并发上限 ≈ 全平台并发容量"反推**，或在创建队列时由运维按队列实际用途填写而非用默认值。
>
> **队列级与项目级的关系**：两者是**串联**关系（项目额度 → 队列额度，见 §12.3 并发控制层级），任务需同时满足才可执行。因此默认值应按"项目额度 ≥ 其下所有队列额度之和"来配置，否则队列额度永远吃不满。

## 12. 调度与执行规则

### 12.1 调度输入

调度器需要综合以下信息：工作流 DAG 依赖关系、步骤资源需求、步骤操作系统约束、**步骤执行节点标签约束**、目标集群或队列、队列并发限制、任务优先级、执行节点在线状态、执行节点剩余 CPU/GPU/磁盘资源、项目资源额度、**工作流并发限制**。

### 12.2 调度规则（V0.2 修订：补充算法级定义）

**调度流程**

1. 步骤依赖满足后进入待调度状态。
2. 待调度步骤进入目标队列。
3. 队列未达到最大并发时允许出队。
4. 调度器选择满足资源和系统约束的空闲执行节点。
5. 若无可用节点，步骤实例保持等待资源状态，并记录阻塞原因（供调度诊断展示）。
6. 若超过等待超时时间，步骤标记为调度失败。

**节点选择策略（V0.2 明确）**

在所有满足约束（操作系统、标签、CPU/GPU/磁盘余量、在线状态、凭据有效）的执行节点中，按以下顺序择优：

1. 当前运行任务数最少
2. 若并列，剩余 CPU 最多
3. 若仍并列，最近一次分配任务时间最早

> 明确排除随机选择，避免热点节点。

**优先级规则（V0.2 明确）**

1. 优先级数值越大越优先。
2. 同优先级按提交时间 FIFO。
3. **入队时排序 + 出队时重新评估**（避免高优先级任务被先入队的低优先级任务长期阻塞）。
4. 队列隔离优先于优先级：低优队列的高优任务不能抢占高优队列的资源。
5. **MVP 不支持抢占式调度**，仅通过队列隔离与手动插队实现资源倾斜。

**亲和性规则（V0.2 明确）**

MVP 提供工作流级「集群亲和」配置：开启后，同一任务的所有步骤优先调度到同一集群，减少跨集群数据传输；不可满足时允许跨集群并在调度诊断中说明。

**心跳与在线状态判定（V0.2 新增 · 关键）**

| 项 | 规则 |
| --- | --- |
| 心跳间隔 | 执行节点每 15 秒上报一次 |
| 判定离线 | **连续 3 次（45 秒）未上报** 才判定为离线，避免网络抖动误判 |
| 离线时运行中步骤的处理 | **不直接判为失败**，标记为「等待执行节点恢复」，保留 5 分钟恢复窗口 |
| 恢复窗口内的处理 | 若节点恢复上报，步骤继续执行；否则标记为失败，失败原因为「执行节点失联」 |
| 疑似失联提示 | 单次心跳缺失时，界面标注「心跳异常」但状态不变，不触发告警 |
| 离线告警 | 判定离线后立即触发告警 |

### 12.3 并发与互斥控制（V0.2 新增 · P0）

**问题**：V0.1 支持多定时触发器与手动触发，却未定义并发规则，会导致同一工作流多个实例同时运行并写入同一资源（经典生产事故）。

**并发控制层级**（v3 回写：原标为「三级控制」，实际含四级，其中互斥锁为步骤级）

| 级别 | 配置项 | 默认值 | 生效方式 |
| --- | --- | --- | --- |
| 项目级 | 最大并发任务数 | 由项目额度决定 | 提交时检查 |
| 工作流级 | 最大并发实例数 | **1** | 触发时检查，超限按策略处理 |
| 工作流级 | 超限策略 | **跳过本次触发并告警** | 可选：排队等待 / 并行执行 |
| 队列级 | 最大并发任务数 | 由队列配置决定 | **出队时**检查 |
| 步骤级 | 互斥锁名称 | 空（不启用） | **出队并匹配到节点后、下发前**竞争（见下方 R-5） |

**互斥锁语义**

0. **竞争时机（v3 回写 R-5）**：互斥锁是**步骤级**的，竞争发生在**步骤出队、完成节点资源匹配之后、下发执行之前**，**不在任务提交路径上**。
   > ⚠️ 因此**提交任务不会返回"互斥组被占用"错误**。提交路径上的并发检查只有三级：项目额度 → 队列额度 → 工作流额度。用户想知道"我的任务是否被某把互斥锁挡住"，走**任务详情的调度诊断**，诊断结果以阻塞原因形式呈现（`40904` 语义）。
1. 步骤配置了互斥锁名称后，全平台**同名锁同一时刻只允许一个步骤实例持有**。
2. 未获取到锁的步骤实例进入「等待资源」状态，阻塞原因显示为"等待互斥锁 `xxx`（当前持有者：任务 xxx / 步骤 xxx）"。
2a. **等待者必须可被唤醒（v3 回写 R-5）**：进入等待的步骤须同时登记到该锁的等待者队列（按原入队序号保序）；**锁释放时立即唤醒队首等待者**重新参与调度。
   > 这是可用性要求而非实现细节：若无唤醒路径，等待者只能干等到「等待超时」（默认 3600 秒）才被判调度失败，上方第 2 条承诺展示的"当前持有者"在整整一小时内都不会刷新——用户看到的是卡死，不是排队。
3. 锁在执行步骤结束（成功/失败/超时/停止）后自动释放。
4. 锁超时保护：持锁超过步骤超时时间后强制释放并记录异常。
5. 互斥锁用于解决"不同工作流操作同一张表/同一份数据"的冲突场景。
6. **互斥锁上禁止优先级插队**（v3 回写 R-5）：对配置了互斥锁的步骤，"插队"操作不可用。
   > 插队会破坏"同名锁严格串行"的语义——被插队的步骤反而要先执行，而这正是互斥锁要防止的。"任务插队"仅对**任务**生效，不改变步骤级串行顺序。

**触发行为的一致性要求**

手动触发、定时触发、API 触发、回填触发**必须使用同一套并发检查逻辑**，不允许某一种触发方式绕过并发控制。

### 12.4 执行规则

1. 执行器根据算子版本的启动命令模板生成实际命令。
2. 平台将用户参数、步骤参数、工作流参数和平台变量注入命令（解析顺序见 10.0.1）。
3. 执行器在目标服务器工作目录中运行命令。
4. 执行过程中持续采集日志。
5. 命令退出码为 0 时默认视为成功（算子可配置其他成功码）。
6. 命令退出码非 0 时默认视为失败。
7. 超过超时时间时终止进程并标记超时。
8. 失败后按重试策略重新执行。
9. **记录步骤实例的实际资源使用峰值与均值**（CPU / GPU / 内存 / 磁盘），用于资源画像（V0.2 新增，见 13.4）。

### 12.5 配置继承链（V0.2 新增）

**问题**：V0.1 中每个步骤都要配置超时与重试，100 个步骤的 DAG 需要配置 100 次。

**继承规则**（优先级由低到高，任一层留空则向上继承）：

```
平台默认值 → 项目默认值 → 工作流默认值 → 算子版本默认值 → 步骤级配置
```

**适用字段**：超时时间、重试次数、重试间隔、失败策略、资源要求（CPU/GPU/内存/磁盘）、运行操作系统约束。

**UI 要求**：留空的字段必须显示继承来源，例如：

```
超时时间  [留空]  继承自：工作流默认（3600s）
重试次数  [2]     （已覆盖工作流默认值 0）
```

### 12.6 平台变量

平台内置变量（不可修改）：

1. 任务编号 `${taskId}`
2. 工作流编号 `${workflowId}`
3. 工作流版本 `${workflowVersion}`
4. 步骤编号 `${stepId}`
5. 项目编号 `${projectId}`
6. 执行集群 `${clusterId}`
7. 执行机器 IP `${machineIp}`
8. 触发人 `${triggerUser}`
9. 触发时间 `${triggerTime}`
10. **业务日期 `${bizDate}`**（V0.2 新增，定时触发与回填场景使用，格式 `YYYY-MM-DD`）
11. **回填批次编号 `${backfillBatchId}`**（V0.2 新增，非回填场景为空）

## 13. 日志与结果规则

### 13.1 日志采集

1. 每个步骤实例独立采集日志。
2. 日志支持实时展示。
3. 日志支持历史查询。
4. 日志至少保留标准输出内容。
5. 支持区分标准输出与标准错误（V1.0）。
6. **日志量上限**（V0.2 新增）：单个步骤实例日志默认上限 100MB，超出后停止采集并追加提示"[日志已达上限 100MB，后续输出已截断]"。
7. **大日志模式**（V0.2 新增）：算子可配置"仅记录尾部 N 行"（如仅保留最后 5000 行），适用于输出极多的计算任务。

### 13.2 日志存储与归档（V0.2 扩充）

| 阶段 | 保留时长 | 能力 |
| --- | --- | --- |
| 热存 | 30 天（可配置） | 在线实时查看、按步骤筛选、关键字搜索 |
| 冷存 | 90 天（可配置） | 仅支持下载，不支持在线检索 |
| 归档后 | 按配置 | 到期删除，删除策略可配置 |

要求：

1. 支持按任务编号查询。
2. 支持按步骤实例查询。
3. 支持按时间顺序读取。
4. **实时通道**（V0.2 明确）：优先采用 WebSocket；断线重连必须支持按 offset 续传，不重复推送。
5. **实时日志延迟**：≤ 5 秒。

### 13.3 日志安全（V0.2 新增）

1. **日志脱敏**：内置脱敏规则，对以下内容自动替换为 `***`：
   - 键值对形式：`password=` `passwd=` `token=` `secret=` `apikey=` `access_key=`
   - 连接串形式：`jdbc:xxx//user:password@host`
   - 私钥块：`-----BEGIN ... PRIVATE KEY-----` 至 `-----END ...-----`
2. **敏感参数脱敏**：参数模板中标记为「敏感参数」的，在所有日志、变量快照、任务详情展示中永久脱敏。
3. **脱敏不可绕过**：脱敏在服务端执行，前端不接触原文。
4. 运维跨项目查看日志原文需授权并留痕（见 11.3）。

### 13.4 执行结果与资源画像（V0.2 新增）

**执行结果（MVP）**：状态、退出码、错误摘要、日志、**变量快照**。

**资源画像（V1.1）**：

平台持续记录每个步骤实例的实际资源使用，形成工作流与步骤级画像，用于资源治理：

```
工作流「每日订单数据同步」近 30 天资源画像
├ CPU：申请 16 核 / 实际峰值 4.2 核 / 均值 1.8 核   → 建议调整为 6 核
├ 内存：申请 32GB / 实际峰值 9.4GB                → 建议调整为 12GB
├ 磁盘：申请 500GB / 实际使用 12GB                → 建议调整为 50GB
├ 单次平均耗时：18m 32s（波动范围 12m ~ 47m）
└ 潜在节省：该工作流可释放约 62% 的申请资源配额
```

同时提供：节点平均利用率统计、资源浪费 Top N 工作流排行、超量申请预警。

**后续扩展**：文件产物、报告产物、数据集产物、产物下载与权限控制。

## 14. 状态机定义（V0.2 新增）

> V0.1 列举了 8 种任务状态与 11 种步骤状态，但未定义状态之间的流转条件。本章为后端状态机实现的直接依据。

### 14.1 任务状态流转

| 当前状态 | 触发事件 | 目标状态 | 附加动作 |
| --- | --- | --- | --- |
| —（初始） | 触发成功（通过并发检查） | 等待中 | 记录 startTime，生成全部步骤实例（均置未开始） |
| —（初始） | 触发时并发已超限 | 不生成任务 | 按并发策略处理（跳过并告警 / 排队） |
| 等待中 | 进入目标队列且队列未满 | 调度中 | 记录队列位置 |
| 等待中 | 用户停止 | 已停止 | 记录停止人与原因，写审计 |
| 调度中 | 首个步骤实例被分配到执行节点 | 运行中 | 记录执行节点 |
| 调度中 | 用户停止 | 已停止 | 同上 |
| 调度中 | 超时未被调度 | 超时 | 记录失败原因「调度超时」 |
| 运行中 | 全部步骤成功 | 成功 | 记录 endTime、总耗时 |
| 运行中 | 任一步骤失败且失败策略为终止 | 失败 | 记录失败原因摘要、未执行步骤置为未开始 |
| 运行中 | 步骤标记为跳过（V1.1） | 部分成功 | — |
| 运行中 | 用户停止 | 已停止 | 记录停止人与原因 |
| 运行中 | 超过任务级超时 | 超时 | 终止执行中的步骤 |
| 成功 / 失败 / 已停止 / 超时 / 部分成功 | — | **终态，不可再流转** | 可通过重跑生成新任务实例 |

**终止态定义**：成功、失败、已停止、超时、部分成功。

### 14.2 步骤实例状态流转

| 当前状态 | 触发事件 | 目标状态 | 附加动作 |
| --- | --- | --- | --- |
| 未开始 | 上游步骤全部成功（或无上游） | 等待依赖 → 立即转为等待资源 | 检查互斥锁与队列 |
| 等待依赖 | 上游步骤成功 | 等待资源 | — |
| 等待依赖 | 上游步骤失败且策略为终止 | 已停止 | 标记「因上游失败未执行」 |
| 等待依赖 | 任务被停止 | 已停止 | — |
| 等待资源 | 满足队列并发 + 互斥锁 + 有可用执行节点 | 调度中 | 记录队列位置与阻塞原因 |
| 等待资源 | 等待超过超时 | 失败 | 失败原因「调度失败：等待资源超时」 |
| 调度中 | 分配执行节点成功 | 运行中 | 记录执行集群、机器 IP、startTime |
| 调度中 | 执行节点不可用 / 凭据失效 | 等待资源 | 记录阻塞原因，重新排队 |
| 运行中 | 退出码为成功码 | 成功 | 记录 endTime、耗时、退出码、资源峰值，解析输出变量 |
| 运行中 | 退出码为失败码且重试次数未用尽 | 重试中 | 写入重试历史，记录本次退出码 |
| 运行中 | 退出码为失败码且重试次数已用尽 | 失败 | 记录失败原因、退出码 |
| 运行中 | 超过步骤超时 | 超时 | 强制终止进程，记录超时 |
| 运行中 | 用户停止任务 | 已停止 | — |
| 运行中 | 执行节点失联超过恢复窗口 | 失败 | 失败原因「执行节点失联」 |
| 重试中 | 等待重试间隔结束 | 等待资源 | 重新参与调度 |
| 重试中 | 用户停止任务 | 已停止 | — |
| 成功 | — | **终态** | — |
| 失败 | — | **终态**（可由用户手动重跑失败步骤） | — |
| 已停止 | — | **终态** | — |
| 超时 | — | **终态** | — |
| 已跳过（V1.1） | — | **终态** | — |

**注意事项**

1. 步骤实例状态变化必须记录时间戳与操作来源（系统 / 用户）。
2. 状态变更必须幂等，重复消息不得导致状态回退。
3. 平台异常重启后，需能根据持久化的状态恢复，不得丢失执行状态。

## 15. 非功能需求（V0.2 修订：量化）

### 15.1 可用性

| 项 | 量化要求 |
| --- | --- |
| 调度链路可用性 | ≥ 99.9% |
| 调度器故障恢复时间 | ≤ 30 秒（自动切换） |
| 平台重启后状态恢复 | 任务状态 0 丢失；运行中的步骤实例在节点侧继续执行，平台恢复采集 |
| 单个执行节点异常影响 | 不影响平台整体可用性；该节点上的运行中步骤按 12.2 心跳规则处理 |

1. 执行环境需要抽象，支持未来扩展 Docker 和 K8s。
2. 触发器需要抽象，支持未来扩展 API、Webhook、消息队列和业务事件。
3. 算子类型需要可扩展。
4. 调度策略需要可扩展。
5. **变量解析器需要可扩展**（V0.2 新增）：支持后续增加新的变量来源。

### 15.3 安全性

1. 凭据不得明文展示（**含平台管理员**）。
2. 敏感参数需要脱敏（含日志、快照、界面展示）。
3. 用户只能访问授权项目数据；运维跨项目访问需授权并留痕。
4. 关键操作需要审计。
5. 上传文件需要进行类型、大小和安全校验。
6. API 触发需要鉴权。
7. **日志内容需自动脱敏**（见 13.3）。
8. **跨项目访问行为必须留痕**（见 11.3）。

### 15.4 性能

| 项 | MVP 目标 |
| --- | --- |
| 任务列表查询响应时间 | < 3 秒（在容量目标规模下） |
| 任务详情 DAG 渲染响应时间 | < 3 秒（100 步骤规模） |
| 实时日志延迟 | < 5 秒 |
| 单工作流步骤数 | ≥ 100 个（展示与运行记录查询） |
| 全平台并发运行任务数 | ≥ 300 个 |

| 调度决策延迟（从可调度到派发） | < 5 秒 |

### 15.5 可观测性

1. 平台服务自身需要有运行日志。
2. 调度决策需要可追踪（每次调度决策记录输入与结果）。
3. 执行节点心跳和资源采集需要可监控。
4. 任务失败原因需要结构化记录（便于后续归类分析）。
5. **平台自身健康度对运维可见**（V0.2 新增）：调度器状态、执行器状态、数据库与中间件健康度，独立于业务监控展示。

## 17. 系统集成与依赖（V0.2 新增）

> 作为企业级公共基础设施平台，能否融入公司现有体系是落地的决定性因素之一。V0.1 未涉及此内容。

| 集成对象 | 必要性 | 集成内容 | 阶段 |
| --- | --- | --- | --- |
| **统一认证（SSO / LDAP / OAuth2）** | 高 | 接入公司统一登录；**MVP 以本地账号兜底**，Sa-Token 侧预留适配层（**v3 回写 R-8**：阶段由 MVP → 一期尾部） | **一期尾部** |
| **组织架构 / 用户目录** | 高 | 同步用户与部门信息；**MVP 以手动导入兜底**，同步接口视 SSO 进度启用 | **一期尾部** |
| **消息通知（邮件网关 / 企业微信 / 钉钉）** | **必须** | 告警通知渠道 | MVP |
| **公司统一告警平台** | 高 | 平台自身告警接入统一告警，不重复建设 | MVP / V1.0 |
| **监控体系（Prometheus / Grafana）** | 高 | 暴露平台自身指标（调度队列深度、任务吞吐、执行器健康） | V1.0 |
| **CMDB / 配置管理系统** | 中 | 执行节点信息可能已在 CMDB，避免重复录入与数据不一致 | V1.0 |
| **代码仓库 / 制品库（GitLab / Nexus）** | 中 | 算子文件从制品库拉取，替代手工上传 | V1.1 |
| **数据平台 / 数据目录** | 低 | V2.0 若需数据血缘再考虑 | V2.0 |

### 集成原则

1. **不重复建设**：公司已有的能力（认证、告警、监控）一律对接，不自建。
2. **必须提供兜底**：若统一认证暂不可用，MVP 需支持本地账号登录作为降级方案。
3. **预留但不过度设计**：V1.1/V2.0 的集成点只需保证接口抽象预留。

> **v3 回写 R-8（2026-09-24 确认）**：上表「统一认证」与「组织架构」两行的**阶段由 MVP 调整为一期尾部**，理由如下——
> ① SSO 依赖外部团队排期，属平台不可控因素；若挂 MVP，上线时间会被他人卡住。
> ② 本节「集成原则 2」已明确「若统一认证暂不可用，MVP 需支持本地账号登录作为降级方案」，原阶段列标 MVP 与该原则自洽性矛盾。
> ③ `PRD §22` 第 12 项经业务方确认为「本地账号 + 预留适配层」。
>
> **MVP 的认证口径**：平台自建用户表（Sa-Token，`login-type=flowops`），登录锁定 5 次/15 分钟，**预留 SSO 适配层**——后续接入只改适配层，不动业务逻辑与权限模型。

## 20. 验收标准（V0.2 扩充）

### 20.1 项目与权限验收

1. 用户可以创建项目并添加成员、分配角色。
2. 不同项目的用户默认不能互相查看算子、工作流、任务。
3. 平台管理员可以查看全平台数据。
4. 项目管理员可以管理本项目成员和资产。
5. **运维人员可查看被授权集群上的他项目任务，但参数与日志默认脱敏；查看日志原文需授权且留痕。**
6. **权限矩阵（11.2）中标注的每一种角色与操作的组合，其允许/禁止行为均经过验证。**

### 20.2 凭据管理验收

1. 用户可以创建平台级或项目级凭据。
2. 凭据列表与详情页不展示明文。
3. 用户可以查看凭据被哪些执行节点引用。
4. 用户可以执行凭据轮换并验证连通性。
5. 引用计数大于 0 的凭据不可删除。
6. 凭据失效后关联执行节点标记为连接异常并告警，正在运行的任务不受影响。

### 20.3 参数与变量验收

1. 算子版本可以声明输出变量。
2. 步骤参数可以引用上游步骤的输出变量。
3. 编辑步骤参数时，平台只展示可达的上游步骤供引用。
4. 引用无效变量时发布校验失败。
5. 任务详情页可以查看步骤实际解析后的参数值（变量快照）。
6. 敏感参数在日志与快照中均被脱敏。

### 20.4 算子管理验收

1. 用户可以上传一个算子文件。
2. 用户可以配置算子参数模板与输出声明。
3. 用户可以查看、编辑和删除未被引用的算子。
4. 工作流步骤可以选择算子和版本。
5. **用户可以在指定执行节点上试运行算子版本，并看到实时日志与退出码。**

### 20.5 工作流编辑验收

1. 用户可以在画布上添加步骤。
2. 用户可以通过连线配置步骤依赖。
3. 用户可以配置串行和并行流程。
4. 用户可以在画布上添加备注。
5. 用户可以为步骤配置参数、超时、重试和自定义参数。
6. 用户可以保存草稿并发布工作流。
7. 系统能够在发布前校验 DAG 合法性，且对无效变量引用报错。
8. **用户可以配置工作流的并发控制参数。**

### 20.6 集群管理验收

1. 用户可以创建集群。
2. 用户可以为集群添加执行节点并绑定凭据。
3. 用户可以查看执行节点总数、在线数、离线数和空闲数。
4. 用户可以查看 CPU、GPU、磁盘资源使用情况。
5. 用户可以配置任务等待队列。
6. 用户可以查看集群正在执行任务、待执行任务和历史任务。
7. 用户可以强制停止运行中任务。
8. 用户可以对待执行任务进行插队。
9. **用户可以测试执行节点的连通性。**

### 20.7 任务管理验收

1. 用户可以查看任务列表。
2. 用户点击任务详情时可以看到完整执行 DAG。
3. 用户可以看到当前执行到哪个步骤。
4. 用户可以点击 DAG 步骤查看步骤详情。
5. 用户可以查看每个步骤的执行集群和执行机器。
6. 用户可以查看每个步骤的实时日志与历史日志。
7. 用户可以查看任务最终状态和失败原因。
8. **用户可以重跑失败步骤，且上游已成功的步骤不会重复执行。**
9. **等待中的任务可以查看调度诊断，明确看到阻塞原因与预计开始时间。**

### 20.8 调度与并发验收

1. 触发工作流时，若并发已达上限，按配置的策略处理并明确提示。
2. 配置互斥锁的步骤在全平台串行执行。
3. 调度器按"运行任务数最少 → 剩余 CPU 最多 → 最早分配"的顺序选择执行节点。
4. 执行节点连续 3 次心跳缺失才判定离线，且离线时运行中步骤不立即判失败。
5. 优先级数值大的任务先于数值小的任务执行，同优先级 FIFO。

### 20.9 告警验收

1. 任务失败后，配置的接收人在 5 分钟内收到通知。
2. 通知内容包含失败原因摘要与任务直达链接。
3. 同一任务的同一告警在抑制窗口内只发送一次。

### 20.10 审计验收

1. 关键操作均写入审计日志。
2. 审计日志包含操作前/后摘要。
3. 可以按对象聚合查看完整操作链路。

## 21. 上线与运营计划（V0.2 新增）

> 平台建成而无人使用是最大的失败。V0.1 未涉及落地路径。

### 21.1 试点选择

1. 首批选择 **1-2 个意愿强、任务结构相对简单的团队** 试点，不追求一次性铺开。
2. 试点周期建议 4-6 周，目标：跑通真实业务并沉淀首批使用案例。
3. 试点团队的准入条件：有明确的自动化任务痛点、有可配合的对接人、任务不涉及最高安全等级数据。

### 21.2 存量迁移

**这是推广成败的关键**。存量脚本散落在 crontab、shell、各团队自建系统中，迁移成本直接决定采纳率。

必须提供：

1. **脚本导入向导**：上传现有脚本 + 填 cron 表达式 → 自动生成算子与工作流草稿。
2. **crontab 批量解析**：粘贴 crontab 内容，批量识别任务并生成对应工作流。
3. **迁移清单工具**：帮助团队盘点现有任务，标记迁移优先级。

### 21.3 培训与文档

面向不同角色提供分层材料：

| 角色 | 材料内容 |
| --- | --- |
| 业务人员 | 如何提交一个计算任务（视频 5 分钟 + 图文） |
| 算子维护者 | 如何上传算子、配置参数模板与输出声明、试运行验证 |
| 项目管理员 | 如何管理成员、配置项目额度与参数、查看项目运行情况 |
| 运维人员 | 如何管理集群与执行节点、处理告警、干预任务 |

同时提供：Cron 表达式速查、平台变量说明、常见失败码对照表（内置在帮助中心）。

### 21.4 支持与值班

1. 上线初期（前 3 个月）设立明确的答疑渠道（群 / 工单）。
2. 明确支持响应时间承诺：阻断性问题 2 小时内，非阻断问题 1 个工作日内。
3. 建立"平台使用问题 → 沉淀进帮助中心"的闭环。

### 21.5 灰度节奏

| 阶段 | 范围 | 准入条件 |
| --- | --- | --- |
| 阶段 1 | 1-2 个试点团队 | 核心闭环可用、告警与凭据可用、试点团队完成培训 |
| 阶段 2 | 单个业务部门 | 试点稳定运行 4 周无 P0 事故、帮助中心与迁移工具就绪 |
| 阶段 3 | 全公司推广 | 部门级稳定运行 8 周、CMDB/监控集成完成、容量满足目标规模 |

## 23. 风险与建议

### 23.1 产品风险

1. 目标用户包含运维人员和业务人员，页面复杂度和易用性需要平衡。**建议**：工作台按角色提供差异化默认视图；为业务人员提供简化视图。
2. 如果一期同时支持 Linux、Windows、SSH、Agent、API、事件触发，范围容易过大。**建议**：MVP 只做 Linux + SSH，其余预留。
3. 多租户、权限、队列、凭据如果后补，后续改造成本较高。**V0.2 已将凭据、权限矩阵、并发控制纳入 MVP。**
4. 工作流编辑器是高复杂度模块，需要尽早明确交互边界。**建议**：MVP 只做核心 DAG 编排，不做分支、循环、补偿。
5. **【V0.2 新增】参数与变量体系若设计不当，会成为长期技术债。** 建议在 MVP 前完成变量解析器的接口设计与评审。
6. **【V0.2 新增】平台建成而采纳率低是最大风险。** 建议同步准备迁移工具与试点计划，不可等到平台完成后再考虑推广。
7. **【V0.2 新增】生态替代风险。** 若 DolphinScheduler 等开源方案在算子资产化方面补齐能力，需重新评估自研价值。建议按 4.3 的三条差异点持续验证。

### 23.2 建议

1. MVP 优先完成 Linux 服务器执行闭环，Windows 支持作为兼容能力逐步补齐。
2. 一期必须纳入项目空间、权限、队列、凭据和审计的基础模型。
3. 工作流编辑器先做核心 DAG 编排，不急于加入复杂分支、循环和补偿流程。
4. 算子参数模板与输出声明要尽早设计，否则业务人员使用门槛会很高，且 DAG 无法传递数据。
5. 任务详情页应作为核心页面优先打磨，它是排障和信任建立的关键。
6. **【V0.2 新增】告警默认开启**，让用户主动去关，而非主动去开。
7. **【V0.2 新增】资源画像尽早上线**：它是平台向管理层证明"治理价值"的唯一量化依据。
8. **【V0.2 新增】建立术语与命名规范**（第 1 节），从源头避免命名歧义带来的长期成本。
